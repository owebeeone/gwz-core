## Findings

- **P2-1 · design §2.5–§2.6 · joins that hold the GIL deadlock with a failing worker.** The `gwz-py-operation` thread acquires the GIL to build its Python error (`native/src/error.rs:40`, `Python::attach`), and `lib.rs`'s `operation_result` comment records exactly this deadlock. `close()`, `cancel_operation` ("returns its cleanup report", so it waits on the operation's thread) and the `atexit` hook all run as Python code holding the GIL. *Fix:* state that every wait in close, cancel and the atexit hook runs under `py.detach`, bounded by the 5 s cleanup bound; add an S6.3 row: close with a failing operation in flight.
- **P2-2 · design §2.4 · the limit's placement, and whether a waiting operation holds a native thread.** S1.1 (1.1.0 amendment §3.2) requires the revision to "state whether a waiting operation holds a native thread"; the design does not. Today both `call` and `submit` go through `asyncio.to_thread` (`bridge.py` `_run_native`), so a natively enforced wait holds a default-executor thread and delays `submit`'s accepted response; a Python-enforced one (asyncio primitives bind to a loop) is per-loop, not per-`Client`, contradicting §2.4. *Fix:* say where the limit lives (native, on the per-Client object, counting `call` and `submit`), which thread a ninth operation waits on, and how cancel reaches a waiter.
- **P2-3 · design · S1.1's named API parts are missing.** S1.1 lists `TransportCleanup`, `close`/`close_report`, `cancel_operation`, `transport_capabilities`, `configure_transport_runtime` and `Client.meta(max_retries)`, with "`configure_transport_runtime` stays process-wide". The design covers only close, cancel and `TransportCleanup`. Both methods are live (`dispatch/read.rs:13,24`; `client.py:371,419`), and `transport_support::server_timeout_ms` feeds `SshEndpointConfig` (`transport_host/mod.rs:66`), process-wide state the "reads no process environment" variant still reads; S6.3's default-clocks row and S7.3 (1.1.0)'s `transport_capabilities` assertion depend on them. *Fix:* a short section giving each item's per-operation meaning.
- **P2-4 · design + §3.17 · no way back to the native path for gwz-py users.** TR1.5's switch has three forms, flag, environment, user configuration (plan line 263); the flag is CLI-only. OD16's refusal and the migration notes send users to the off switch, and OD6's rationale is that without it downgrading is the only way back. Neither document says the environment and user-configuration forms govern gwz-py's operations (resolved from the snapshot, since the runtime reads no process environment) or what TR1.5's first-operation notice is in gwz-py. *Fix:* one bullet in design §2.2 and in §3.17 placing gwz-py under TR1.5/TR2.5, plus an S6.3 row with the switch on.
- **P2-5 · amendment §3.1 line 72, §3.14 lines 323 and 326 · stale decision records in adopted text.** Both sentences still read "OD14, OD15 and OD16 are open"; the plan's decisions list (after line 32) gains only OD13; OD13's record still says "**1.2.0** ships … gwz-py on the transport". *Fix:* "OD14 decided 2026-10-01 (§3.17); OD15 and OD16 open"; decisions list gains OD14; OD13's 1.2.0 bullet reads "gwz-py through the session host, replacing 1.1.0's per-operation stage (OD14)".
