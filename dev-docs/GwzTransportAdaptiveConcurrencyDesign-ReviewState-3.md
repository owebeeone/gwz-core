## Changed-range analysis

Ranges read in full (from the diff): status/§1/D3/D5/D8 (3, 18, 26, 28, 31); §4.1 (135–136); §4.2 (151); §4.4 (186–205); §4.5 (214–237); §4.6 (276–277); §4.7 (304); §4.8 (331); §4.9 (339–340); §4.10 (350–351); §5.2–§5.3 (378, 394); §5.5 (412–424); cases 2, 3, 22, 27, 29, 31–33, 42–50 (492–540); §11 (556, 558); F16 (577); OQ12/OQ16 (592, 596); §14 items 3, 4, 6, 9, 12, 13, 17–19 (601–623); Changelog (702–714).

- **The restore row as a closed grammar.** Entry: the retry machine becomes Healthy with `N < N_good`, from any limit-machine state. While the retry machine is not Healthy no confirmation can be open (the `k = 1` routing closes it) and no probe can start (`Connected = 0`), so the restore never enters on top of an in-flight test. Exits are complete: Overload → STABLE; a completed step with a refusal and no Overload → STABLE; `N_good` → SATURATED/STABLE. A Suspect refusal in a step opens a confirmation whose hold stops nothing already admitted, waits for the step's wave to resolve, tests at `Connected + 1`, and either Overloads (exit 1) or is refuted (the step then completes with a refusal → exit 2). A Throttle in a step is an Overload at once. No cycle. Against Down/parking: a parked member is not queued on the limit machine's key until the retest succeeds; the retest's own success is the first Connected and starts the restore at `S = max(N, 2)`. One gap: the STABLE probe timer may expire *during* a step (the machine's state during a restore is not named) → P3-11.
- **HTTPS Connected vs `connected()` and `FirstConnect`.** The three moments are now distinct and named. Consequence checked: the retry machine becomes Healthy at TLS (`retry.rs:88-89`) even when the discovery is then throttled, so an HTTPS retest's TLS success starts the restore with `Connected = 0` and `S = N`; the step then fills to `N` and doubling begins from the first answered discoveries. Correct, merely slower by one step. `abandoned` after `succeeded` is a no-op (`machine.rs:211-215`, the flight was already taken), so the retry machine stays Healthy on a throttled key, which is the design's intent (§5.1's rationale).
- **`min(Connected, hi(a))`.** For a conclusive ordinary refusal `hi(a) < N`, so `N` strictly decreases per Overload (monotone, as D3 needs). For a fair confirming test `lo = k − 1 = Connected` at start and quiet precludes Settling, so `N := k − 1`. With `Connected = 0` and `hi ≥ 1` (everything Settling) `N := 1`; the probe's base then fails, admission resumes at `Possible < 1`, the first clean start has `hi = 0` and goes to the retry machine — converges. SATURATED's residual (one decrease to one below the limit, repaired at `T0`) is now stated (D5, R1, case 22b).
- **`Ns` estimator's hold against `N`.** The hold is on new setups only, bounded by the recorded setups' clocks; the `N` machine's confirmation and the `Ns` hold can coexist (different signal classes) and neither waits on the other. Clockless setups are exempted from "quiet" (§4.5 step 2) but not from the `Ns` window's resolution → P3-8.
- **Test-pending and the confirmation after the carrier change.** The confirmation never closes for want of a carrier and its hold narrows to new setups while there is none; this cannot stick: a member that needs a new connection is by definition a carrier, and one that can lease does so. The final-attempt carrier exception (§4.5 rule 3, §4.7) is not reflected in the test-pending preconditions (§4.5 line 218) → P3-10.
- **Down ("Park, give up after 2") as a machine.** States: Down(failed = 0 | 1 | ≥ 2), with `retest_at`. Inputs: arrival before/at `retest_at`; retest success / retriable failure / Permanent failure; carrier cancelled. Every pair is defined: parked members self-carry at `retest_at` ("the first member waiting or selecting"), so a cancelled carrier does not strand them; success resets both counters and triggers the restore; two failures switch arrivals to fail-fast while a retest still runs every 30 s; Permanent → Closed. Bounded per member (≤ 30 s + one retest). No stuck state. Interaction with the limit machine: a Down key has no Connected (its exhaustion went through `hi = 0`/`k = 1`), so no test is due and no confirmation is open while Down.
- **Pool additions against C1/C2/C6/C8.** Create-only flag: loop 1 skip, per request. Evictor-bound hold: a hold record `{key, username, evictor: Option<RequestId>, until}` counted in `counts_for_host`/`counts_for_user_host`, consulted by the loop-3 guard and by loop 2's ordering; `next_deadline()` includes `until`; `can_install_capacity` ignores holds. Per-(scheme, host, port) count: F16 records that `counts_for_host` ignores the port and leaves the predicate to the plan — acceptable as a stated fact. Nothing in these contradicts the pool's existing invariants (`closed()` precondition, `Closing` in totals, reuse before creation).
- **Inconclusive → wait for the window's settlers (§4.4).** Bounded by `Ts`; under continuous `Discarded`/cross-identity churn at the ceiling a mid-command limit can stay inconclusive for as long as the churn lasts. The first wave's Overload is unaffected (no churn yet). Unchanged from my round-2 risk; the design now states it (D5, R1, case 50). Risk, not a finding.

## 1. Findings

### [P3-7] The `Ns` test is starved whenever an `N` probe is "due" but its base is unmet

- **Location:** §4.6 line 277 ("the `Ns` test runs only when no `N` test is due"); §4.10 line 351 ("runs only when no `N` test is due"); §4.5 step 3 line 222 ("if not … nothing is tested, admission resumes and **the test stays due**").
- **Root cause:** "due" and "startable" are conflated: a probe stays due while `Connected < N` (demand below `N`), and the `Ns` precedence rule keys on "due".
- **Violated invariant:** §4.7 "A command never goes longer between tests while a member is queued" as applied to `Ns`.
- **Sequence:** STABLE `N = 20`, `Connected = 5`, 15 setups wanted, `Ns = 4` after a `MaxStartups` blip that has cleared. `T` expires → probe due → base `Connected = 20` not met → stays due. The `Ns` test wants 5 in flight (wanted, within `Possible < N`) but "runs only when no `N` test is due" → never. Setups run 4 at a time for the rest of the command although the server would take 32. Bounded (throughput only; `Ns` under-admits, which is safe).
- **Required correction:** "runs only when no `N` test is **startable** (its base holds and the key can be made quiet)"; equivalently, a due probe whose base is unmet yields the slot to a due `Ns` test.
- **Closure test:** L1: `N = 20`, demand 15 setups, `Ns = 4` lifting: the `Ns` test runs within one `Ns` timer gap; the spy shows the probe still due and never started.

### [P3-8] The `Ns` window's resolution has no clockless-setup exemption: one hung `--ssh-timeout 0` setup holds every new setup on the key indefinitely

- **Location:** §4.10 line 350 ("hold new setups on the key … when every setup in `S_lo_s(a)` has a result, `Ns := …`"); §4.5 step 2 line 221 (the exemption, for "quiet" only).
- **Root cause:** the resolution predicate waits for a result from every recorded setup; a setup with no clock may never return one.
- **Violated invariant:** every wait bounded (§5.2); under `--ssh-timeout 0` the design's own position is that *that* setup may hang, not that the key's other members may.
- **Sequence:** `--ssh-timeout 0`, wave of 8, one setup H hangs after TCP accept (no banner), a drop on another setup is conclusive (`hi_s = 7 < 32`): `S_lo_s` includes H; the hold on new setups begins; 6 resolve, H never does; `Ns` is never assigned and the hold never lifts; every later SSH member on the key waits forever, where today only H's member would. Case 47 covers the `N` confirmation, not the `Ns` window.
- **Required correction:** add to §4.10 the sentence §4.5 step 2 already has: a clockless setup in `S_lo_s(a)` is not waited for; it counts as not succeeded, and the window resolves when every clocked setup in it has a result.
- **Closure test:** case 47 extended with a drop on another setup: `Ns` is assigned from the clocked setups within their clocks, the hold lifts, and the other members proceed while H hangs.

### [P3-9] The §4.6 diagram's Overload edges still carry `N := max(1, Connected)`, contradicting §4.2 and §4.5 rule 4

- **Location:** §4.6 lines 260 and 266 (`STABLE -> STABLE` and `SATURATED -> STABLE` labels); §4.2 line 151 and §4.5 rule 4 line 237 (`N := max(1, min(Connected, hi(a)))`).
- **Root cause:** the revision-4 patch changed the prose and not the normative diagram.
- **Violated invariant:** one definition per action (the design's stated aim for §4.6: "with every action stated").
- **Sequence:** an implementer builds the machine from the diagram (the artefact L1's tests are "in the style of" `machine_tests.rs`), applies `max(1, Connected)` on Overload, and P2-6's loop at `L + 1` returns for the reused-connection case (`Connected = 9`, `hi = 8`); case 43 would catch it only if it is run against that build.
- **Required correction:** relabel both edges `N := max(1, min(Connected, hi(a)))`, and the Appendix A mapping sentence likewise if it quotes the formula.
- **Closure test:** textual: no occurrence of `max(1, Connected)` without `min(…, hi(a))` in §4.6 or Appendix A.

### [P3-10] Test-pending's precondition excludes the final-attempt confirming carrier that rule 3 and §4.7 allow

- **Location:** §4.5 line 218 ("While a test is due and a member is queued **that is not on its final attempt** and needs a new connection: … none for a confirmation"); §4.5 rule 3 line 236 and §4.7 line 304 (the exception: a final-attempt member carries the confirming test when no other can).
- **Root cause:** the carrier exception was added to rule 3 and §4.7 and not to the numbered precondition that governs the hold and the quiet wait.
- **Violated invariant:** determinism of the sub-state's entry: two sections give two preconditions for the same hold.
- **Sequence:** `--max-retries 1`, reset limit 8, wave of 32 (case 45): after the wave every refused member is on its final attempt. By rule 3 the confirmation is open and will be carried by a final-attempt member; by the numbered list no member satisfies the precondition, so steps 1–3 (hold, quiet, start) never run, and the confirmation's "holds every new start" has no mechanism. An implementer following the list never starts the test; one following rule 3 does. Case 45 would detect the first reading.
- **Required correction:** in line 218, "that is not on its final attempt (for a probe test; for a confirming test, any member, §4.7's exception)".
- **Closure test:** case 45 as written, with the L1 spy asserting the test-pending sub-state was entered.

### [P3-11] The limit machine's state during a restore is unnamed, so a probe timer expiring mid-step has no defined effect

- **Location:** §4.6 line 276 ("from any state, the restore runs … DISCOVERING's one-per-test climb does not apply while a restore runs"); §5.5 line 424 (the step rules); §4.5 line 218 (test due "when the probe timer has expired (STABLE)").
- **Root cause:** the restore is specified as a procedure over the machine rather than as a state, so STABLE's timer, which may have been running when the retest succeeded, is neither suspended nor consulted.
- **Violated invariant:** every state × input pair defined.
- **Sequence:** STABLE `N = 4`, `T` running; the retest succeeds → restore step `S = 8`, four starts admitted in parallel; `T` expires mid-step → a probe is due → test-pending step 1 caps ordinary starts at `Possible < N = 4` (already exceeded by the step) and step 2 forbids new starts until quiet; the step's remaining admissions, if any, and the probe's base (`Connected = 4`, quiet) contend. Whichever wins, the outcome is bounded: either the step completes (its exits set `T := T0`, cancelling the stale expiry) or a single probe runs first and the step resumes. Throughput only, but two implementations diverge.
- **Required correction:** name RESTORING as a sub-state of the machine during which the probe timer is suspended and test-pending is not entered (the exits already set `T := T0`); state that a confirmation opened by a step is the only test that runs during a restore.
- **Closure test:** L1: a restore entered with `T` 100 ms from expiry: no probe starts during the step; the step's exit sets `T := T0`; the spy shows the sub-state.

## 2. Invariant analysis

- **Fail-closed direction, all five P3s.** P3-7 and P3-8 lose throughput (under-admission of setups; a key-wide wait in a mode the user chose for unbounded waits); P3-9 is a transcription error that would reintroduce a known loop if the diagram alone were implemented; P3-10 and P3-11 are determinism gaps whose every resolution is bounded. None invents capacity; none permanently caps a key on a transient cause except P3-7's `Ns`, which the fix addresses and which under-admits safely until then.
- **Window inferences and judgement (§4.3, §4.4).** Four attempt kinds now cover every start the design can make: ordinary (`Possible < N`), probe (quiet, `Connected = N`), confirming (quiet, `k = Connected + 1`), restore step (`S`). Their start conditions are disjoint except restore-vs-ordinary (a restore step's starts are above `N` and the row says they are not tests), and every refusal of each kind has a named outcome. With `min(Connected, hi(a))` the believed limit is monotone-decreasing per Overload and rises only by observed Connected.
- **Closed grammar.** Test-pending, the confirmation, the restore, Down/parking and the retry machine's Waiting/Degraded interlock by the `Connected = 0` separation (the retry machine counts only `hi = 0`/`k = 1` failures; the limit machine tests only with `Connected ≥ 1`). I found no reachable configuration in which two holds wait on each other: the confirmation's hold is on new setups and its own test is the start it waits for; the `Ns` hold waits on recorded setups' clocks; test-pending waits on in-flight clocks and `Ts`; parking waits on `retest_at`. The one unbounded wait is P3-8's clockless case.
- **Pool consistency (§4.9 vs C1/C2/C6/C8).** The three pool additions (create-only, evictor-bound hold, port-aware count) are each a local change to one loop or one predicate of `schedule()`/`count_where`; none alters `closed()`'s precondition, lease liveness or `install_capacity`'s idle requirement. The two lock domains (F10) remain the plan's to order; the design now says so and names what crosses.
- **Determinism and testability.** L1 can express every rule once P3-10 and P3-11 are stated as sub-states; L2 over the real `PoolMachine` covers P3-4/P3-5's closures (cases 41, 42b, 48). The spy assertions in cases 43, 45, 47–50 are the right shape.
