## 1. Findings

### [P2-1] A repository's or workspace's `gwz.transport` value refuses gwz-py network operations under an `error` warnings filter

- **Root cause.** §3's ignored-value notes are carried in gwz-py as `warnings` warnings "of the same kind" as the switch-on notice (§4), issued at the native entry before the operation, and §4 states that a filter which turns the warning into an error "makes that `call` or `submit` raise it, before any effect". No carve-out exists for §3's notes.
- **Location.** §3 "The note" and "A file the scan cannot read gets no note. The scan never fails a request."; §4 "§3's notes are warnings of the same kind." and "A filter that turns it into an error makes that `call` or `submit` raise it, before any effect."; §10 the gwz-py form of "An ignored value".
- **Violated invariant.** §3's own "The scan never fails a request", and the design's premise that a workspace or repository value is "Ignored, by construction" and that which path runs — and so whether a request runs — "is the user's choice alone".
- **Interleaving.** (1) The workspace root's `.git/config` holds `[gwz] transport = off`, which is exactly "what `git config` writes without `--global`" (§1), on a workspace others write and share (§3's threat model), or the user's own. (2) The Python process runs under `python -W error`, `warnings.simplefilter("error")`, or pytest's common `filterwarnings = error`. (3) `client.fetch(...)` reaches the native entry; the switch resolves off; the §3 scan finds the key and issues the ignored-value `UserWarning`; the filter raises it. (4) `call` raises `UserWarning`, not a `GwzError`, and the fetch never runs. Whether the second operation proceeds depends on whether the per-`Client` record was kept before the raise, which the text does not say.
- **Impact.** A file the design promises cannot affect the switch fails network operations outright for a class of callers; in CI it is a red build caused by a repository file the caller may not own, with the exception type hiding it as a warnings-policy matter.
- **Required correction.** §3's notes in gwz-py take a carrier that cannot refuse an operation: a `logging` record on logger `gwz` at `WARNING`, or a field on the operation's result (the CLI already has `meta.transport_off_switch.ignored` for exactly this). Only the switch-on notice stays a `warnings` warning, and §4 says so explicitly, keeping "before any effect" for that one alone. If the design keeps a warning for the notes, it must state that the `error` filter turns a repository file into a refusal, which contradicts §3 and is not acceptable on this axis.
- **Closure test.** §9's gwz-py rows gain: under `warnings.simplefilter("error")` with a repository value present and the switch off, `call` and `submit` complete on the transport, the fixture records the connection, and the note is observable through its carrier; the existing "under `error`, `call` and `submit` raise it before any effect" row is restated as applying to the switch-on notice only.

### [P2-2] An unreadable user configuration file refuses every network command, where git, libgit2 and 1.0.17 ignore it

- **Root cause.** §2 chooses "An unreadable or unparsable one is refused", treating two cases alike that libgit2 and git treat differently.
- **Location.** §2 "A missing file carries no value. An unreadable or unparsable one is refused."; §9 gwz-core unit row "an unreadable or unparsable file refused, naming it"; §10 "`could not read gwz.transport from <file>: <cause>`".
- **Violated invariant.** 1.0.17 parity, the release's rule, and the draft's own claim that these are "the files `git config --global` reads", since git ignores an unreadable configuration file. libgit2 `config_file.c:114-124` maps a file that exists but fails `access(R_OK)` to `GIT_ENOTFOUND`, with the comment that it emulates git for sandboxed macOS applications; `repository.c:1317-1319` tolerates it, so 1.0.17 runs every operation under such a file.
- **Reproduction.** `chmod 000 ~/.gitconfig; gwz fetch`: the candidate exits 2 before any request; 1.0.17 fetches. Real-world forms: `sudo -u svc env HOME=/home/alice gwz fetch` where alice's `.gitconfig` is mode 0600; gwz-py embedded in a sandboxed macOS application whose git configuration is unreadable, libgit2's own motivating case. In gwz-py every network operation raises `invalid_request` until the process sets `GWZ_TRANSPORT`, the only other form it has.
- **Impact.** A setup that works on 1.0.17 loses every network operation on upgrade, with recovery only by passing the flag or variable on every invocation. The escape hatch's own resolution becomes a new lock-out.
- **Required correction.** §2: an unreadable file carries no value, as libgit2 treats the file itself (`config_file.c:114-124`) and git does; an unparsable file stays refused (parity holds there: libgit2 refuses to open any repository under it, so 1.1.0 refusing only network requests, before any effect, is not worse). For diagnosability, `--verbose` names the skipped file and `meta.transport_off_switch` carries it (for example a `skipped` list beside `ignored`), so the silence is visible. §9's row becomes "an unreadable file carries no value and is reported; an unparsable one is refused, naming it". §10 drops the unreadable case from the refusal text or keeps the text for parse failures only.
- **Closure test.** The unit row above; a gwz-cli row with `~/.gitconfig` mode 000 and the switch otherwise unset: the fetch takes the transport, exit 0, `--verbose` shows `transport off switch: off (default)` and the skipped file.

### [P2-3] With the switch on, the native path runs under defaults 1.0.17 never had, and the draft says "as in 1.0.17"

- **Root cause.** The retry plan's Phases 1 and 2 raised the operation-level defaults (`--jobs` 50 → 100, `--max-per-host` 8 → 32, `--ssh-timeout` 3 s → 9 s) for the transport's pool and clocks; `par_map_per_host` and `set_server_timeout_ms` apply the resolved values to every operation, so the native path inherits them, and the draft asserts parity without deciding the question.
- **Location.** §6 "`--jobs` and `--max-per-host` still bound member operations, each on a connection of its own, as in 1.0.17."; §6 "9 seconds by default"; §5 "What it keeps is 1.0.17's behaviour"; §10's `--transport` long help ("as gwz 1.0 did"); §9's `--ssh-timeout 2` row; TR8.4's native-route row "at the default settings".
- **Evidence.** gwz-core `v1.0.17` `resolve_jobs.rs:2` (50) and `resolve_per_host.rs:2` (8) against `9d4dd92f` (100, 32); gwz-cli `v1.0.17` `lib.rs:177` `unwrap_or(3)` against `0218cc72` `unwrap_or(9)`; retry plan §6 "The operation already resolves those into `par_map_per_host`" and "The logical limits stay"; amendment 2 §3.20's MaxStartups record, whose answer on the transport is retry, which §6 of the draft says the native path lacks.
- **Interleaving.** Switch on; `gwz fetch` over 32 members on one self-hosted stock OpenSSH host (`MaxStartups 10:30:100`). The native path starts 32 libssh2 handshakes at once (OD18 records that 1.0.17 "opens its connections at once", bounded by its per-host limit). Beyond the tenth unauthenticated connection sshd drops each new one with probability rising from 30%; each drop is a setup failure with no retry, so that member fails. On 1.0.17 the per-host limit of 8 never reaches the drop regime, and every member succeeds. Separately, a dead host is reported after 9 s per step rather than 3 s, and `--ssh-timeout`'s own long help ("stalled setup is retried", "the same 30 second setup budget", "Retries are controlled by --max-retries") describes clocks the native path does not have; the draft amends only `--verbose`'s help.
- **Impact.** Members fail with the switch on that succeed on 1.0.17, which inverts the switch's purpose as the way back to 1.0.17's behaviour; TR8.4's native-route row compares 1.0.17 at 8 per host with the switch at 32 and attributes the difference to the route; the ledger row's parity statement is false.
- **Required correction.** §6 states the defaults the native path runs under with the switch on. Recommended under the release's parity rule: when the flag is omitted and the switch is on, 1.0.17's values (jobs 50, per-host 8, timeout 3 s), with explicit flags still honoured. If the operator keeps the retry plan's values instead, then §6, the ledger row (§5), the migration notes and `--transport`'s long help name all three differences and the MaxStartups consequence, and `--ssh-timeout`'s long help gains one sentence for the switch. Either way §5's "What it keeps is 1.0.17's behaviour" is qualified accordingly.
- **Closure test.** gwz-cli row: 32 members against a fixture sshd configured `MaxStartups 10:30:100`, switch on, no flags: every member succeeds (recommended option), or the ledger records the drop count beside 1.0.17's on the same fixture (alternative). The rendered `--ssh-timeout` and `--transport` help equal the revised §10.

### [P2-4] The workspace note scan can block a request indefinitely, in gwz-py with the GIL held, from a file the request does not use

- **Root cause.** §3 opens, for every network request, the root's and every present member's `<common dir>/config` and `config.worktree` through libgit2's reader, which follows `include.path` and guards only against directories, and §3 guarantees only that the scan "never fails a request" — a hang is not a failure.
- **Location.** §3 "The note" (the file set) and "A file the scan cannot read gets no note. The scan never fails a request."; §2's gwz-py timing, "at each network operation's native entry ... while the caller holds the GIL", which the scan shares ("When a driver resolves the switch for a network request, it also looks for the key").
- **Violated invariant.** "The scan never fails a request", read as the design intends it: the note is a diagnostic that must cost a request nothing. Also §3's own scope argument: the scan widens the files a request touches to repositories outside its targets.
- **Evidence.** The model code `config_scan.rs:47-58` checks `symlink_metadata` for existence only, then `git2::Config::open`; libgit2 `config_file_read` → `git_futils_readbuffer_updated` (`futils.c:242-253`) rejects directories only, then `open(2)`, which blocks on a FIFO with no writer; `parse_include` (`config_file.c:564-595`) follows `include.path` to any path, so the file set is not bounded to the repository; a large regular file is read whole (`st_size` allocation).
- **Interleaving.** A member the request does not target (`gwz push --target @root`) has `.git/config` replaced by a FIFO, or holds `[include] path = /dev/stdin` or a path to a FIFO. The scan blocks before the request runs, with no timeout and nothing printed. In gwz-py the block occurs at the native entry with the GIL held, so every Python thread stops. Who: anyone who writes the shared workspace, §3's own threat model. The same member blocks any command that opens it, but 1.0.17's `push --target @root` does not open it.
- **Impact.** A stuck command, or a stuck interpreter, caused by a diagnostic; recovery is killing the process.
- **Required correction.** §3 bounds the scan: each file is opened only if `symlink_metadata` reports a regular file under a stated size (for example 1 MiB), the scan covers the request's repositories (its targets, as the operation resolves them) rather than every member present, and in gwz-py it runs after `py.detach`, never with the GIL held. "Never fails a request" becomes "never refuses or blocks a request; a file that is not a regular file under the bound is skipped without a note". An `include.path` inside a scanned file remains the repository's own hazard, as for any command that opens it, and §3 says so.
- **Closure test.** A FIFO at a non-target member's `.git/config`, and a 2 GiB regular `config` at another: `gwz push --target @root` completes with no note for either; a gwz-py `call` under the same workspace completes and a second Python thread makes progress during the scan.

### [P3-1] §2's "never the process's" and "libgit2's order" claims do not hold for `~/` includes or for libgit2's sandbox and setuid branches

- **Root cause.** The resolver chooses the files from the snapshot and then parses them with libgit2, which resolves part of the path set from process-global state fixed at its initialisation.
- **Location.** §2 "found from the snapshot's variables, never the process's"; "`include.path` is followed, as git and libgit2 follow it"; "These are the files `git config --global` reads and writes, in libgit2's order (`sysdir.c:324-420`)"; §9 "a snapshot whose `HOME` differs from the process's reads the snapshot's"; §5/§10 `file`, which names the deciding file.
- **Evidence.** `config_file.c:523-528`: an `include.path` beginning `~/` goes through `git_sysdir_expand_homedir_file`, whose directory is set once at `git_sysdir_global_init` (`sysdir.c:453-465`) from the process's `HOME`, or from the passwd entry under `APP_SANDBOX_CONTAINER_ID` or uid ≠ euid (`sysdir.c:324-363`); gwz sets no search path. The server design's every-session row records the same fact for 1.2.0. git's `--global` lookup uses `$HOME` and `$XDG_CONFIG_HOME`, never the passwd entry, so the draft's list is git's, not libgit2's, in those two cases.
- **Interleaving.** gwz-py: the process starts with `HOME=/home/a` and libgit2 initialises at import; the script sets `os.environ["HOME"] = "/home/b"`; `/home/b/.gitconfig` holds `[include] path = ~/.gitconfig.d/gwz`; the include resolves to `/home/a/.gitconfig.d/gwz`, a file §2 says is never read, and its `gwz.transport = off` turns the switch on. The §9 test row cannot pass as written when the file has such an include. In a sandboxed macOS process, the switch is read under `$HOME` while the native path's own credential-helper and `known_hosts` reads use the passwd home.
- **Impact.** Narrow: a value from outside the stated file set; a test row that cannot pass in one form; `file` possibly naming the including file rather than the one that held the value.
- **Required correction.** §2 states the two exceptions: `~/` in `include.path` resolves against libgit2's process-wide home, fixed at its initialisation (in gwz-py, at import), not the snapshot; and the list is git's `--global` file set, which differs from libgit2's own global lookup under `APP_SANDBOX_CONTAINER_ID` or uid ≠ euid, where the native path's own reads use the passwd home. §9's row reads "with no `~/` include". §10 says whether `file` is the top-level file or the included file that held the value.
- **Closure test.** The amended unit row, plus one with a `~/` include asserting the documented resolution.

### [P3-2] gwz-py's resolution point moves from per operation (1.1.0) to per `Client` at `open` (1.2.0) with no statement of the visible change

- **Root cause.** §2 pins, and §9 tests, that "a change to `os.environ` or to the file takes effect at the next operation", while §8 resolves the switch "when its `Client` opens", and no sentence names the reversal as a documented behaviour change.
- **Location.** §2 "A change to `os.environ` or to the file takes effect at the next operation."; §9 "a change to `os.environ` between two operations changes the second's route"; §8 "gwz-py does so when its `Client` opens ... replacing 1.1.0's per-operation resolution".
- **Consequence.** A 1.1.0 script that toggles `GWZ_TRANSPORT` between operations on one `Client` silently keeps the route it opened with on 1.2.0. The Python design's §2.8 records the 1.1.0 capture point as a documented change and §4 records that the session host replaces it, so the program expects the move; the off-switch text should say its per-operation semantics are 1.1.0's and that 1.2.0's notes (S7.5 (1.2.0) Surface) state the move.
- **Required correction.** One sentence in §2 or §8: the per-operation resolution is 1.1.0's; in 1.2.0 a `Client` resolves the switch once at open, and a change takes effect in a new `Client`, which the 1.2.0 migration notes state.
- **Closure test.** The 1.2.0 gwz-py row: a change to `os.environ["GWZ_TRANSPORT"]` between two operations on one `Client` does not change the second's route; a new `Client` takes the new value.

## 2. Invariant analysis

- **Who can flip it.** The resolver reads the flag, the variable, and the user's global files; the files are chosen from the snapshot, relative `HOME`/`XDG_CONFIG_HOME` names no file, `includeIf` is skipped (`config_file.c:727`, confirmed), `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_COUNT` and the system file are not read. Every divergence from libgit2's own lookup I found (relative `HOME`, empty `XDG_CONFIG_HOME`, which libgit2 reads as the relative path `git`) is in the safe direction: the switch reads nothing where libgit2 would read a workspace-relative file. A workspace, member, `gwz.conf/` or `.gwz/` value cannot set it; the one workspace-persisted global setting is `--url-scheme`'s and the draft keeps the switch out of it. In gwz-py the inherited process environment can set it, as for `GWZ_URL_SCHEME`; that is the user's environment by the program's existing rule. In 1.2.0 the host never derives it (`context.rs:223-227` and its test), and the server's `GWZ_TRANSPORT` is inert; `HOME` and `XDG_CONFIG_HOME` are every-session must-match rows, so a server's native path reads the client's home. What a repository value can still do is P2-1 (refuse, in gwz-py) and P2-4 (block); neither flips the route. The `~/`-include exception is P3-1.
- **Never a fallback.** The route is chosen at `capture` (gwz-py) or at dispatch (gwz-cli) before any connection, from a value gwz never sets; the retry machine retries setups on the transport only; a transport failure returns as that failure and no code path re-dispatches. In 1.2.0 the value is fixed at open. §6's claim survives every interleaving I constructed. The hint (§10) names the switch only in TR1.8's refusals for setups 1.0.17 serves and the transport does not, which amendment 2 §3.5 authorises; the native path's host-key check is libgit2's `known_hosts` with no callback (`ssh_libssh2.c:758-766`), so the hint is not a host-key downgrade. The machine-proxy 407 case carries the OD16-class auto-logon hazard; that belongs to TR1.8's Safety list and the draft does not weaken it.
- **Resolution failures and stuck states.** A malformed variable or file refuses before any effect with a message naming the form and the override, so the user can always see why and get out through the form above; an unparsable file is at parity, since libgit2 refuses to open any repository under it (`repository.c:1317-1319`). The unreadable case is a regression (P2-2). The scan can block (P2-4). A gwz-py `Client` with eight running native operations is wedged until they end, as §6 documents; that is the native path's uncancellability, 1.0.17's property, and `close()` returns within the bound.
- **Disclosure.** `file`, `ignored[].file` and the notes print configuration-file paths. gwz-cli's machine output already carries absolute workspace paths (`abspath`), and `--verbose` rows carry remote URLs, so a home-directory path is not a new class of disclosure; libgit2's parse errors in `<cause>` are fixed strings with file, line and column, except "invalid escape at <rest of value>", which could echo part of a value and is worth a redaction note when TR2.5 writes the refusal, but is not a finding on the text.
- **gwz-py.** The switch-on `UserWarning` is issued with the GIL at the native entry, once per process by text under the default filter, raised under `error` before any effect: a documented choice the caller controls with both knobs. P2-1 is the case where a file the caller does not control reaches the same path. Threads and two `Client`s share Python's registry correctly. Cancellation of a running native operation is `unsupported_operation`, `close()` and exit wait up to `CLEANUP_BOUND` and report unconfirmed, and a native thread outliving exit records without attaching to the interpreter (Python design §2.6; decision 14's limitation is recorded). Killing a libgit2 fetch mid-transfer leaves a temporary pack and no corrupt refs, as on 1.0.17.
- **Mixed versions and degraded paths.** `GWZ_TRANSPORT=off` against 1.0.17 is inert and the route is native anyway; `--transport` against 1.0.17 is a clap usage error, as any new flag is. Before S7.1 the ordinary build does not read the variable and is native. A 1.2.0 server started with `GWZ_TRANSPORT=off` serves switch-off sessions on the transport. The SSH remote form uses the client's value. OD16: §6 names `transport_support.rs:272-274` correctly and nothing in the draft claims the switch lessens the hazard.
- **"Never worse than the status quo."** Holds for the route, the credential callback, host keys, the helper policy and cancellation. Fails in two places: an unreadable global file (P2-2) and the native path's defaults (P2-3).

## 3. Risks and next action
