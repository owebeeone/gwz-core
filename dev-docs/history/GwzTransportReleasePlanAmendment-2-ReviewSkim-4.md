**P2-1** · amendment §3.19, "OD10 reversed" (lines 455–460) · TR1.6 is told to design a git2-style helper runner ("how each helper form starts, as git2 starts it: a bare name as `git credential-<name>`, an absolute path, and a `!` shell command"), while the accepted session plan already designs the transport's helper mechanism differently: CS3.4 (line 411) "Implements §5.8's credential-helper rule and §5.7's `Cred::credential_helper` row" as one `git credential fill` spawn with `env_clear()` plus the snapshot, `GIT_TERMINAL_PROMPT=0`, `-c credential.interactive=false`, time-bounded and killed on drop, with its addendum (C10: explicit working directory, no repository-local configuration) and working rule (C11: `GIT_DIR`, `GIT_COMMON_DIR`, `GIT_WORK_TREE` dropped), and "a new `Cred::credential_helper` call fails gwz-core's check". §3.19 cites neither, and its "(the server design's item C10)" dangles: no C10 exists in the server design; the C10 is CS3.4's addendum. Two designs for one mechanism, and a 1.1.0 TR1.6 that mirrors git2's parser would be replaced by CS3.4 in 1.2.0 with a behaviour change (git's own helper matching differs from git2's). *Fix:* TR1.6's bullets read: "the mechanism is CS3.4's `git credential fill` spawn with the snapshot's environment less `GIT_ASKPASS`, `SSH_ASKPASS`, `GIT_DIR`, `GIT_COMMON_DIR` and `GIT_WORK_TREE`, an explicit working directory, bounded and killed on drop (session plan CS3.4, its addendum C10 and working rule C11), brought into 1.1.0 as TR3.4 brought S6.2's pins; 1.0.17's `Cred::credential_helper` semantics are the parity reference, and TR1.6 records each difference"; drop the git2-form bullet; name CS3.4 in §1's session-plan entry if its text changes.

**P2-2** · amendment §3.19 TR1.6, TR1.8 "Precedence of the credential helpers" (line 163) and OD16's precedence bullet (line 364) · Which URL a helper is asked for after the transport's one validated discovery redirect is not stated, and "as 1.0.17's credential callback does" is platform-dependent: libgit2's http.c passes the redirected `server->url` (`http.c:157-158`, after `git_net_url_apply_redirect` at :252), while WinHTTP passes the configured `t->owner->url` (`winhttp.c:1243-1246`). A helper keyed by host could answer for the configured host and have its credential sent to the redirect target — the shape of skim-2's P2-4, which revision 4 fixed for SSPI but not for helpers. *Fix:* TR1.6 states "a helper is asked for the URL the credential will be sent to, after the transport's one validated discovery redirect; a redirect after the challenge ends the operation with no credential sent", with a redirect fixture row; TR1.8's precedence bullet and OD16's cite it.

**P2-3** · amendment TR1.8 "Precedence of the credential helpers" (line 163) and OD16 (line 364) · "the helper's credential is used, and no SSPI exchange starts" has no mechanism for a helper credential against a challenge that offers only `Negotiate`, `NTLM` or `Digest`. 1.0.17 on Windows applies a helper's user/pass to those schemes (`apply_userpass_credentials`, `winhttp.c:139-151`; `parse_unauthorized_response` admits all four, `:618-640`; the callback hands a userpass to an NTLM challenge since NTLM sets `USERPASS_PLAINTEXT`, `:618-622`). TR1.6 designs helpers and gh as Basic. A Windows user whose helper holds a domain password for an NTLM/Negotiate-only IIS or TFS server works on 1.0.17 and has no defined behaviour on 1.1.0, and it is not a listed parity exception. (On macOS and Linux 1.0.17 has neither NTLM nor Negotiate: libgit2-sys defines no `GIT_NTLM`/`GIT_GSSAPI`, so `auth_ntlm.h:16-34` and `auth_negotiate.h:15-25` make both `git_http_auth_dummy`.) *Fix:* TR1.8 states that on Windows a helper credential answers a `Negotiate` or `NTLM` challenge through SSPI with an explicit identity (`SEC_WINNT_AUTH_IDENTITY_W`), and whether `Digest` is served or listed as an exception; the `Negotiate` fixture gains an NTLM-only row with a helper credential; S7.2's notes record it.

**P2-4** · amendment §3.19 TR2.8, "The list" and "Tests" (lines 471–478) · The `ssh-rsa` rule "only where libssh2 uses it: for a server that offers no SHA-2 RSA algorithm" and its test "never against one that does" do not match libssh2 1.11.1: (a) with no `server-sig-algs` received, libssh2 does no upgrade and signs `ssh-rsa` whatever the server supports (`userauth.c:1380-1383`); (b) with `server-sig-algs` present, it intersects it with "rsa-sha2-512,rsa-sha2-256,ssh-rsa" (`openssl.c:5213-5218`, `LIBSSH2_RSA_SHA1` is 1 on OpenSSL and WinCNG) in that preference, so `ssh-rsa` only when the server lists it and no `rsa-sha2-*`, and an empty intersection fails with "No signing signature matched" (`:1503-1506`), no SHA-1 fallback; (c) when the agent returns a signature of another method than the one requested, the first attempt fails with `LIBSSH2_ERROR_ALGO_UNSUPPORTED` and libssh2 retries with the key's default `ssh-rsa` (`agent.c:560-563`; `userauth.c:1754-1763`), even against a server that advertised SHA-2. As written, the rule's test would assert the opposite of (a), and (c) is uncovered. *Fix:* the bullet reads: "`ssh-rsa` (SHA-1) exactly where libssh2 uses it: when the server sent no `server-sig-algs`; when `server-sig-algs` lists `ssh-rsa` and no `rsa-sha2-*`; and, once per key, when the agent answers a `rsa-sha2-*` request with an `ssh-rsa` signature. When `server-sig-algs` lists none of the three, the key fails as libssh2's does." Tests: one row per case, and `rsa-sha2-*` whenever `server-sig-algs` lists it. TR2.8's Safety review names the SHA-1 cases and that an attacker cannot strip `server-sig-algs` (it travels after the key exchange).
