## 1. Findings

### [P3-5] The automount walk's probe is a following, automounting lookup, so the probe itself can perform the contact the walk exists to prevent

**Location.** Object §3.4, "Automounts and network file systems" (line 134): "the client walks an absolute path from `/` and checks each prefix's file-system type with `statfs` … before looking up the next component."

**Violated invariant.** The bullet's own rule: no lookup below an automounter's mount before the refusal; and the addresses bullet's "before any file-system, pipe or network call takes the address."

**Mechanism.** `statfs(2)` resolves its path with a following lookup, and on Linux with an automounting one: `fs/statfs.c`'s `user_statfs` resolves with `LOOKUP_FOLLOW | LOOKUP_AUTOMOUNT`, and there is no `lstatfs`. Two consequences. (a) A symbolic-link component is followed by the probe: `statfs("/tmp/x")` where `/tmp/x -> /net/10.9.9.9/y` looks up `/net/10.9.9.9` and triggers the mount before the walk ever probes `/net`. On Linux, `fs.protected_symlinks` (default on most distributions) blocks a link planted by another user in a sticky world-writable directory, so this needs macOS, a link in a directory the attacker can write, or the user's own link. (b) An autofs direct map (`/-` entries) places the trigger at the path itself, and a probe of that prefix mounts it; the host contacted is the administrator's, not the attacker's, so the effect is a mount and a possible hang rather than a disclosure.

**State sequence.** macOS with the default `/net -hosts` map. Another local user creates `/private/tmp/gwz-501 -> /net/10.9.9.9/x` while the victim's `TMPDIR` is unset (the `/tmp/gwz-<uid>/` fallback), or the victim's own `GWZ_SERVER` names a path through a link. The victim runs `gwz status --server auto`. The walk probes `/`, `/private`, `/private/tmp`, then `statfs("/private/tmp/gwz-501")`, which follows the link, looks up `/net/10.9.9.9` and makes automountd contact 10.9.9.9; the command blocks for the mount timeouts. The listener check's "no symlink" rule would refuse afterwards, but the contact has happened.

**Impact.** The narrowed remainder of P3-1's consequence: a network contact from a path string and a stuck command, with no credential leaving (uid, gid and hostname in AUTH_UNIX). Bounded by the preconditions above.

**Required correction.** The probe is a non-following, non-automounting lookup, and a symbolic-link component is not followed by the probe: the client reads its target and walks that target from `/` under the same rule, with a bounded link depth. On Linux, `statx` with `AT_SYMLINK_NOFOLLOW | AT_NO_AUTOMOUNT`, refusing a component that carries `STATX_ATTR_AUTOMOUNT`, and `fstatfs` on an `O_PATH | O_NOFOLLOW` descriptor for the file-system type; on macOS, `open` with `O_SYMLINK`/`O_NOFOLLOW` and `fstatfs` on the descriptor, with TR1.3 establishing how a direct-map trigger presents. Symbolic links must be walked, not refused, since `/var`, `/tmp` and `/etc` are links on macOS and `TMPDIR` lives under `/var/folders`.

**Closure test.** §3.6's refused-address rows gain: on macOS, an address whose component is a link under a local directory pointing under `/net`, refused with no lookup below `/net`; on Linux, an address under an autofs direct-map trigger, refused with the trigger left unmounted (the automount daemon's log records no mount request). Non-architectural; cleared to land without a further round.
