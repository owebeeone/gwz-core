## 1. Findings (new in revision 2)

### [P3-11] Every next step is "`git ls-remote` with this member's URL", and nothing on the surface says where that URL is — and before the member exists, under `--url-scheme https`, the manifest's URL is the wrong one

- **Location.** M2, M3, M4, M5, M9, M10: "run `git ls-remote` with this member's URL" (and variants); "Pages that change": Troubleshooting "gives the checks (`git ls-remote` with the member's URL, …)". Messages name no URL, by rule.
- **Violated expectation.** The one instruction every message relies on must be executable cold. No gwz command prints a member's URL (`gwz ls`: id and path). For a cloned member `git -C <path> remote get-url origin` answers; for one not yet cloned — the first-day `gwz clone` and `materialize --lock` cases, and clone.md's private-member retry — the only visible source is `gwz.conf/gwz.yml`, whose URLs are the manifest's form.
- **Scenario.** QuickStart's own recipe for a reader without SSH keys: `gwz clone --url-scheme https git@github.com:org/ws.git`. A private member fails with M2. The user opens the manifest, finds `git@github.com:org/private.git`, runs `git ls-remote git@github.com:org/private.git`, gets `Permission denied (publickey)`, stores no HTTPS credential, and gwz fails again with M2.
- **Impact.** The https-scheme user — the population the HTTPS transport most serves — is sent to the SSH URL by the only instruction available.
- **Required correction.** State where the URL is, in the Troubleshooting section and in one clause of the messages: "`git -C <member path> remote get-url origin` for a cloned member; for one not yet cloned, the manifest's URL in the form gwz uses — `https://…` when the workspace was cloned with `--url-scheme https` — which `gwz --verbose materialize --lock` prints as `manifest-url -> effective-url`."
- **Check.** Walk the `--url-scheme https` clone with a private member from the text alone and reach `git ls-remote https://github.com/org/private.git`.

### [P3-12] On clone and materialize, M3's outcome is swallowed by the private-member skip, so the user who could fix it never sees the instruction

- **Location.** "Member boundaries": "Clone treats every outcome whose code is `remote_rejected`, M2, M3, M7 and M9, as an access refusal …, so a `private: true` member is skipped quietly …, as 1.0.17 skips one with no credential." N14: "A failed `private: true` member is skipped on clone only when its code is `RemoteRejected`." clone.md: "Skipped clones produce no member progress, response row or transport diagnostic."
- **Violated expectation.** A quiet skip is right when the account has no access (M9) or no credential (M2 — the 1.0.17 parity case). A rejected credential (M3) is a fixable fault; M3 exists to say "renew it". Folding it into the skip hides the one message the user needs, and `--verbose` shows nothing either.
- **Scenario.** A `gh` user with an expired token runs `gwz clone` (or the `materialize --lock` retry) on a workspace with private members: the members are silently skipped; `gwz ls --unmaterialized` shows `private, skipped`; public members work. The user concludes they lack access and never runs `gh auth refresh`.
- **Impact.** A diagnosability regression specific to this design: 1.0.17's documented skip was "no credential"; revision 2 extends it to a rejected one.
- **Required correction.** Keep the quiet skip for M2, M7 and M9; for M3 either fail the member (a rejected credential is not an access refusal) or keep the skip and surface the reason: a transport diagnostic row under `--verbose`, and the reason class in the `ls` note (`private, skipped: credential rejected`). At minimum, N14 and clone.md must say a rejected credential is skipped too.
- **Check.** The expired-token clone walkthrough shows M3, or a note naming the rejected credential.

### [P3-13] M5 and M6 reuse `unsupported_operation`, which the catalog's own text says "now means exactly 'not built yet'"

- **Location.** Table rows M5 and M6: `unsupported_operation` / `UnsupportedOperation`. ErrorCatalog at `ab48966f` row 22: "v0 handler does not implement the requested option or target. | Use a supported v0 mode."; line 94: "`unsupported_operation` now means exactly \"not built yet\": …". "Pages that change" amends row 22 but not that sentence.
- **Violated expectation.** A script keyed on `UnsupportedOperation` as "this build lacks the feature; upgrade or use another mode" misreads a server-side challenge (M6) or gwz's own security refusal of a redirect (M5), whose recovery is "point the remote at the new URL".
- **Required correction.** Either carry M5 under `remote_rejected` (the server's redirect is what gwz declines to follow with a credential; its facts `helper, true, null` already separate it) and keep M6 under `unsupported_operation` with row 22 and the line-94 sentence amended to name the HTTPS scheme exception; or amend both texts for both messages. The check is textual.
- **Check.** The catalog contains no sentence stating `unsupported_operation` means exactly "not built yet" without the HTTPS exception; row 22's recovery covers M5/M6's.

### [P3-14] N3 names only `includeIf "gitdir:…"`; `includeIf "hasconfig:remote.*.url:…"` is the natural per-host way to scope credential settings and is equally repository-conditional

- **Location.** N3: "or under `includeIf "gitdir:…"`, does not apply". M2 says "under `includeIf`" generally.
- **Scenario.** A user with `[includeIf "hasconfig:remote.*.url:https://github.com/work-org/**"] path = ~/.gitconfig-work` reads N3 as not about them, meets M2, and cannot reconcile the two.
- **Required correction.** N3: "under any `includeIf` (`gitdir:` or `hasconfig:remote.*.url:`)". One phrase.
- **Check.** N3's wording.
