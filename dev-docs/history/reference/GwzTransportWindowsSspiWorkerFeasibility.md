# Native Windows SSPI process-worker feasibility

**Nonnormative investigation, 2026-10-03. No product implementation, policy adoption, or GO decision.** A separate native SSPI worker process is feasible for bounded design review: it can retain the complete authentication context across token exchanges, and the parent can terminate and supervise its owned process tree without attempting to interrupt an SSPI thread. The tested Windows Job arrangement also worked inside the existing Job imposed by the actual OpenSSH launch shape.

The standalone Python/ctypes fixture ran on Windows 11 build 26200, Python 3.13.5 x64, E: ReFS. It called `secur32.dll` directly. Synthetic credentials and local native token exchange were used; NULL credentials were exercised only for NTLM acquisition and its initial token. No credentials were offered to external hosts, and no OS/account/service/trust/hosts/zone/shared-proxy settings changed.

| Executed native fixture | Evidence |
|---|---|
| Worker owns native NTLM conversation | Acquire succeeded; first `InitializeSecurityContextW` returned `SEC_I_CONTINUE_NEEDED`; local native acceptor supplied a 158-byte challenge; the same worker/context returned `SEC_E_OK` and a 450-byte response. Final server authentication was not attempted: the identity was deliberately synthetic. |
| Normal exit, including NULL initial-context path | `DeleteSecurityContext` and `FreeCredentialsHandle` returned zero; held process wait confirmed exit code zero; Job accounting confirmed no active processes before capacity release. |
| Parent closes IPC | Worker observed EOF, performed native cleanup, and exited normally; parent confirmed exit and an empty Job. |
| Oversized IPC frame | Declared size 100001 exceeded the 100000-byte bound; worker rejected it and exited with code 1; parent reaped it before releasing capacity. Token bound was 65536 bytes. |
| Controlled worker stall and descendant | A real SSPI call had already returned; worker retained native identity/context storage and then slept. Job termination was followed by held-handle worker/descendant exit and an empty Job in **2.24 ms**. Admission was refused and credential storage retained before confirmation. |
| Abrupt parent loss | Outer observer held worker and descendant handles, terminated their owner, then confirmed both exits in **3.58 ms**. Closing the last noninherited Job handle supplied cleanup. |

These are individual local measurements, not worst-case timing guarantees. No blocked SSPI provider call was reproduced. The fixture proves actual native process/Job behavior around retained SSPI state; it does not prove successful integrated authentication, Kerberos, Digest, strict EPA, TLS channel binding, proxy authentication, or HTTP Git parity.

The worker was created suspended with an explicit executable path and inherited anonymous-pipe handle allowlist, assigned to an unnamed Job with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, checked for membership, then resumed. No breakaway flag or Job handle inheritance was enabled. A descendant created normally by the worker was confirmed in the same Job. Nested Job assignment succeeded while the SSH parent was already in a Job. This supports the observed launch shape; assignment failures in other hosts must fail closed before worker execution. [Nested Jobs](https://learn.microsoft.com/en-us/windows/win32/procthread/nested-jobs), [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).

The private IPC carries bounded frames containing challenge/token bytes and status, never credential/context pointers or native handles. The worker owns its complete conversation, native buffers and handles; the parent remains responsible for transport and admission. This is an experimental framing fixture, not a new GWZ protocol. A production design must retain existing credential/scope/fallback policy, bind each conversation to its transport/target and supplied channel bindings, and reject late results after cancellation.

Cancellation has two separate stages: request termination, then observe exit using a held process handle. A successful `TerminateJobObject`/`TerminateProcess` call is not exit confirmation. The fixture retained a real semaphore permit and parent credential bytearray until `WaitForSingleObject` signaled worker exit and Job accounting reported no descendants. A deterministic zero-time wait on the live worker returned `WAIT_TIMEOUT` and preserved both ownership and refused admission. If termination cannot be confirmed within the response deadline, return a bounded cancellation result while quarantining that operation's permit/storage/handles and continuing supervised reaping; do not admit replacement work against that slot. Unconfirmed termination after a kill request was not reproduced here. [TerminateProcess](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-terminateprocess), [WaitForSingleObject](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject).

Normal cleanup explicitly zeroed the fixture's owned native buffers and parent bytearray. Abrupt termination bypasses worker cleanup; confirmed process exit and subsequent handle closure establish process lifetime completion, **not secret zeroization in physical memory**, erasure of every Python temporary, or provider-state erasure. The Python fixture contains synthetic constants and immutable token copies and is not a production secret-storage design. Future real helper credentials must use bounded private IPC and deliberate zeroizing storage, avoid argv/environment/disk/logs, and retain required buffers until observed worker exit. The child environment was reduced to Windows runtime roots, fixture temporary paths and encoding; tokens/passwords were excluded from result logs. Anonymous pipes and a Job are lifecycle controls, not protection against a privileged process or another process able to read the same user's memory. Executable integrity, handle access and IPC/secret handling require review. [Process Security and Access Rights](https://learn.microsoft.com/en-us/windows/win32/procthread/process-security-and-access-rights).

Worker primary-token SID hash, authentication LUID and session ID matched the **SSH parent process**; this observed session was session 0. NULL native NTLM acquisition/initial context succeeded there. That is not proof of interactive desktop SSO or thread impersonation parity. `CreateProcessW` uses the caller process primary token, not an impersonated thread's token. A production worker must execute under the intended identity/logon session; service launch, impersonation and alternate-token choices need explicit review. No cross-SID/token-launch test was performed. [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw), [AcquireCredentialsHandle](https://learn.microsoft.com/en-us/windows/win32/secauthn/acquirecredentialshandle--general).

The Job supervises the owned worker and its inherited descendants. LSASS and external credential agents such as Pageant are outside it. Worker exit cannot establish cancellation, quiescence, or erasure of their internal operations; they were not terminated or instrumented. Provider-specific abrupt-exit behavior remains a review requirement. This approach improves lifecycle control over an in-process SSPI thread without promising an absolute Windows kernel stop deadline, and it preserves the option of native provider behavior without requiring the independent Rust candidate's explicit-credential-only API. Native TLS remains unchanged.

**Recommendation:** proceed only to bounded design review of a native process worker: whole-conversation ownership, parent transport binding, same intended identity, suspended Job assignment, bounded/redacted IPC, confirmed-exit admission, quarantine/reaping, and normal versus forced cleanup. Product parity and adoption remain unqualified.
