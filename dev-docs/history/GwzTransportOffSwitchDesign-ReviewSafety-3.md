## 1. Findings

### [P3-6] The Windows no-command set omits `!`, which Git Bash expands inside double quotes

- **Root cause.** §10's Windows rule double-quotes `<file>` and withholds the command for `%`, `$` and `` ` ``, the characters `cmd` and PowerShell expand inside double quotes. Many Windows gwz users run commands from Git Bash or MSYS, where an interactive shell performs history expansion on `!` inside double quotes as well (only single quotes suppress it), and `cmd` with delayed expansion enabled expands `!VAR!`.
- **Location.** §10 "Values, paths and identifiers", third bullet; §9's Windows row ("a path with `%` or `$` getting no command", which also omits the backtick the rule names).
- **Interleaving.** A Windows path `C:\ws\proj!git\.git\config` holds the key; the note's command, pasted into an interactive Git Bash, expands `!git` to the user's previous `git` command line; a quote inside that line closes the string and the remainder runs as further commands. With a `!` followed by a character bash cannot match, the command merely fails with "event not found".
- **Impact.** Bounded: it needs a `!` in a path, an interactive POSIX shell on Windows, and a matching history event; the POSIX rule itself (single quotes) is immune. But the Windows rule is frozen with a known gap, and the design already says TR1.8 "may refine" it.
- **Required correction.** Add `!` to the Windows no-command set (one character), and make §9's Windows row test all four characters; or state that the Windows command is for `cmd` and PowerShell and print the POSIX single-quoted form when the client runs under a POSIX shell on Windows. TR1.8 may still refine.
- **Closure test.** §9's Windows row: a path with `%`, `$`, `` ` `` or `!` gets no command, and a path with none of them gets the double-quoted command, which `cmd` and PowerShell run.

### [P3-7] The POSIX quoting row never exercises the one character that defeats single quotes

- **Root cause.** §9's quoting row tests a space and `$(` in a member path; neither contains `'`. The `'\''` rule is the whole defence for a path holding `'`: an implementation that single-quotes without it turns `/ws/it's$(cmd)/.git/config` into `'/ws/it's$(cmd)/.git/config'`, where the inner `'` closes the string and `$(cmd)` runs — the exact interleaving P2-5 was about, surviving through an implementation slip the test would not see.
- **Location.** §9 gwz-cli "quoting" row and the gwz-py row that follows it ("quoting and escaping as in gwz-cli's rows").
- **Impact.** Coverage: the frozen rule is right, but its only load-bearing case is untested.
- **Required correction.** The row's path holds a space, a `'` and `$(` together (for example `it's $(touch marker)`), and the assertion that nothing else runs stands (the marker does not appear). The gwz-py row inherits it.
- **Closure test.** The row as amended, through `sh -c`.

### [P3-8] 1.2.0 inherits no site for the native defaults fill — a consequence of E3's architecture

- **Root cause.** E3 keeps the 50 / 8 fill in the drivers: gwz-cli's `policy()` and gwz-py's native entry (`route::capture`'s request rewrite). §8 says 1.2.0's session host replaces that stage for gwz-py and that the `Client` resolves the setting once at open, but names no site for the fill once the native entry is gone; §12 names CS8.28 for gwz-py's CLI `--transport` only. The session plan's steps are not amended to carry it. This is the one new architectural root cause in the changed range: the native-default rule is duplicated per driver and per stage, with no owner in core, so each new stage must re-implement it or silently lose it.
- **Location.** §6 "How" and "Why the drivers and not core"; §8 "One value, before `open`"; §12.
- **Interleaving.** 1.2.0: a gwz-py `Client` opens with `transport_off` true; its requests reach the session host without the 1.1.0 native entry; nothing writes 50 and 8 into the policy; core resolves 100 and 32; the `MaxStartups` failure the design removed in 1.1.0 returns for gwz-py sessions, with no test row in §9's 1.2.0 list to catch it.
- **Impact.** A documented 1.1.0 guarantee ("runs at 1.0.17's defaults", §1) lapses in 1.2.0 for one driver, silently.
- **Required correction.** §8 states where the fill lives in 1.2.0. The natural single site is the session host, which already knows the session's `transport_off` from `open`'s options (`SessionOptions::transport_off`): when it is true and a request's policy leaves `concurrency` or `max_connections_per_host` unset, the host fills 50 and 8 before admission — one site for every client, which also closes the TR2.11 gap for callers that reach core through a session. §12 names the session-plan step that owns it (the CS3.10 / CS8.3 re-check it already triggers can carry it), and §9's 1.2.0 list gains the row.
- **Closure test.** 1.2.0 row: a gwz-py session with native selected and no values, 32 members against the `MaxStartups` fixture, every member succeeds and the server sees at most 8 concurrent connections; a 1.0.17-default row for a library caller through a session.

## 2. Invariant analysis

- **Who can flip it.** Unchanged and safe: the resolver's inputs are the flag, the variable and the user's global files; a workspace value is read only in the request's targets, under a regular-file ≤ 1 MiB guard that now also governs how the git directory is located (E9), and it can neither refuse, block, nor — with E1 — place runnable text in the user's shell on POSIX. On Windows the residual is P3-6's `!`.
- **Never a fallback.** No change; the fills and the timeout are set at resolution, before any backend or connection; nothing re-dispatches.
- **Stuck and degraded states.** No new ones. An unparsable include is refused with libgit2's file and line, at parity with 1.0.17, where libgit2 refuses to open any repository under it. A FIFO at a targeted member's `.git/config` is now skipped before any open, since the scan reads the `.git` and `commondir` files as text.
- **Disclosure.** `--verbose` now lists the global files read (`; read /home/u/.gitconfig`); the home path was already shown for a skipped file and absolute paths are already in machine output. libgit2's `<cause>` names a file and line only.
- **gwz-py.** The `UserWarning` under `error` surfaces as `GwzBridgeError` with the warning as `__cause__`; notes are `logging` records; the file reads and scan run off the GIL; `Client`'s new `None` default sends every explicit value and changes nothing for `gwz`. The one-clock limitation is stated where the advice is given.
- **Mixed versions and the native defaults.** gwz-cli and gwz-py both fill 50 / 8 and the CLI sets 3 s; a gwz-core library caller without a host context runs at 100 / 32, which the ledger and notes now state (its only known consumers are the two drivers). 1.2.0's gap is P3-8.
- **"Never worse than the status quo."** Holds for the route, host keys, credentials, both drivers' defaults in 1.1.0, the unreadable-file case and the repository-value cases. The lenient, documented exception remains gwz-py's 9 s libgit2 default.
