## 1. Findings

### [P2-6] The Overload's `N := max(1, Connected)` counts the refused attempt's own connection: a request-level limit is never learned below `L + 1`, and the key loops there charging members

- **Location:** §4.2 line 151 (`N := max(1, Connected)`, "Connected counted when the overload is accepted"); §4.1 line 136 (Connected: "Setup complete … Yes"); §4.3 line 162 (an exchange on a leased connection: "the leased connection is the attempt's own, in neither set"); §4.4 R3 line 197 ("`N := max(1, Connected)`, perhaps 3 while the others are still setting up") and R10 line 204 ("a 429 that arrives on a connection already counted Connected"); §4.5 rule 4 line 236; §4.6 lines 259, 265.
- **Root cause:** the Overload's value is taken from a count that includes connections the refusal proved the server would *not* allow: for HTTPS the refused attempt's own connection is "Connected" from TLS (the pool's `connected()` fires at TLS, `https_connection.rs:336-342`), and for a refusal on a reused idle connection every idle connection is counted although a request-level limit does not count idle ones. `hi(a)`, which the window already computes and which excludes the attempt's own connection, is the right upper bound and is not used.
- **Violated invariant:** D3 "`N` falls only to the number of connections … connected at the same moment" read as "the number the server was holding when it refused"; §4.2's own gloss "the refusal shows it would not allow the one more" — the "one more" is inside `Connected`.
- **Sequence (steady state):** STABLE, `N = 9`, server limit 8 at the request level (429 on discovery, no `Retry-After`), 8 leased and busy, one member queued. `Possible = 8 < 9` → ordinary start X: TLS up → X is Connected (`Connected = 9`) → discovery 429. Judged: others = 8 → `hi(X) = 8 < 9` → conclusive Throttle → Overload → `N := max(1, Connected) = 9` (X is still Connected until its lease is released `Discarded`, which follows the result). STABLE at 9, `T := T0`, note "limit now 9". X → Closing → Settling. Next queued member: `Possible = 9` → wait `Ts` → `Possible = 8 < 9` → start → 429 → `N := 9` again. Every start at 9 is refused and charged; `N` never reaches 8; a member that needs a slot while the 8 are busy spends its `R + 1` attempts at one per `Ts` and fails with `Capacity`. **Sequence (first wave):** SATURATED, 32 connects all reach TLS (`Connected = 32`), 24 discovery 429s: the first is conclusive (`hi = 31 < 32`) → `N := 32` → "`N = C` → SATURATED": a no-op Overload; the following 429s set `N := Connected` as discards happen, ending at 9 (the last 429's own connection still Connected), never 8. R3's narrative ("perhaps 3 while the others are still setting up") holds only for a connection-level refusal (a reset during connect, where the attempt was never Connected). **Reused connection:** `N = 9`, 8 busy + 1 idle, the member leases the idle one, discovery 429: `hi = 8 < 9` → Overload → `N := Connected = 9`. Same loop.
- **Impact:** the operator's primary scenario (GitHub answering 429) converges to one above the limit, with a refused, charged attempt per member start at that level: throughput at `L` but every queued member burns its budget. With `Retry-After` the loop is slower (one hold per refusal) and members fail after `R + 1` holds.
- **Required correction:** (a) On an Overload, `N := max(1, min(Connected, hi(a)))`: the refused attempt's own connection never counts, and for a leased exchange the idle connections beyond what the server could have held are excluded by `hi(a)`. (b) For HTTPS, define **Connected** for the limit machine as "the first exchange answered with a non-throttle status" and keep a TLS-up connection in **Setting up** until then (the retry machine's `FirstConnect::Connected` at TLS is unchanged; say that the two "connected" moments differ). With (b), the first-wave Overload takes `N` from the proven connections (R3's "3, then raised by successes"), and with (a) the steady state yields `N := 8`. (c) Restate R3, R10 and §4.5 rule 4; state that a `Retry-After` hold also holds exchanges on leased connections (case 36's assertion), since a request-level throttle counts those.
- **Closure test:** L1 and L3-H, limit 8 enforced at the request level on new and reused connections, no `Retry-After`: after the first wave `N = 8` exactly; in steady state no start at 9 is admitted except the probe; no member spends more than 2 attempts; the note never shows 9. A second run with the limit at the connection level (reset during connect) must still give case 24's trajectory.

### [P2-7] The restore step's starts have no judgement target: read literally their refusals are inconclusive, the step never ends, and the restore has no exit

- **Location:** §5.5 line 420 ("each step admits up to `min(N_good, 2 x max(1, Connected))` connections … a step whose starts all succeed raises `N` … a conclusive refusal during the restore is an ordinary Overload and ends it"); §4.4 table lines 181–185 (three attempt kinds only); §4.6 line 283 (DISCOVERING "fills to `N` in parallel; the next test is due at once"); §4.9 line 336 (the pool's limit is `N`, raised only to `N + 1` or `k` for a test); §4.1 line 144 (one test slot).
- **Root cause:** the restore admits several starts above `N` at once, but §4.4 judges a refusal as conclusive only against its attempt's target, and the only target an above-`N` start can have is a test's (`N + 1`, one at a time). A restore start has no row; under the ordinary row its `hi` (the other step starts plus Connected) is `≥ N`, so it is inconclusive.
- **Violated invariant:** every state × input pair defined (brief); the restore must end in STABLE or SATURATED (§5.5's own last sentence).
- **Sequence:** outage with survivors: Overload → `N := 4`; survivors lost; host returns; retry machine's probe succeeds → Healthy, `N = 4 < N_good = 32` → restore, step target `min(32, 2 × 4) = 8` (with `Connected = 4`): 4 new starts in parallel. The limit after the outage is 6. Two succeed (`N := 6` by §4.2), two are refused: each has `hi = 4 + 3 = 7 ≥ N` (whether `N` is 4 or 6) → inconclusive by the ordinary row → "no input", requeued, charged. "A step whose starts all succeed" is false; "a conclusive refusal … ends it" never fires; the next step's rule is undefined (re-admit to 12? stay?). If the step is re-run, the two are refused again, charged again, until no non-final carrier remains; the machine is then in a restore with no timer (DISCOVERING has none), no test slot in use, and no exit: `N = 6` until a later ordinary refusal happens to be conclusive. Three further gaps on the same rule: (i) the step's target can be *below* `N` (`N = 4`, `Connected = 1` after the first probe → target 2), contradicting DISCOVERING's own "fill to `N`"; (ii) a conclusive refusal during an outage recovery is a Suspect, which by §4.5 rule 3 opens a confirmation, not "an ordinary Overload"; (iii) the pool's limit (§4.9) is `N` or `N + 1`, so the pool refuses to create the step's extra connections (the very defect P2-4 fixed for the single test).
- **Impact:** the restore either stalls below `N_good` with members' attempts spent, or is undefined; both are bounded (throughput and attempts), but the design's stated recovery guarantee (D8, OQ16, case 27b "meets a conclusive refusal at 16, `N := Connected`, STABLE") is not delivered by its rules.
- **Required correction:** add a fourth row to §4.4: **Restore step start** — starts when the retry machine has just become Healthy and `N < N_good`; target `S := max(N, min(N_good, 2 × max(1, Connected)))`; its starts are not tests (no test slot, no quiet requirement) and are carried by non-final members; refusal **conclusive iff `hi(a) < S`**, routed through the evidence filter as any conclusive refusal (a Throttle is an Overload at once; a Suspect opens a confirmation, which, being taken at `Connected + 1` on a quiet key, settles the step); a step is complete when every start has a result; if all succeeded, `N := Connected` by §4.2 and the next step doubles; the restore ends on any Overload (STABLE at the new `N`, `T := T0`) or on reaching `N_good` (SATURATED if `N_good = C`, else STABLE with `T := T0`). §4.9: the pool's limit is `S` for the step's duration, set under the admission lock like a test's. Remove "is an ordinary Overload".
- **Closure test:** case 27b re-derived from the rows: `N = 4`, `N_good = 32`, post-outage limit 6: one step to 8, two refusals, exactly one conclusive (`hi = 7 < 8`), confirmation at `k = 7` refused fair → `N := 6`, STABLE at `T0`; no member spends more than one attempt on the restore; the pool created 4 entries. And the degenerate case `Connected = 1`, `N = 4`: the first step targets 4, not 2.

### [P2-8] `Ns := lo_s(a)` sets the setup limit to the wave's size minus one; later drops of the wave are inconclusive; `Ns` converges one wave per member attempt, and case 3's claim is false

- **Location:** §4.10 lines 345–347 (`lo_s(a)` = other setups in progress for the whole window; "conclusive iff `hi_s(a) < Ns`: … `Ns := max(1, lo_s(a))`"); §10.2 case 3 line 489 ("`Ns` is set from `lo_s` at the first conclusive drop, settles at most 10 after successes"); §4.7 bound applied to `Ns` (case 3).
- **Root cause:** `lo_s` of the first drop to return is the number of co-setups of the wave still in progress, not the number the server was holding: a `MaxStartups` drop returns in one round trip while the accepted setups take a full login, so at the first drop every other setup is still in progress. The value is taken before the wave has resolved, which is the error revision 3 corrected for `N`'s confirmation (§4.5 last paragraph) and not for `Ns`.
- **Violated invariant:** D1/§4.10 "a conclusive pre-authentication drop lowers `Ns` to the limit"; §4.7's bound as applied to `Ns`.
- **Sequence:** first wave of 32 SSH setups, `MaxStartups` 10 (deterministic drop above 10). All start in one pass. First drop returns after one RTT: `hi_s = 31 < Ns = 32` → conclusive → `Ns := lo_s = 31`. Second drop: `hi_s = 31 ≥ 31` → inconclusive. All 22 drops: `Ns = 31`. The 10 successes: `Ns := max(31, lo_s + 1)` → 31. 22 members requeued (attempt 1). Second wave: setups in flight `< 31` → 22 start; 12 dropped; first drop `hi_s = 21 < 31` → `Ns := 21`; rest inconclusive (attempt 2). Third wave: 12 start, 2 dropped, `Ns := 11` (attempt 3). Fourth wave: 2 start (attempt 4, their last; these are ordinary starts, permitted on a final attempt), both accepted. Refused attempts: 22 + 12 + 2 = 36 against the bound case 3 claims (`(C − L) + 1 + 6 = 29`); `Ns` ends at 11, not 10. With OpenSSH's probabilistic drop (`10:30:100`), the fourth wave's two final-attempt setups can be dropped at 30%+, failing members.
- **Impact:** a steady `MaxStartups` limit below the wave costs every member one refused attempt per wave for about `R` waves, can fail members on their final attempt under the default probabilistic drop, and leaves `Ns` one above the limit; the only SSH signal the design has (F2) is handled by an estimator that does not converge in one step.
- **Required correction:** take `Ns` when the drop's window has resolved: on a conclusive drop `a`, record `S_lo_s(a)`; when every setup in it has a result, `Ns := max(1, |succeeded ∩ S_lo_s(a)|)` (the co-setups the server actually let through were the ones it was holding), and until then hold new setups as the confirmation holds starts. Later drops of the same wave are no input (as co-refusals are). The `Ns` test then climbs it on the setup timer as §4.10 says. Re-derive case 3's bound from this rule (one wave of `C − L` refused setups, then at most the tests).
- **Closure test:** L3-S with a deterministic drop above 10 and a first wave of 32: after the wave resolves `Ns = 10` exactly; the second wave admits 10 setups and none is dropped; refused setups total `C − L = 22`; no member spends more than 2 attempts. L1 with scripted result order (drops first, logins later) asserting `Ns` is not assigned until the window resolves.

- **Violated invariant:** D6 "A test is a real member's new connection".

Loop 1 leases it to M. M "succeeds" with no setup: `Connected = 8`, judged as a success with `lo = 8`: PROBING→DISCOVERING (`Connected < C`), `N` unchanged, DISCOVERING tests again at once. One wasted cycle, and the pool's limit sat at 9 with no 9th connection. Bounded: nothing is learned wrongly.
- **Required correction:** mark the test's pool request **create-only** (skip loop 1), or state that a test served by reuse is "unfair, re-armed" and that the pool reports whether a request was served by reuse (the retry machine already receives `fresh`, `machine.rs:134`). Say which.

### [P3-5] After a settling hold lapses, a different waiting request can take the freed slot, orphaning the evictor's victim record and causing one extra eviction

- **Location:** §4.9 line 337 ("A waiting request whose recorded eviction victim has become a settling hold treats the victim as still present … until the hold lapses"); C2 (`schedule()` loops 2 and 3, `allocation.rs:47-130`).
- **Root cause:** the guard is keyed on the victim's presence (entry or hold). When the hold lapses, the slot is unowned: loop 2 serves waiting requests in `BTreeMap` order, and if another request (whose own victim is still a hold) is earlier, it creates; the evictor then finds its victim neither an entry nor a hold, the host still full, and loop 3 evicts again. Today one `closed()` is followed at once by one creation, so the orphaning cannot happen; the hold introduces the gap.
- **Violated invariant:** one eviction per waiting request (the pool's own rule, and case 42's "exactly one `Evicted`").
- **Sequence:** limit 8, 2 leased + 6 idle of A; requests R1 then R2 of identity B (R2 earlier in map order). R1 evicts I1, R2 evicts I2; both close → holds. I1's hold lapses first: loop 2, R2: `total() = 7 < 8` → R2 creates. R1: `total() = 8` → no. Loop 3, R1: victim I1 is gone and not a hold → guard false → host full → evict I3. I2's hold lapses → R1 creates. Three evictions for two requests; bounded by the number of waiting requests on the key.
- **Required correction:** bind the lapsed slot to its evictor (the hold carries the requester's id and loop 2 serves that request first), or make the guard "this request has already evicted once and has not been served", or let any request whose recorded victim is gone (not merely a hold) wait for the next `schedule()` after a creation rather than evict again. Say which; case 42 should add a second waiting request.
- **Closure test:** pool unit test as the sequence above: exactly two `Evicted` closes for two requests, in any map order.
