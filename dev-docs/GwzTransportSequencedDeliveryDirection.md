# GWZ transport — sequence messages within each virtual stream

Date: 2026-09-23. Status: **DRAFT direction, not a frozen protocol or implementation authorization**.

The operator selected ordering in the virtual-stream protocol rather than relying on the host scheduler to preserve every stream's delivery order. This is a new design direction after the [profile-3 reordering NO-GO](../../dev-docs/GwzTransportV3ReorderingDesign-Verdict.md), not another patch to that stopped object. The accepted placement and existing profile-1/2 contracts remain controlling until a complete sequenced-stream design is reviewed. The proposed profile-3 number is unreleased and may be reused only after an explicit compatibility review; no field number, version or public API is frozen here.

## Required behavior

Each side numbers the messages it generates for a given positive stream ID, starting at one. The counter belongs to **one stream and one sending direction**; there is no binding-wide delivery order and no shared counter between the two sides. Different streams may be delivered in any interleaving. Within one stream, the receiver admits bounded out-of-order messages but applies their effects and exposes their bytes to the file-stream API in causal sequence. A message waiting for a gap is buffered, not treated as successfully applied. Missing predecessors eventually produce an explicit bounded failure, never an indefinite wait or a successful close.

An abortive terminal (`OpenFailed`, `IdentityCheckFailed`, `Failed` or `Cancel` where legal) may explicitly supersede earlier messages in its own direction. The receiver validates its session, request, operation, endpoint, stream, version and terminal body before fixing failure. It then discards earlier buffered or later-arriving messages covered by that terminal without changing the failure outcome, facts or lease ownership. A graceful terminal (`Closed`, successful identity completion, or an ordered half-close transition) cannot skip missing predecessors. It becomes effective only after its preceding message sequence and the applicable byte/close prerequisites are accounted for. The exact terminal watermark and abort declaration are part of the detailed protocol design, not inferred from a delivery callback.

The existing `Data.offset`, `EndWrite.final_offset` and `Close.final_offset` remain independent checks on byte continuity and half-close semantics. A byte count alone cannot account for zero-byte `Window`, `Flush`, `Flushed` or terminal controls; message sequence supplies that ordering. Neither message numbers nor byte offsets assert Git-level success. Once the transport supplies the same ordered bytes, EOF and errors as a socket, git2 interprets the Git protocol response as it does today.

The host still pins the exact sender/receiving Port generation for an item and cannot use a legacy receiver's session-mismatch `Ok` as admission to another generation. It owns bounded delivery, retry and cleanup; it does **not** need a per-stream FIFO to make the peer's protocol state correct. It must allow a missing lower sequence to make progress while later messages are buffered or waiting, rather than occupying every task or byte slot with higher sequences. A terminal must resolve in-flight admission/abort races before the host releases cleanup ownership. Profile-3 `WrongSession` remains a receiver safeguard, not a substitute for the host generation check.

## Details the next design must freeze

1. The taut Envelope field(s), negotiated version, sequence allocation point, duplicate identity rule, overflow behavior and terminal cutoff/watermark. Retained profile-1/2 encoding and behavior must remain unchanged.
2. The distinction between **received into a bounded reorder buffer** and **applied in sequence**. An Open/CheckIdentity receipt may acknowledge endpoint work only after its opening action and route are admitted; a buffered later control is not yet an applied effect. The host and async Port API need a truthful completion signal for both states without holding a global lock or waiting behind an unrelated stream.
3. Per-stream and per-binding reorder-byte/frame limits, reserve for the missing predecessor, gap timeout, and fair retry under backpressure. Include bounded frames that arrive before Open sequence 1 without letting an unregistered request or unverified endpoint context create work.
4. The exact two-direction close and cancellation grammar. A successful Closed must not hide missing Data or controls; an abortive terminal may discard them only with an explicit cutoff and stable failure result. An already dequeued frame must be either delivered, retained under the cutoff, or atomically aborted—never silently lost and then counted as successful delivery.
5. Charged cleanup and terminal replay state. A late duplicate or superseded frame must not reopen a route, adopt facts, release a second lease or fail another stream merely because it arrived after an abortive terminal. A missing predecessor or unresolved host delivery race must fail the binding by its deadline.

The proof should permute messages independently in both directions and across streams, with random Data chunk sizes and random read sizes, and compare the reconstructed streams byte-for-byte against source data. It must replay a failing seed deterministically. Directed cases include `Failed` overtaking an already dequeued `Window`/`Flushed`, successful `Closed` arriving before Data or EndWrite, missing and duplicate sequence numbers, a pre-Open frame, full reorder capacity with the missing predecessor ready, mixed-profile generation replacement, and two streams sharing a binding where one fails without changing the other's outcome.

No transport, core, CLI or Python behavior is activated by this direction note. The next artifact is a complete taut/profile/host design with a settled tuple and dual review before implementation.
