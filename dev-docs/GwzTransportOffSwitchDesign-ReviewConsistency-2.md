## 1. Findings

### [P3-6] §10's gwz-py surface and the migration notes omit D3's gwz-py exceptions, and §6's "Explicit values are honoured" is contradicted by its own next bullet

- **Location.** §6 line 92: "Explicit values are honoured." §6 line 95: "A `Client` built with `max_connections_per_host=32` cannot be told from the default and sends no value (`client.py:188-194, 294-295`), so it runs at 8 on the native transport"; and "A native operation uses the process's value: `configure_transport_timeout`'s, or 9 seconds." §10 lines 188–199 (gwz-py's frozen surface) and §5 line 86 (the migration notes "state the same defaults") say neither.
- **Root cause.** D3 was applied to §6 and §9 (line 151 tests the per-call value only) but not carried into the gwz-py part of the frozen surface.
- **Evidence.** `client.py:294-295` at `766de530` is exactly the elision the draft describes, so the edge is real: an explicit `Client(max_connections_per_host=32)` is indistinguishable from the default and is rewritten to 8 under native. gwz-py's CLI, which has `--ssh-timeout` (`cli.py:77-78`), runs at 9 seconds when the flag is omitted and native is selected, while gwz-cli runs at 3; §6 line 95 covers "an application", and gwz-py's CLI is not named anywhere.
- **Violated invariant.** §10 is "the surface this freezes" and S7.5 (1.1.0)'s Surface review reads it; a documented promise ("explicit values are honoured") must state its exception where it is made.
- **Consequence.** A Python application that passes 32 explicitly and selects native silently runs at 8 against a documented promise; gwz-py's CLI users read D3's "3 seconds" and get 9; S7.2's migration notes, as §5 specifies them, would not carry either.
- **Required correction.** Either (i) qualify §6 line 92 ("Explicit values are honoured, except gwz-py's constructor value of 32, below"), add to §10's gwz-py bullets the three facts (the request policy carries 50 and 8 when unset; a `Client` constructed with 32 runs at 8 under native; the libgit2 timeout is the process's, 9 seconds unless `configure_transport_timeout` or gwz-py's CLI `--ssh-timeout` set it), and add them to §5's migration-notes sentence; or (ii) remove the edge by giving `Client.__init__`'s `max_connections_per_host` a `None` default meaning unset, which changes no caller's behaviour with gwz selected, and say in §12 that this is the one gwz-py signature change under amendment 2 §3.1's "public API unchanged" rule — the drafter may decline (ii) with a reason. See also the architectural note in §2.
- **Closure test.** §9's gwz-py rows gain: a `Client(max_connections_per_host=32)` operation with native selected carries the documented value; gwz-py's CLI with `GWZ_TRANSPORT=native` and no `--ssh-timeout` against the silent fixture fails at the documented timeout.

### [P3-8] The removal command for a global value reached through `include.path` names a file that does not hold the key

- **Location.** §2 line 40 and §10 line 161: "a value reached through `include.path` is reported against the file that included it." §10 line 174 (the note), line 179 (the refusals) and line 192 (gwz-py's warning): "remove it with `git config --file <file> --unset gwz.transport`". §10 line 162 asserts that this command "removes the key from that file whichever it is".
- **Evidence and sequence.** `~/.gitconfig` holds `[include] path = ~/.gitconfig.d/gwz`; that file holds `gwz.transport = native`. The resolver reports `file` as `~/.gitconfig` (deviation 4, justified: git2-rs's `ConfigEntry` exposes no origin path, `config.rs:525-565`). The note tells the user `git config --file ~/.gitconfig --unset gwz.transport`; git exits 5 ("key does not exist" in that file) and the setting stays native. The same holds for the refusal of a malformed included value. `ConfigEntry::include_depth()` is exposed (`config.rs`, the accessor at the cited range), so the design can tell an included value apart even without its path.
- **Violated invariant.** Surface P3-1's disposition, which revision 1 adopts, "every form's help entry and message names its undo"; and §10 line 162's own claim about the command.
- **Consequence.** The one undo the message gives fails for every value a user keeps in an included file, which is a common dotfiles layout.
- **Required correction.** When `include_depth > 0`, the note, the refusal and the warning say "in a file included by <file>" and give the undo as "remove it from the included file, or run `git config --global --unset-all gwz.transport` after removing the include" (or any equivalent the drafter prefers); §10 line 162's "whichever it is" is qualified to a value the file itself holds; the JSON gains nothing unless the drafter wants `included: bool`.
- **Closure test.** §9's gwz-core file rows: an included value's note names the including file and the included-file wording; the given undo command, run against the fixture's files, removes the value.

**Architectural note (new in revision 1, labelled as such).** D3 places route-dependent defaults in the drivers: gwz-cli's `policy()` and gwz-py's native entry each write 50 and 8 into the request when unset, while the route itself is decided in core (`transport_binding::configure`, by the presence of a host context) and core's `resolve_jobs`/`resolve_per_host` "need not learn the route".
