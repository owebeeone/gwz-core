## 1. Findings

### [P1-1] TR1.3's revision list carries the server design's unverified listener into the release: the client sends its secret-bearing environment as the first frame to whatever answers at the address

- **Location.** Object §5 Phase 1 TR1.3 (lines 150–156), Phase 4's Windows note (line 216), Phase 7 exit (242–245), §8 "Live authenticated connections in a server" (364). Controlling text: server design §3 ("`SessionOpen` is the client's first frame… `SessionOpen { …environment: EnvironmentEntry[]… }`"), §4 (every check is on the host's accept side; "the host refuses a directory with another owner"), §4 default address (`$XDG_RUNTIME_DIR/gwz/`, else `$TMPDIR/gwz-<uid>/`, else `/tmp/gwz-<uid>/`), §7 (`auto` "uses the default server for this environment, and starts one if none answers"), §11 (Windows pipe `\\.\pipe\gwz-<user SID>-<key>`), contract §5.6 ("The snapshot is secret-bearing… captured losslessly" — the whole process environment).
- **Violated invariant.** Server design §4: the snapshot "crosses the socket once, in `SessionOpen`, over a connection that has already passed both checks." Both checks are performed by the *server* on the *client*. Nothing verifies the *listener* before the *client* writes the snapshot. Severity contract: credential exposure.
- **State sequence.** (1) Victim's environment lacks `XDG_RUNTIME_DIR` and `TMPDIR` (cron, a container, a CI runner, an SSH login without logind), so `auto` resolves to `/tmp/gwz-<uid>/server-<key>`; `<key>` is a hash of the core version and must-match values (`HOME`, `XDG_CONFIG_HOME`, `umask`, timeout), all guessable. (2) Another local user pre-creates `/tmp/gwz-<uid>/` (world-writable `/tmp`, sticky bit allows creation) and listens on `server-<key>`. (3) The victim runs any command with `--server auto` or `GWZ_SERVER=auto`: the socket channel "connects, sends `SessionOpen`" — the entire environment (`GH_TOKEN`, cloud keys, proxy credentials, everything) — before reading a byte. The victim never reaches the host-side directory-owner refusal because it never starts a host: the squatter answered. Windows: the pipe namespace is global; any user can create `\\.\pipe\gwz-<SID>-<key>` first (SIDs are enumerable); the client connects and writes `SessionOpen`. An explicit `--server ADDRESS` has the same shape by construction.
- **Impact.** Disclosure of every secret in the caller's environment to another local user, on the one code path the plan adds for reuse across commands. OD2's opt-in default narrows who is exposed, not whether.
- **Required correction (text, this object).** Add to TR1.3's list: the client verifies the listener before sending anything — on Linux/macOS `SO_PEERCRED`/`getpeereid` on the connected client socket must equal the caller's uid, and the socket file and its directory must be owned by that uid with no group/other bits and no symlink; on Windows `GetNamedPipeServerProcessId` → token user SID must equal the caller's, and the connect uses `SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`; the `/tmp` fallback is refused unless the directory already exists with that owner and mode (or dropped); a failed check refuses with a named code and sends no frame. Add "client-side listener verification" to Phase 4's list of Windows primitives and to Phase 7's exit ("the sandbox refusal" gains "and the squatted-listener refusal, from the client side, on all three platforms"). Add the hazard to §8.
- **Closure test.** A listener owned by another uid (or, on Windows, a pipe created by another SID) at the `auto` path and at an explicit address: the client exits with the refusal code and the fake listener records zero bytes received. A directory at the `/tmp` fallback with the wrong owner or mode: the same.

### [P2-3] TR1.5 leaves the off switch's scope open, so a workspace- or repository-scoped configuration key would let a workspace force every network operation onto the native route silently

- **Location.** TR1.5 (164–172: "the switch's form (a configuration key, an environment variable, a flag, or several) and their precedence"); OD6 (351); S7.1 (273: "The native branch stays… for the off switch").
- **Violated invariant.** Transport design §3.1–3.3 and the gh-only HTTPS policy: the transport refuses arbitrary configured credential helpers and URL-embedded credentials; Transport Plan Phase 6 "no advertised route silently remains native". The server design's own sandbox argument (§4) already treats workspace configuration as attacker-controllable ("Git runs commands named in a workspace's own configuration").
- **State sequence.** TR1.5 chooses a gwz configuration key without stating its scope. A workspace manifest or a member's repository configuration sets it. Every operation in that workspace takes the native path: libgit2 runs the repository's configured `credential.helper` and, in a server, libssh2 uses the server process's agent (see P2-4). Nothing in normal output says so; only `--verbose` and the documentation ledger do.
- **Impact.** A workspace silently removes the gh-only and endpoint-owned credential protections for everyone who clones it; through a server it also selects a different agent. This is worse than 1.0.17 only in that the user believes the protections apply.
- **Required correction.** TR1.5 states: the switch is scoped to the user's process — a flag, an environment variable, or user-level configuration — and a workspace- or repository-level value is ignored (or refused with a message naming the scope); precedence is flag > environment > user config; a session whose switch is on prints one non-verbose notice on the first network operation.
- **Closure test.** A workspace whose manifest and member `.git/config` both set the key: the transport route is taken and the observation says so; the same value in user config or the environment: the native route is taken, reported in the notice and in `--verbose`.

### [P2-4] TR1.5 requires the off switch to "work through a server", but native SSH in a transport-build server authenticates with the server's agent, which the server design's must-match list excludes in transport builds

- **Location.** TR1.5 (166: "that the switch travels in the session's environment snapshot and works through a server"); TR1.3 list (150–156) has no corresponding item. Controlling text: contract §5.8 ("libgit2 and libssh2 read some process state themselves: the SSH agent socket when they connect"); server design §5 must-match row ("`HOME` and `XDG_CONFIG_HOME` in every build, plus `SSH_AUTH_SOCK` in ordinary builds") and §5 rule ("A command run through a server must behave as the same command run in the client's own process, or be refused").
- **Violated invariant.** Server design §5's rule; contract §5.6 (a session's credentials come from its snapshot).
- **State sequence.** Transport-build server started from terminal A (`SSH_AUTH_SOCK_A`). Client B in terminal B (`SSH_AUTH_SOCK_B`, a forwarded agent with a different GitHub key) runs `gwz push` with the off switch set. The snapshot carries the switch; the session takes the native route; libssh2 in the server process connects to `SSH_AUTH_SOCK_A`; the push authenticates as A's identity. The `auto` key does not separate the two because `SSH_AUTH_SOCK` is not a must-match value in transport builds.
- **Impact.** Identity crossover between same-user sessions on the one route the switch enables; a push attributed to and authorized by the wrong key.
- **Required correction.** TR1.5 and TR1.3 both state: when the switch is on, every variable the native path reads (`SSH_AUTH_SOCK` at least, plus any libgit2/libssh2 process read the contract §5.8 list names) joins the session's must-match set, so a mismatch refuses with `server_environment_mismatch`; alternatively, a session with the switch on is refused by a server and must run in-process. The `auto` key includes the switch and those values when the switch is on.
- **Closure test.** Phase 7 exit adds: a server started with one `SSH_AUTH_SOCK`, a client with the switch on and a different `SSH_AUTH_SOCK`: refused, and no connection is opened with the server's agent (the fixture agent records zero signature requests).

### [P2-5] TR1.2's questions omit relocating endpoint configuration from runtime construction to the operation; the endpoint code and HTTPS design §4 fix the agent, home, TLS roots, proxies and the `gh` environment at construction, so a host-context runtime would serve every session with the constructing environment's identity

- **Location.** TR1.2 Q1 (133: "The host context owns one transport runtime and pool… when they are built") and Q2 (134–138: equality inputs for reuse; "for HTTPS: TLS roots and proxies"); Q11 (147). Controlling text: contract §5.6 ("Each network operation derives its endpoint configuration from [the session's snapshot]: the SSH home and agent socket, TLS roots, proxies, and the `gh` environment") — satisfied today only because each operation builds its own runtime; HTTPS design §4 ("Snapshot the endpoint environment at runtime construction, allow gh to use that environment"); live `local_command.rs:33–37` (one `vars_os()` snapshot feeds both endpoint configs), `transport_host/mod.rs:40–54` (`SshEndpointConfig{home, agent}` from `from_environment()`), `https_auth.rs:31,326–327` (the `gh` helper runs with `config.environment`, the construction-time snapshot), `pool/mod.rs:169–175` (`Request` carries no environment).
- **Violated invariant.** Contract §5.6 and server design §5 ("The server's own environment is used for nothing on the session path"); HTTPS design §4 "Look up credentials afresh for each Gh HTTP request" — fresh, but with whose environment.
- **State sequence.** TR1.2 answers Q1 "the host context builds the runtime once" and Q2 "connections are reused when these inputs are equal", and answers Q11 only for pool changes. Implementation keeps the endpoint's construction-time configuration (there is no question asking it not to). In a server, the runtime is constructed from the first session's (or the serving CLI's) snapshot; every later session's private-HTTPS request runs `gh auth git-credential get` with that `GH_TOKEN`/`GH_CONFIG_DIR`, and every new SSH connection uses that agent and known_hosts. Q2's equality check runs over inputs that no longer vary per session, so it passes vacuously. The challenge-reuse code is not a vector (`ChallengeLease` is scoped by session and operation), which leaves this as the single HTTPS crossover path.
- **Impact.** Credential and identity crossover between same-user sessions and clients through a server, and between operations in one Python process after an environment change; a P0-class defect if built as the questions permit.
- **Required correction.** Add to TR1.2's list, before Q2: "**Configuration ownership.** Endpoint configuration — SSH home, agent, known_hosts inputs, TLS roots, proxies and the `gh` environment — becomes a per-operation input derived from the requesting session's snapshot (contract §5.6), carried on each request into the shared runtime; HTTPS design §4's construction-time snapshot and `SshEndpointConfig::from_environment` are superseded; the design names the gwz-transport and endpoint changes this needs (Q11)." Q2 then says equality is computed over those per-request inputs, and Q10 adds that a request never observes another session's configuration.
- **Closure test.** Phase 6 exit adds: two sessions on one host context with different `GH_TOKEN` values and different `SSH_AUTH_SOCK` values against the disposable fixtures: each `gh` invocation sees its own session's token, each new SSH connection asks its own session's agent, and no connection is shared (the fake `gh` and fixture agents record per-session inputs).
