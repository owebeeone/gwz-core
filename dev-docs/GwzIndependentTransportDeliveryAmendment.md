# GWZ transport — independent delivery amendment

Date: 2026-09-23. Status: **DRAFT; review required**. This amends the accepted [endpoint placement design](GwzRemoteTransportPlacementDesign.md) and its [embedding guide](../docs/TransportPlacement.md). It is paired with the new application [start-ticket design](../../dev-docs/GwzOperationStartTicketDesign.md), but transport delivery has its own owner and progress rules. No production route or physical wire carrier is activated by design approval.

## 1. Two logical lanes, one transport owner

An application lane carries GWZ commands, admission, results, events and cancellation. A **transport delivery lane** carries only `(existing request_id, gwz_transport::Envelope)` between the core mux and the selected endpoint. These lanes may share an in-process Taut carrier, but must not share an application call's request/response scheduling, result queue, worker, lock or cancellation future. A transport frame must be emitted and consumed without creating a GWZ action call or waiting for an action response, event subscription, Python `await`, or final result. Transport messages are not application responses, and an application result is not transport EOF.

The accepted `RequestMeta.transport_message` tag 10 and `ResponseMeta.transport_message` tag 9 remain optional compatibility attachment slots and retain their types. They do **not** constitute the delivery schedule. When no application message is being sent, a host must provide a delivery-only Taut message/event carrying the same request ID and shared Envelope through the supplied in-process channel. Define a generated host-only Taut message `GwzTransportDeliveryV1` with required field 1 `request_id: string` (the already registered internal transport ID, at most 128 UTF-8 bytes) and required field 2 `message: gwz_transport::Envelope`. It is an asynchronous delivery event in each direction, not a `GwzCore` action service method and not an application response. Its receiver/route generation comes from the bound host port, never from a caller-selected field. The existing one-field `GwzTransportDelivery` consumer-test wrapper is evidence for Envelope projection only; it must not be mistaken for this full host message. There is no requirement for a new physical connection, wire framing or iroh in this batch. A host that can only piggyback transport frames on application request/final-response traffic cannot advertise nonlocal placement.

Core owns Git operation policy, mux registration, stream identity and the local endpoint. The endpoint owner owns SSH/HTTPS connections, authentication and pooling. The delivery host owns the two forwarding pumps and bounded queues between `TransportPort`s. For local placement, both ports and pumps may remain in Rust, without crossing Python. For a Python-supplied route, `gwz-py` owns the in-process delivery host on the Python event loop; it forwards generated Taut delivery messages to the Rust core/endpoint ports, but does not parse Git stream content, select a remote or manage pooled connections. The Python Client owns the delivery host's lifecycle, not each application coroutine.

## 2. Python event-loop binding

Before the first application command that selects a Python-supplied endpoint, `NativeCoreBridge` binds one delivery host to the Client's running event loop and exact native runtime/route generation. Both directional pumps start before transport request registration or Bind/Open. The host has one owner across overlapping application operations and retains its loop reference until all registered request scopes and their transport cleanup retire. A Client used from a different loop must fail before transport admission or use an explicitly reviewed transfer API; it must not silently install a second pump for the same binding.

The pumps are independently scheduled tasks, not children of `start_fetch()`, `fetch()`, `result()`, an event iterator or any action waiter. Cancelling any of those waiters cannot cancel, pause or replace either pump. Returning an application result, releasing a terminal, or timing out a cleanup wait cannot stop a pump while owned transport work remains. The host continues delivering Window, Cancel, Failed, Close and peer facts after a result where needed for stream/request cleanup. No Python callback is invoked from Rust while holding a mux, pool or operation lock. Blocking native Git and endpoint work stays off the Python loop and GIL.

The current single FIFO `TransportPort::next_message()` plus blocking `deliver()` is **insufficient** as the only host pump: a blocked Data admission can strand Window or Cancel behind it despite a control reserve. Extend the candidate port with independently selectable **urgent-control** and **ordered** outbound queues (`next_urgent_message()` and `next_ordered_message()`, or one equivalent atomic selector) and one delivery task per queue per direction. The four tasks belong to one host owner; neither an application worker nor a blocked ordered delivery may stop urgent delivery. The urgent queue contains Window, Cancel and Failed, plus an abortive binding-shutdown notification. Window may bypass Data because it grants credit for the opposite flow. Cancel/Failed may bypass and atomically discard earlier unsent Data for **their own request/stream**; they cannot discard a peer's Data. Open, CheckIdentity, Bind/Bound, Data, Flush/Flushed, EndWrite and graceful Close/Closed remain in the ordered lane and preserve their own stream's causal order. An urgent message cannot overtake the Bind/registration that authorizes its context. Across unrelated streams no global FIFO promise is made; ordering is per request/stream where the protocol requires it.

Both directions progress concurrently. Bounded host and transport queues, with separate reserved urgent-control capacity, account for the entire encoded delivery message before allocation. Each ordered task has at most one dequeued frame in flight; the urgent task may continue while that frame waits for peer admission. A slow receiver may backpressure Data normally. If an ordered frame cannot be admitted within a fixed **30-second host delivery-stall deadline**, the binding fails closed and wakes all affected owners; this is independent of a disabled SSH read timeout. This supplies a bounded outcome for a same-stream graceful Close that must remain behind undelivered Data. Shutdown disconnects without waiting for that deadline. No successful `deliver()` acknowledgement is inferred from queueing an application response. Existing `next_message()` may remain for local legacy users but cannot be used alone to qualify a supplied endpoint. The proposed queue selection requires implementation and tests in `gwz-transport` and the core facade before activation; this document does not claim current code already supplies it.

An item transferred by either queue selector is either delivered exactly once to the peer port or causes that binding to disconnect. A cancelled pump, loop shutdown, decode error, invalid context, bounded-queue failure or carrier loss must atomically mark the binding failed, wake all four tasks and all affected stream/request waiters, reject new Open/check, and retain cleanup ownership. It must not silently drop an item and leave a stream live. Local shutdown completion is reported only after owned local workers/streams actually drain; remote cleanup confirmation remains separate. The Client may close application admission without losing the delivery host until its transport scopes drain. If the event loop is closing or cannot service the pumps, it cannot promise delivery: it fails the binding and lets Rust's supervisor finish local cleanup. A Rust-side host watchdog observes pump heartbeat independently of the Python loop and disconnects a loop-stalled binding after the 30-second delivery-stall deadline; a blocked loop cannot be relied on to run its own timeout. The contract guarantees delivery **while the bound host is live**, and explicit failure otherwise; process crash cannot guarantee either delivery or remote rollback.

For a core-local Rust endpoint, the same ordering, backpressure, control-progress and fail-closed rules apply to Rust-owned pumps. Python's event loop does not relay messages that never cross the Python/core boundary. A Python Client still must keep its native runtime alive through cleanup and must not mistake application task cancellation for host shutdown.

## 3. Correlation and independence boundary

For this new ticket contract, the transport delivery lane uses a **Client-generated internal transport request ID** in `RequestMeta.request_id` and the Envelope; the optional caller correlation ID moves to `OperationPrepareV1.caller_request_id` field 6 and to the terminal's caller-ID field. The Python Client generates a unique, never-reused internal ID from its immutable Client/route generation nonce and monotonic `start_seq` before prepare, writes it into the canonical action request and hands that exact ID to its bound delivery host. The host registers it with the prospective operation/route context **before** sending `operation.commit_v1`; core checks the same ID during admission and installs request-local cleanup ownership before transport registration. The first Bind/Open/check may be accepted only after core and endpoint registration match that ID and the committed admission context; prepared-but-uncommitted IDs cannot emit frames. This is the accepted placement design's “existing request_id” for a v1 ticket, while `StartTicket.request_id` remains caller correlation only. The core mux validates registered request, operation, endpoint, session and stream IDs as specified by the accepted placement design. A delivery-only message cannot register a new request, authorize an endpoint, or create an operation. Registration survives user-visible completion until stream/check cleanup seals and drains. Distinct application operations can share one endpoint/pool and delivery host without sharing cancellation authority. Cancelling one operation seals only its request and leaves peer streams and pumps running.

The two lanes share fate only at a failed common carrier or explicit Client/runtime shutdown: both are notified, and neither fabricates application success or rollback from transport closure. An application handler that is blocked on Git I/O cannot prevent the transport lane from delivering the frame that unblocks it. Conversely, transport queue saturation cannot prevent application cancellation/close control from being scheduled. The host must either meet these progress conditions or refuse that placement before Git/credential effects.

## 4. Exact authority change and gates

Replace the first paragraph of placement design §4, which permits metadata attachment slots as the delivery mechanism, with this amendment's §1 delivery-only lane requirement. Retain its tag/type allocations, Bind/Bound context checks and bounded cleanup. Replace placement §4's host-pump paragraph with this amendment's §§2–3 independent queue, loop and failure rules. For new ticketed operations, replace placement §4's “Admission of a command registers its unique live request_id and caller-owned operation_id before binding or checks” and “The client host registers its live request_id before command dispatch” (the latter begins a sentence after “The” at line 206) with this amendment's §3 generated `RequestMeta.request_id`, host handoff before commit and two-sided context registration. Version-0 request IDs retain their old meaning; no frame may create a registration.

The accepted operator clarification says: “The current gate must prove that the shared transport envelopes fit and travel inside the existing Taut request/response messages, using the existing request IDs, while ordinary operation calls remain intact.” Replace that sentence with: **The in-process gate must prove that `GwzTransportDeliveryV1` carries shared Envelopes and registered transport request IDs through an independent Taut delivery lane while ordinary operation calls remain intact; optional request/response attachment fields retain their old additive compatibility meaning but do not drive delivery progress.** In accepted batch C, replace “Prove in-process embedding in the existing CLI/core and gwz-py/core Taut messages” and “Exercise optional transport attachments with existing request IDs through both consumer bindings and the core candidate” with: **Prove in-process delivery-only Taut events through both CLI/core and gwz-py/core bindings, including when application dispatch is blocked or idle, and retain optional-attachment compatibility fixtures separately.** Other batch-C exclusions of physical wire, processes and iroh remain. This is an amendment to the **candidate host-delivery assumption**, not a production v0 service-method change. The paired embedding-guide update makes this proposed replacement visible to consumers; the Rust port gains the queue-selective methods above only when implementation passes its gate.

Design GO requires Consistency/Safety review of this exact amendment paired with the application ticket contract, and a docs-only Surface review of the proposed Python caller guide. Before activation, qualify the exact generated outer Taut delivery shape and additive old-reader behavior, then prove: both directions make progress during a blocked Git handler and with no application messages; two peer operations overlap; cancelling one application await leaves delivery live for the other; result/terminal release precedes late transport cleanup; Window/Cancel/Close progress under data saturation; a pump fails between dequeue and delivery; loop shutdown and route replacement fail streams without false final cleanup; and a stale envelope cannot attach to a new request. A physical wire protocol, separate processes and iroh remain deferred.
