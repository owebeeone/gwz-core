## 1. Findings

### [P2-1] A test is never defined relative to its target, so the probe's central transition is unreachable and its refusal loops without backoff

- **Location:** §4.4 lines 171-174 (the conclusive/inconclusive predicate), §4.5 line 191 (the test's "hi = N exactly (no decrease, timer doubles)"), §4.6 lines 232 and 251 (`PROBING -> STABLE: test refused, conclusive; T := min(2T, Tmax)`), §4.7 line 265 (an unfair test is re-armed with no change to `T`).
- **Root cause:** "conclusive" is defined once, as `hi(a) < N` (§4.4), and then used in §4.5/§4.6 for the fair probe, whose `hi` is exactly `N` by the quiet rule (its `S_hi` starts as the `N` Connected connections and nothing is ever removed, §4.3). Under the only definition given, a fair probe refusal is **inconclusive**, and §4.4 says an inconclusive test "is re-armed as soon as the key is quiet (§4.7), with no backoff". Separately, no precondition says a test start requires `Connected = N`; the test start is "allowed iff the test slot is free and the key is quiet" (§4.5), and §4.6's DISCOVERING tests "as soon as the key is quiet and a member is queued".
- **Violated invariant:** every state × input pair must be defined, deterministic, and the recovery grammar closed. The pair (PROBING, fair test refused) is defined twice with contradictory outcomes, and the edge labelled "test refused, conclusive" cannot fire.
- **Sequence:** STABLE at `N = 8`, 8 Connected, limit 8. `T` expires, member queued, key quiet → PROBING, test X at 9. `S_hi(X) = {8 Connected}`, `hi(X) = 8`. X is refused. §4.4: `8 >= 8` → inconclusive → `T` unchanged → "re-armed as soon as the key is quiet": X's connection is Gone (refused by the server, C4), the key is quiet at once, a member is queued → next test at once → refused → … Each refusal is one attempt of the carrier (§5.3), so members burn `R + 1` attempts at round-trip speed; §4.7's bound "refused tests at a steady limit … 6 in 31.5 s" is not delivered. Second consequence: in DISCOVERING with `Connected < N` (e.g. after a limit lifts, 3 of 8 in use), the first start is a "test" at concurrency ≤ `N`, succeeds trivially, `N := max(N, Connected) = N`, DISCOVERING again; with "ordinary starts are held while a test is in flight" (§4.5) every start becomes a serialised test: one setup in flight at a time until `Connected` reaches `N` — the throughput collapse OQ13(c) exists to avoid, one SSH login at a time.
- **Impact:** either a hot refusal loop that fails members by budget (reading §4.4 literally) or an undefined transition (reading §4.6); and a serialised climb whenever DISCOVERING is entered below `N`.
- **Required correction:** define the test by its target. (a) Precondition: a test start exists only when the key is quiet, `Connected = N`, a non-final-attempt member is queued, and the test slot is free; with `Connected < N` only ordinary starts are admitted (`Possible < N`), in parallel, as the confirmation already says ("fill up to k − 1 first"). (b) Verdict of a test `a` at target `N + 1`: `hi(a) < N` → Overload (as any attempt); `lo(a) = N` (every one of the `N` stayed Connected for the window, so `hi(a) = N` too) → **refused at `N + 1`**: `N` unchanged, `T := min(2T, Tmax)`, PROBING → STABLE; anything else (`lo(a) < N`: something left during the window) → unfair, re-armed, `T` unchanged. (c) Rename §4.6's edge accordingly and state that an ordinary attempt's refusal with `hi(a) >= N` is inconclusive while a *test's* refusal with `lo(a) = N` is the fair-refusal verdict. (d) Say the same for the confirming test at `k`: fair iff `lo = k − 1`.
- **Closure test:** L1: STABLE at 8, limit 8, 200 members, 60 s: assert refused tests at `t0 + 0.5, 1.5, 3.5, 7.5, 15.5, 31.5 s` then every 30 s, and no two tests closer than `T`; and the same key entered into DISCOVERING with 3 Connected and 20 queued: assert ordinary starts run in parallel up to 8 before the first test and that no start with `Connected < N` is recorded as a test by the spy.

### [P2-2] The Suspect confirmation cannot converge under concurrency: `k` is set from a window that counts the co-attempts, and "fill to `k − 1`" regenerates that overlap

- **Location:** §4.5 lines 201-206 (confirmation: `k = hi(a) + 1`; "if fewer than k − 1 are Connected, ordinary starts fill up to k − 1 first"; co-refusals "may lower k to the least hi + 1 among them"; the moot rule); §4.3 line 159 (`S_hi` adds every connection that enters Setting up during the window, nothing removed); §4.4 R3 line 180 ("every attempt starts with hi = 31"; "for a Suspect wave the first conclusive refusal opens a confirmation"); §10.2 case 2 line 436 (expects one test at exactly `k − 1 = 8` connected).
- **Root cause:** `k` is derived from `hi`, and `hi` counts every concurrent setup, so for a wave of `W` attempts `k = W` regardless of the server's limit `L`; the refused concurrency `k` is then unreachable (`L < k − 1`), and the fill that tries to reach it is itself a wave whose refusals have `hi ≈ k − 2`, lowering `k` by one per wave.
- **Violated invariant:** a conclusive Suspect must become an Overload within bounded attempts (D1, §4.7's bound "a Suspect's confirmation: 1 refused test"); no member fails while budget remains (§1).
- **Sequence:** SATURATED, `C = 32`, first wave of 32, limit 8, refusal is a reset (Suspect; this is the **only** SSH signal, F2). All 32 start in one pass: `hi = 31` for each (R3). First refusal: `31 < 32` conclusive → confirmation, `k = 32`, hold at 31 Possible. 8 succeed, 24 refused (co-refusals, all `hi = 31`, `k` stays 32), 24 requeued (attempt 1 used). Moot? `8 + 24 >= 32` → no. Connected = 8 < 31 → "fill up to 31": 23 ordinary starts in one pass, each with `hi = 8 + 22 = 30` → all refused → co-refusals (they started before the confirming test) → `k := 31`; attempt 2 used. Fill to 30: 22 starts, `hi = 29`, `k := 30`; attempt 3 used. Fill to 29: attempt 4 used; members fail with `Capacity`. `N` never moved; the confirming test never started; the design's case 2 ("one test, then N = 8") is not what its own rules produce. **Second scenario, R9/§5.5:** a host outage with 32 members in flight: every refusal is Suspect with `hi >= 1` (the others are Setting up or Settling), so none reaches the retry machine (§4.8 routes only `hi = 0` there); the filter requeues with no wait (§5.1: "the retry machine is told abandoned: its 1 s backoff must not sit in front of a confirming test"), the fill re-admits them at once, and members burn `R + 1` attempts in about four connect round trips — well inside the 10 s outage §5.5 was written to survive. R9's "refusals at hi >= 1 lower N toward 1" presumes Overloads, which a Suspect never yields here.
- **Impact:** every member of a wave above a Suspect limit fails by budget without the limit being learned; a short outage at concurrency fails every member in flight in about a second, defeating §5.5.
- **Required correction:** set the confirmation's target from what the server can have held, not from the wave: `k := min(hi(a) + 1, Connected_at_refusal + 1)`, lowered further by co-refusals to the least such value; and make the confirming test the **first start after the wave resolves** with precondition `Connected = k − 1` and quiet (P2-1's test definition), with no fill wave: ordinary starts fill one at a time (`Possible < k − 1` admits one; the next after its result) until `Connected = k − 1`, so each fill attempt has `hi = Connected` and a refusal among them is itself conclusive at a lower `k`. State that a refusal with `hi(a) = Connected` (no other setup in flight) at `hi >= 1` is the Suspect's confirmation when a confirmation is already open at `k > hi + 1`. Re-derive case 2 and the R9 scenario from the corrected rules and assert the attempt count per member (≤ 3 in case 2).
- **Closure test:** L1 and L2: first wave 32, limit 8, reset refusals: all 32 members succeed; exactly one confirming test; `N = 8` after it; no member uses more than 3 attempts. L1: `outage(t1, t1 + 5 s)` with 32 members in flight: assert no member spends more than 2 attempts before its first retry-machine wait, and members whose budget allows it succeed after `t1 + 5 s`.

### [P2-3] A confirmation whose target becomes unreachable holds the test slot forever: a stuck state that caps the key for the command

- **Location:** §4.5 lines 201-209 (the confirmation holds the test slot; its only exits are refused/succeeded/re-armed/moot); §4.6 line 231 (`STABLE -> PROBING` needs the test slot, via §4.5 "the test slot is free"); §4.6 line 244 (an Overload during a pending test goes to STABLE but says nothing about a pending confirmation).
- **Root cause:** the moot rule compares `k` against connections-plus-queued-members, not against the admission target `N`; when `N` falls below `k − 1` after the confirmation opened, the confirmation is neither moot nor reachable.
- **Violated invariant:** fail-closed direction — "never permanently cap a key on a transient cause"; closed recovery grammar — every held resource (the test slot) has a bounded release.
- **Sequence:** SATURATED, `C = 32`, 10 attempts in flight. A reset refusal with `hi = 9` → confirmation, `k = 10`, hold at 9. A co-attempt (started before) gets a 429 with `hi = 9 < 32` → conclusive Throttle → Overload → `N := Connected = 6`, STABLE, `T := T0`. The confirmation remains: it needs `Connected = 9`, admission allows `Possible < 6`; moot check `6 + 20 >= 10` → not moot. The test slot is held. `T` expires repeatedly; `STABLE -> PROBING` requires the slot → never. `N = 6` for the rest of the command although the server lifted at once. The same arises when `k` is lowered below … no: only when `N` falls below `k − 1`, i.e. on any Overload (Throttle, or another confirmation's result) while a confirmation is pending, and on the §5.5 outage path.
- **Impact:** a permanent cap at a value set by one transient signal, exactly what the operator's direction rules out; no diagnostic, since the note prints only on Overload.
- **Required correction:** an Overload closes every pending confirmation (its question is answered: the limit is at most `N`), releasing the test slot; and the moot rule becomes "moot when `k − 1 > N`, or when connections plus queued members are fewer than `k`". Add the pair (confirmation pending, Overload) to §4.6's "every state also takes these".
- **Closure test:** L1: the sequence above; assert the test slot is free after the Overload, `STABLE -> PROBING` fires at `t + T0`, and `N` climbs back to `C` once the limit lifts. A spy asserts no confirmation outlives an Overload.

### [P2-4] The pool cap set to `N` refuses the `N + 1` test: the probe is served by eviction (always unfair) or times out

- **Location:** §4.5 line 193 ("The pool's per-host cap is set to N (§4.9)"); §4.9 line 297 (`set_limit(key, n)`, "honoured in schedule() next to per_host and per_user_host and in idle eviction"); §8 line 405 ("the pool closes idle connections above N first"); §4.6 lines 223, 251 (PROBING: one test start at `N + 1`).
- **Root cause:** the pool's limit is set to the believed limit `N`, but the test is an `(N + 1)`-th connection; the pool creates nothing at the cap (C1) and instead evicts an idle connection for the waiting request (C2).
- **Violated invariant:** the machine's one test must be a real `(N + 1)`-th connection (D3: "`N + 1` is only the admission target of the one test start"); the pool must not decide the test's fairness.
- **Sequence:** STABLE, `N = 8`, pool limit 8, 7 leased + 1 idle (another identity). PROBING: the test's checkout enters the pool. Loop 1: no reusable idle of its identity. Loop 2: `total() = 8 >= 8` → no creation. Loop 3: host full → victim = the idle one → `Closing(Evicted)`. After `closed()` (and the settle hold, §4.5) the connection is created: the server sees 8, not 9. The test "succeeds" with `Connected = 8` → `N` unchanged → unfair → DISCOVERING → next test at once → same eviction → … a livelock in which every member start at the limit costs a close, a settle wait and a reconnect, and the limit is never tested. With 8 leased and 0 idle: no victim; the request waits in the pool until its allocation deadline (30 s, `clock.rs:19-21`) → `AllocationTimeout` → `Phase::Other` → `Return`: the carrier member **fails** with an allocation timeout, contradicting "testing alone can never fail a member" (§4.7). Note also that gwz-core's §5.2 "the allocation clock stops" cannot stop the pool's own `deadline` once the request is inside the pool.
- **Impact:** the probe never produces a fair result, or fails its carrier; the limit is never climbed after it lifts.
- **Required correction:** the pool's `set_limit` carries the **admission target**, not `N`: `N` normally, `N + 1` (or `k`) from the moment a test start is admitted until its result, set under the same lock as the test's admission; and the test's request must be marked so the pool neither reuses nor evicts for it ("no idle connection on the key is closed or evicted" (§4.5) must be a pool rule, since eviction is the pool's, C2, and idle expiry is the pool's clock, C6). State that the test's pool request is submitted only after the limit is raised, and lowered again on the test's result or abandonment.
- **Closure test:** L2 with the real `PoolMachine`: STABLE at 8 with 7 leased + 1 idle of another identity, probe due: assert the pool creates a 9th entry, no `Evicted` close during the test's window, the fixture's `max_seen = 9`; and with 8 leased + 0 idle: the 9th is created and no carrier sees `AllocationTimeout`.

### [P2-5] The settle hold turns one eviction into a cascade: the cited eviction guard releases as soon as the victim is disposed, while the held slot keeps the host full

- **Location:** §4.5 line 193 ("a slot freed by closed() is held for the settle time before schedule() may reuse it, so eviction cannot start the replacement inside the settle window"); §4.9 line 297 (`set_settle(key, ms)`, "the time a slot freed by closed() stays counted"); §2.5 line 79 (the cited eviction mechanics, `pool/allocation.rs:97-131`).
- **Root cause:** the guard that stops a waiting request from evicting twice is `pending.eviction.is_some_and(|victim| self.entries.contains_key(&victim))` (C2, `allocation.rs:98-101`); `closed()` removes the entry and calls `schedule()` at once (`lifecycle.rs:195-196`). With the slot still counted for `Ts`, the host is still full on that very `schedule()`, the guard no longer holds (the victim is gone), and loop 3 picks the next-oldest idle connection.
- **Violated invariant:** the pool's own invariant that one waiting request evicts at most one idle connection and then waits for its slot; §4.5's claim that the settle hold "cannot start the replacement inside the settle window" is true but at the cost of closing every idle connection on the host.
- **Sequence:** STABLE, `N = 8` (pool limit 8 with settle), 2 leased + 6 idle of identity A; a request of identity B arrives. Loop 2: full → no creation. Loop 3: evict `I1`. `Close` → dispose → `closed(I1)`: entry removed, slot held; `schedule()`: loop 2 full (held slot counted); loop 3: `eviction = I1` not in entries → proceed; full → evict `I2`. Each `closed()` repeats it: `I3 … I6` within `Ts` (cleanup is local, C4/§2.5: a socket shutdown). After `Ts`, six slots free and 6 settles later the request is served; the next five identity-A members reconnect from scratch (each a setup plus, at the limit, a settle). Under a throttle at `N` this is the steady state whenever identities mix (HTTPS scoped credentials, `HttpsScoped`, `mod.rs:140-145`; SSH explicit keys).
- **Impact:** throughput loss of the key's whole idle set per mixed-identity request at the limit, and, since each eviction is a close the server must settle, a burst of `Settling` that keeps the key non-quiet (P3-3) and feeds `hi` of every attempt in the window.
- **Required correction:** specify the pool change exactly: a slot freed by `closed()` becomes a **Settling entry** (or a per-key counted hold) that the eviction guard treats as the request's still-present victim, so a request with a Settling victim neither evicts again nor creates until the hold lapses; `next_deadline()` must include the hold's expiry so the driver wakes to schedule; and say how `can_install_capacity` (C6) treats Settling holds (ignore them, or the next operation waits ≤ `Ts`). Cite the guard at `allocation.rs:98-101` as the line the change touches.
- **Closure test:** a `PoolMachine` test: limit 8 with settle 250 ms, 2 leased + 6 idle of A, one request of B: assert exactly one `Evicted` close, the request becomes `Opening` at `closed + 250 ms`, and 5 idle entries survive; `next_deadline()` returns the hold's expiry.

### [P3-1] "Lost" is not an event the endpoints report, so the model's "server's limit ≥ Connected" premise fails for every idle connection the server has closed, and R7's bound is understated by the idle count

- **Location:** §2.5 line 80 ("A connection the server closes is reported through idle_closed"); §4.1 line 136-138 (Gone "lost by the server's own close … at once"; "All of them are counted by the server now, so the server's limit is at least Connected"); §4.4 R7 line 184 ("N can then be one too high until the loss is seen, which costs one refused attempt"); §4.9 line 298 and F10 line 497 (`idle_closed` listed among the events the endpoints already see).
- **Root cause:** nothing in gwz-core calls `idle_closed` (C3); idle sockets are not read; a server-side close of an idle connection is observed only when the connection is next leased and used, at which point it goes `Discarded → Closing → closed()` like a client close (C5), i.e. Settling, not Gone.
- **Violated invariant:** the window model's floor "limit ≥ Connected" (§4.1) and the premise that the reports the window needs exist (F10).
- **Sequence:** `N = 8`; the wave ends; 8 idle; the server closes all 8 idle keep-alive connections (GitHub does, after a short idle). `Connected = 8` still. Members arrive: each leases a dead idle connection (reuse first, C1), fails on use, `Discarded` → Settling for `Ts`. `N` does not fall on a close (§4.2). After each dead one settles, `Possible` frees a slot, an ordinary start is admitted at true concurrency 1…8 — fine — but if meanwhile the limit fell to 4, the first refusal has `hi = 7 < 8` → conclusive → `N := Connected`, which still counts the remaining dead idle ones. The direction is safe (dead ones occupy slots the client will not use, so live ≤ limit), but the cost is one refused attempt **per dead idle connection**, not one, and the L2 fixture's `server_close(conn, t)` (§10.1) has no production counterpart: L2 would pass on an event production never delivers.
- **Impact:** a false premise in the model and a wrong cost bound; L2 coverage that cannot represent production; §10.1's test spy cannot pin a report that does not exist.
- **Required correction:** state the fact (no idle-loss report exists; `idle_closed` is uncalled, C3), move "lost" out of the events "the endpoints already see", restate R7's conversely-clause as "per idle connection the server has closed, one refused attempt, observed at its next lease", and either (a) accept it, or (b) add to §4.9 that the hosts must poll idle sockets for EOF and report `idle_closed` (which also makes `Gone at once` true). L2 must then model loss either way the design chooses.
- **Closure test:** L2 with `server_close` of `d` idle connections and a limit that then falls: assert at most `d` extra refused attempts and that `N` never exceeds live + dead-idle at any step; and, if (b), a host test that an idle SSH and an idle HTTPS connection closed by the fixture are reported `idle_closed` within one step.

### [P3-2] The outage rollback restores the penultimate `N` when several Overloads happened, and is keyed to "leaves Healthy", which the retry machine's Cold start does not pass through

- **Location:** §5.5 point 4, line 366 ("records the N it had before the most recent Overload that has not been followed by a success, N_before … N := N_before and the limit machine is put in STABLE"); §10.2 case 27 line 464 ("N is restored to its value before the outage").
- **Root cause:** an outage at concurrency produces a run of Overloads (R9: "refusals at hi >= 1 lower N toward 1"), each lowering `N`; "the most recent Overload" names only the last one.
- **Violated invariant:** D8/OQ16: a decrease caused by an outage is rolled back.
- **Sequence:** SATURATED at 32; outage; Overload 1: `N := 20`; Overload 2 (as Possible shrinks): `N := 5`; Overload 3: `N := 1`; `hi = 0` → the retry machine leaves Healthy → `N_before` = the `N` before the most recent Overload = 5. The host returns; probe succeeds; `N := 5`, STABLE, `T0`. DISCOVERING climbs 5 → 32 at one setup per test (12 to 24 s of SSH logins, OQ14), the cost OQ16 says the rollback exists to avoid. Also: during the first wave the retry machine is Cold, not Healthy (`machine.rs:63-69`, C7), so "when the retry machine leaves Healthy" does not fire for an outage in the first wave; and `N_before = C` must land in SATURATED, not STABLE (§4.6: STABLE is `N < C`).
- **Impact:** throughput loss only (the climb), and a rule that reads differently from its test.
- **Required correction:** "`N_before` is the `N` before the **earliest** Overload of the unbroken run of Overloads not followed by a success"; "leaves Cold or Healthy"; "STABLE with `T := T0`, or SATURATED if `N_before = C`".
- **Closure test:** case 27 extended: three Overloads in the outage; assert the restored `N` equals the pre-outage value, and the same with the outage in the first wave (retry machine Cold).

### [P3-3] The probe has no priority over ordinary starts, so under continuous close-and-replace churn at `N` the key is never quiet and the timer never fires a test

- **Location:** §4.5 line 191 (test start "iff the test slot is free and the key is quiet: no other setup in flight, nothing Closing, nothing Settling"); §4.6 line 231 (`STABLE -> PROBING: T expires AND member queued AND key quiet`); §4.5 line 195 ("a member that needs a different identity's slot waits one close plus Ts").
- **Root cause:** between `T`'s expiry and the test's start nothing holds ordinary starts; every freed slot is taken by an ordinary start (`Possible < N`), and each close puts the key through Closing and Settling, so a key whose members discard or evict at every finish (mixed identities, `Discarded` releases, C5) has no quiet instant.
- **Violated invariant:** fail-closed direction: a limit that has lifted must be re-tested within `Tmax` (§4.7 "A command never goes longer between tests").
- **Sequence:** STABLE at `N = 8`, identities alternate A/B per member, each finish evicts one of the other identity (P2-5 aside): at every moment one connection is Closing or Settling and one setup is in flight. `T` expires; "key quiet" is false; the test waits; it stays false for the rest of the command. The limit lifted at `t + 1 s`; the key runs at 8 until the command ends.
- **Impact:** a transient limit holds for as long as the churn does; bounded by the command and by the churn, so throughput only.
- **Required correction:** once `T` has expired and a non-final member is queued, hold ordinary starts **except those needed to bring `Connected` to `N`** (so the deadlock "hold ordinary to get quiet, but need ordinary to reach `N`" is avoided), until the key is quiet and the test starts or no member remains; make that a named sub-state (PROBE PENDING) of STABLE so L1 can assert it.
- **Closure test:** L1: the churn script above with a limit that lifts at `t1`; assert a test starts within `T + Ts +` one setup time of `t1` and `N` climbs.

## 2. Invariant analysis

- **"Success ⇒ limit ≥ lo + 1; refusal ⇒ limit ≤ hi" (§4.3).** Sound as inequalities, given correct reports: `S_lo` only shrinks and `S_hi` only grows over the window, so the server's count at the unknown decision instant is bracketed. The success rule `N := max(N, Connected)` is at least as strong as `lo + 1` at the instant of success (R2 shown correct: a leaver drops out of `Connected` too). The gap is in the premises: `Connected` includes idle connections the server has silently closed (P3-1), and `Gone at once` for a server close is false in the code for idle connections (C3) and true only for refused setups (C4). Direction of the error: safe (never invents live capacity), cost understated.
- **Connection states (§4.1) as a description of what the server may count.** Complete for HTTPS and for SSH's post-authentication limit. For `MaxStartups` the design is right that Setting up is "maybe", and §4.10's `Ns` handles the pre-auth count once the banner is reported (F11). Two states the table does not name but the code has: (a) a setup refused after TCP connect is removed by `connected(Err)` with no Settling (C4): correct for a server-side drop (the server closed it), but a client-side abort of a connecting socket (`CancelConnect`/`AbortConnect`, `ssh_pool.rs:314-332`) also ends in `connected(Err(Cancelled))` and removal — a socket the client closed mid-handshake, which the server may still count: it should be Settling, not Gone; the design's R6 covers only the abandoned-job case. Bounded (one `hi` undercount per cancelled connect), noted here rather than filed since it only arises on cancellation or an allocation expiry, which §5.2 makes rare. (b) `Closing` in the pool includes `IdleExpired` on the pool's clock (C6), which the machine must see as a client close; §8's "the pool closes idle connections above N first" is the same event.
- **"Server's limit ≥ Connected at every instant" and `N := max(N, Connected)`.** True for live connections, false for dead idle ones (P3-1). The rule is still safe in the fail-closed sense: a dead idle connection occupies one of the `N` slots on the client side, so live never exceeds the limit through it; the cost is a refused attempt per dead connection when it is detected and its slot refills.
- **The machine (§4.6), state × input.** With P2-1's definition applied, every pair is defined: SATURATED × Overload → STABLE; SATURATED × refusal is always conclusive (`hi ≤ C − 1`), never inconclusive; STABLE × Overload → STABLE; STABLE × `T` expiry → PROBING only under the quiet gate (P3-3 for liveness); PROBING × {Overload (impossible for the test itself: `hi = N`; possible only for a pre-test attempt, which quiet excludes), fair refusal, success, unfair} defined; DISCOVERING × {success < C, success = C, Overload, unfair} defined. Without P2-1 the pair (PROBING, fair refusal) is contradictory. The confirmation lives outside the four states and has an open exit (P2-3). Cancellation is defined (dropped with the retry machines). No deadlock between "quiet" and "ordinary starts held" as written, because nothing holds ordinary starts before the test starts; the fix for P3-3 must keep it that way for the starts needed to reach `N`.
- **Evidence filter × retry machine (§4.5 × §5.5).** The two machines gate the same start (`decide()` and admission) and the design makes each a wait reason (§5.2); a test start must pass `decide()` too — implied, not stated; harmless. `abandoned` on a throttle requeue releases a Degraded probe (C7) so the next member starts at once: correct for a healthy-but-narrow key, and the reason P2-2's outage scenario burns budgets (no wait sits on the filter path). With P2-2 fixed (`N` reaches 1 after one confirmation), attempts serialise, `hi = 0` routes to the retry machine and its waits apply.
- **Ts and the pool (§4.5, §4.9, §2.5).** The settle hold is consistent with `closed()`'s precondition (`cleanup.sent || aborted`) and with `Closing` counted in totals; it is inconsistent with the eviction guard (P2-5) and silent on `can_install_capacity` and `next_deadline` (noted in P2-5). `idle_closed` freeing at once is correct in the pool and unreachable in production (C3).
- **TOCTOU between admission's `Possible` and the pool's `schedule()`.** Admission runs in the endpoint; the pool's state moves under its own mutex on the thread that releases or drives (C8); the endpoints see `connected`/`closed` only in the `PoolHost` step. The pool's cap is the backstop for the ordinary case, which is why P2-4 matters: once the pool's limit equals the admission target under one lock discipline, a lag in gwz-core's view can only under-admit. The design defers the ordering proof to the plan (F10); that is legitimate, but the plan should know that today the limit machine's inputs come from two lock domains (the endpoint's and the pool's) and that `start_closing` is visible to the host only as a dequeued `Close` action, after the fact.
- **Two keys on one host.** §4.1 says "the pool's per-host cap still spans both"; the SSH and HTTPS pools are separate `PoolMachine`s (`install_capacity_pair`, `capacity.rs:219`), each counting its own entries, so the two machines do not share a cap. Harmless inaccuracy; no finding.
- **`Ns` (§4.10) × `N`.** Admission requires both `Possible < N` and setups in flight `< Ns`; a pre-auth drop feeds `Ns` only. No conflict found; until F11 the fallback is conservative, as stated.
- **L1 determinism (§10.1) given F10.** A pure machine over an ordered event stream can express every rule once P2-1 names the sub-states (test pending, test in flight, confirmation pending) and P2-3 closes the confirmation's exits; the one thing L1 cannot pin is an event the production hosts never emit (P3-1).
