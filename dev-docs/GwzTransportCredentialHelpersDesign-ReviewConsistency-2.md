## 1. Findings

### [P2-1] §11's "codes stay `remote_rejected` where 1.0.17's are" is contradicted by M6 and M8, whose 1.0.17 codes were `remote_rejected`, so clone's documented quiet skip and fetch/push's codes change for those cases

- **Location:** §11, the codes table (M6 → `unsupported_operation`; M8 → `git_command_failed`) and the sentence "Codes stay `remote_rejected` where 1.0.17's are, so scripts keyed on them keep working"; §8 D19 ("Fetch and push give every failure but `missing_remote` the code `remote_rejected`"); N14; T17 (asserts `git_command_failed`).
- **Violated invariant:** the design's own stated parity principle for codes, and the release's rule (OD13): a deliberate difference from 1.0.17 that can break a working setup is covered by a cited decision or put to the operator. E3 (the remediation plan) decides codes only "where neither the existing codes nor the existing facts let a driver tell apart two outcomes" and keeps `remote_rejected` where 1.0.17's are; it does not cover these two departures, and no OQ poses them.
- **Evidence.** 1.0.17 for M6's case: a 401 naming no scheme libgit2 knows yields `GIT_EAUTH` "server requires authentication that we do not support" (`http.c:184-187`); fetch and push map it to `remote_rejected` (`handle_fetch.rs:432-435`; `push_member.rs:521-526`); clone recognizes it as an access refusal both by code (`transport.rs:740`) and by message (`:750`) → `remote_rejected` → a `private: true` member is skipped quietly (`apply.rs:55, 69-72`; `clone.md:65-70`). 1.0.17 for M8's case: git2 skips a non-UTF-8 value or a missing field (`cred.rs:483-486, 352-355`), the callback falls to its final `Auth` error (`transport_support.rs:275-279`), and the same three mappings give `remote_rejected`. Revision 2 gives M6 `unsupported_operation` and M8 `git_command_failed` on every operation, and §11 says "Every other outcome fails the member" on clone.
- **Reproduction:** `gwz clone` of a workspace with a `private: true` member on a server whose 401 offers only `Bearer` (or, on macOS/Linux, only `Negotiate`/`NTLM` with no `Basic`): 1.0.17 skips the member and the clone succeeds; revision 2 fails the member with M6 and the result is `Partial`/`Failed`. A fetch of such a member: 1.0.17 reports `RemoteRejected`; revision 2 reports `UnsupportedOperation`, so a script keyed on `remote_rejected` no longer matches.
- **Impact:** a parity break of documented clone behaviour and of fetch/push codes, contrary to the sentence that claims the opposite; T17 would pin the departure.
- **Required correction (either):** (i) M6 and M8 take `remote_rejected`, with the scheme names and `<cause>` carried in the message as now, and N14 says so (OQ5's allocation for M4/M10 is unaffected); or (ii) D19 and N14 state the two departures and the clone-skip consequence, and a new open question puts them to the operator. §11's principle sentence then reads "Codes stay `remote_rejected` wherever 1.0.17's were, M6 and M8 included" or names the exceptions.
- **Closure test:** T10(b) and T17 assert the chosen codes; T8(c) gains an M6 case (`private: true` member, `Bearer`-only 401) asserting the clone outcome the revision chooses.
