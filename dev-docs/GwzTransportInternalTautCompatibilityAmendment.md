# GWZ transport — internal Taut compatibility amendment

Date: 2026-09-24. Status: **DRAFT operator clarification for review; no implementation or activation**.

The operator confirmed that the `gwz-transport` Envelope messages are currently internal and have no other clients. This narrows only that Envelope protocol's compatibility scope of the accepted [sequenced requirements](GwzTransportSequencedStreamRequirements.md) and [design](GwzTransportSequencedStreamDesign.md) for the planned profile-3 implementation. It does not change message ordering, endpoint authority, Git behavior or the future-carrier boundary.

**C1 — Lockstep projections.** The `gwz-transport` Envelope schema and its generated Rust/Python projections may change together. The new implementation does not owe byte-for-byte compatibility with previously serialized *transport Envelopes* or acceptance by old generated *transport Envelope* readers. This waiver does not cover the outer GWZ request/response schema or ordinary-local old/new driver/core interoperation. Do not hand-edit generated code or create a shadow protocol.

**C2 — Functional regression.** While the current internal profile-1/2 paths remain in use, they must still perform their current operations correctly after regeneration. This is a functional regression gate, not a retained-reader or encoded-byte compatibility gate. A profile mismatch must still refuse before Git, credential or pool effects; a profile-3-only Bind must not silently downgrade. These are current-session safety rules, not a promise to support independently deployed old clients. Receiver-generation pinning, unsupported-capability refusal, malformed-message rejection and bounded-resource checks remain required. For the separate GWZ request/response boundary, remote transport requirements §5.1 G6, ordinary-local old/new driver/core fixtures, capability affinity and explicit-cli/old-core refusal before operation submission remain controlling.

**C3 — Field shape.** `Envelope.message_seq` remains optional at the Taut shape because bootstrap and current profile-1/2 messages do not carry a sequence value. The generator may encode its absent value as null; no legacy-reader qualification or wrapper solely to preserve old bytes is required. Profile-3 positive-stream frames must carry a positive sequence and pass current encoding, decoding and bounded-validation tests.

**Precedence.** For this profile-3 work, C1–C3 supersede [sequenced requirements](GwzTransportSequencedStreamRequirements.md) Q8's unchanged profile-1/2 *encodings* clause and [sequenced design](GwzTransportSequencedStreamDesign.md) §5's retained-reader/old-projection qualification. They also supersede the old-reader and old-byte gates in [placement design](GwzRemoteTransportPlacementDesign.md) §3 ("retained old readers", "wire compatibility is tested"), §6 ("old v1 serialized fixtures and retained Rust/Python decoders"), §8 (old/new combinations solely as tests of historical *transport Envelope* readers), and §9 ("preserves v1 wire meanings") **only where those clauses govern internal transport Envelope bytes as prerequisites for adding profile 3**. No part of this waiver applies to GWZ request/response encoding, ordinary-local old/new core/driver combinations, capability affinity or unsupported explicit-placement refusal. The historical placement acceptance and existing profile-1/2 functional semantics remain intact. No physical wire-carrier qualification is introduced.
