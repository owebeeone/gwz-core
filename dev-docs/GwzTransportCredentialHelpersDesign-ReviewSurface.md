## 1. Findings

### [P2-1] M2 and M3 send the user to git to store or update a credential that, in the most common GitHub setup, git neither holds nor can renew

- **Location.** M2: "gwz does not prompt: store a credential with git first, for example by running `git fetch` in this repository, then retry." M3: "gwz does not erase or replace stored credentials: update it with git, then retry."
- **Violated expectation.** A failure message's next action must work for the setups the notes themselves name. N8 names `gh auth setup-git`, which makes gh — not git, not a keychain — the holder of the credential for github.com (and, per `gh auth setup-git --help`, for every authenticated host). gh's helper answers `get` from gh's own login; the way to renew it is `gh auth login` or `gh auth refresh`. Git has no command that updates a credential a helper holds; the "update with git" route is only git re-prompting on the terminal after a rejection and handing the typed value to the helper's `store`, which a sign-in bridge such as gh's does not keep (gh's `store` is a no-op; verify against a revoked token). M3 does not even name a command.
- **Scenario.** Walkthrough case 2: a `gh auth setup-git` user whose token expired runs `gwz fetch`. gh returns the expired token, the server rejects it, the member fails with M3. The user does what M3 says and runs `git fetch` in the member: git asks gh, gets the same token, is rejected, prompts on the terminal, the user types a fresh PAT, the fetch works. `gwz fetch` again: gh still returns the expired token → M3 again. Nothing in M2/M3/N8 says `gh auth login`. The same loop holds for M2 when the user has never signed in to gh: `git fetch` works once, gwz never sees the typed credential.
- **Impact.** The most common GitHub HTTPS setup is sent round a loop by the shipped text; the message's confident "then retry" makes the user suspect gwz.
- **Required correction.** Rewrite the next action of M2 and M3 so it (a) names a concrete command for the storing helpers (`git fetch` / `git ls-remote <url>` in the member or at its URL), and (b) states that the credential is renewed **where it is held** — "if your helper is a sign-in tool (for example `gh`), sign in with that tool (`gh auth login`)". N8 should carry the same sentence for the upgrade reader.
- **Check.** Walk case 2 from the revised text alone and reach `gh auth login` without guessing; walk a GCM/osxkeychain user with a revoked PAT and reach a working command. Both commands must appear in the message or in a doc page the message names.

### [P2-2] The "no credential available" outcome cannot be told from M8 by §11's text, and M8 has no next action — so the CI / fresh-machine user lands on an opaque message

- **Location.** M2: "The server asked for HTTPS credentials, and no configured git credential helper returned one." M8: "`git credential fill` failed, or returned output gwz cannot use. No credential was sent." N4: "a helper that prompts on the terminal fails after the interaction allowance." Nothing in §11 says what gwz does with git's **own** prompting (terminal, `GIT_ASKPASS`), which is not a helper.
- **Violated expectation.** Each message must correspond to a condition a reader can recognise, and the common failure must carry the actionable text. By git's documented behaviour, `git credential fill` either returns a username and password or prompts; when no helper answers and no terminal is available or prompting is disabled, it **exits 128** with `fatal: could not read Username for '<url>'` (verified above). That is, "no configured git credential helper returned one" is never a success of `git credential fill`; on its face it is "`git credential fill` failed" — M8. §11 does not define how M2 is distinguished from M8, and does not state whether gwz disables git's terminal prompt (then every no-helper run is "terminal prompts disabled", exit 128) or leaves it enabled (then several parallel members write `Username for 'https://…':` prompts over each other on the user's terminal, and a run without a terminal fails as above).
- **Scenario.** Walkthrough case 4: a CI job with no helper, or a fresh Linux machine (no helper is configured by default) with a private HTTPS member. The member fails with "`git credential fill` failed, or returned output gwz cannot use. No credential was sent." The engineer reads this as a broken git or an incompatible gwz, checks `git --version`, reinstalls, searches the error text — and finds nothing, because the cause is simply that no credential is configured, and git's stderr line (the one that says so) is withheld under "They name no URL, host or helper output".
- **Impact.** The first-day failure with the simplest cause lands on the one message with no cause and no next action; the well-written M2 is unreachable or reachable only by an unstated rule.
- **Required correction.** (a) Define in §11 that git's "could not read Username/Password" outcome — no helper answered and prompting is unavailable or disabled — **is M2**, however `git credential fill` reports it. (b) State the prompting policy in the notes: whether gwz runs `git credential fill` with terminal/askpass prompting disabled, and what a user with no helper and a terminal sees. (c) Give M8 a cause class and a next action (see also P3-7), and say where git's own error can be seen without the credential (for example under `--verbose`, if that is where it goes).
- **Check.** Run a private HTTPS member with no helper, no terminal: the member error is M2, not M8. The notes answer "I have no helper and a terminal — what happens?" in one sentence.

### [P2-3] M2–M8 carry no stated machine code, so a script or gwz-py caller cannot tell "sign in" from "retry" from "install git" without parsing message text — and allocating codes later is a compatibility break

- **Location.** "**M1** (`external_tool_missing`)" is the only message given a code. "The `--verbose` row and JSON keep their fields; `credential=helper` already shows the method." "They replace 'HTTPS endpoint request failed: <code>' for these outcomes".
- **Violated expectation.** The error catalog is the stable protocol enum (`GwzErrorCode`), and its own text records the project standard that outcomes a driver "could not tell from" one another get codes (the Local Clone Family sections allocate codes exactly for that reason). The catalog has no code for a missing, rejected or timed-out credential; `remote_rejected` is documented as "Remote rejected push/tag push/delete", `permission_denied` as "Reserved for filesystem/authorization denial". Whatever existing code M2–M8 inherit, seven outcomes with four different recoveries (configure a credential; renew it; wait or retry; nothing you can do here) share it.
- **Scenario.** A gwz-py application (README: `GwzOperationError.member_errors`, each with `code`) or a `--json` CI script needs to decide whether to prompt the operator to sign in, retry after a timeout, or fail the build with "install git". It can key on `ExternalToolMissing` for M1 only; for M2–M8 it must match English sentences that §11 may still reword. If 1.1.1 later allocates `credential_missing`/`credential_rejected`, every consumer keyed on the 1.1.0 code for those outcomes breaks — the compatibility break the axis rule names.
- **Impact.** Diagnosability defect at the JSON/Python boundary, frozen by release.
- **Required correction.** State in §11 the code each of M2–M8 carries, in both spellings (`snake_case` catalog row, PascalCase JSON). Allocate distinct codes where the recovery differs — at minimum: credential missing (M2, M7), credential rejected (M3), helper timed out (M4), request refused by gwz policy (M5, M6), helper/protocol failure (M8) — and add or amend the ErrorCatalog rows (row 32's "Reserved for missing external tooling" must become the real cause and recovery).
- **Check.** `gwz --json fetch` against the five scenarios of §2 yields a documented, distinct `code` per recovery; the catalog table lists each; gwz-py's `member_errors[i].code` matches.

### [P2-4] N3 says `git` runs in `/`, which by git's documented configuration discovery drops repository-local and `includeIf "gitdir:"` credential configuration — and then M2's next action loops

- **Location.** N3: "A helper named by a relative path no longer starts, since `git` runs in `/` (D4–D6, D8)." N2: "git chooses the helpers, from the configuration git itself reads, its own system file and `GIT_CONFIG_*` included."
- **Violated expectation.** A release note that reveals a mechanism must state its user-visible consequences, not one of them. Git reads the repository's `.git/config` only when run inside (or pointed at) that repository, and `includeIf "gitdir:…"` includes match only against a discovered repository. A `git credential fill` run in `/` therefore reads system and global configuration only. N2's "the configuration git itself reads" is true but misleading: it is not the configuration git reads **in that repository**, which is what every user means by "my git config". N3 names only the relative-path-helper consequence.
- **Scenario.** A developer keeps work credentials behind `[includeIf "gitdir:~/work/"] path = ~/.gitconfig-work` (the standard work/personal split), or sets `credential.helper`/`credential.username`/`credential.useHttpPath` in a member's `.git/config`. After upgrading, `gwz fetch` fails that member with M2 ("no configured git credential helper returned one"). The user, who did configure one, follows M2: `git fetch` in the member succeeds — git-in-the-repository reads the include — and stores the credential in the work helper. `gwz fetch` again: M2 again, because gwz's `git` never sees that helper. The text gives no way out and no hint that the scope is the problem.
- **Impact.** A common configuration pattern is broken on upgrade with a message whose next action confirms the user's config is fine, then fails again — a wrong path. If the design in fact does pass the repository's configuration, N3's sentence is wrong as written and misleads the same reader (then P3).
- **Required correction.** State exactly which git configuration scopes the lookup reads (system, global, `GIT_CONFIG_*`, repository-local, conditional includes) and, for any scope it does not read, say so and give the remedy (move the setting to the global file or `GIT_CONFIG_*`, or the off switch). M2 should name "a helper in your global git configuration" if that is the rule.
- **Check.** Walk the includeIf user from the revised N3 and M2 alone to a working configuration without guessing; the note contains the word "repository-local" (or equivalent) and a verdict on it.

### [P3-2] M4 names a bound the user can neither find nor change, blames "the git credential helper" when it may be git's own prompt or several helpers, and gives no next action

## 2. First-day walkthrough

From §11's text alone, plus the existing docs. "Guess" marks a point the text does not settle.

1. **`gh auth setup-git` user fetches a private GitHub repo.** N8 says gh runs because git's configuration names it; N1 says git must be on PATH (a gh user has it). The fetch succeeds; `--verbose` shows the helper row. Guesses: none, unless the user's gh configuration lives in a repository-local or `includeIf` scope (P2-4), in which case M2 appears and the user cannot tell why.
2. **Same user, expired gh token.** gh returns the stale token; the server rejects it; the member fails with M3 and, per N6, is not re-asked in that run. M3 says "update it with git": `git fetch` works once (git prompts, the typed PAT is used) and gwz fails again with M3 on the next run. Guesses: that the fix is `gh auth login`/`gh auth refresh` (P2-1); whether gwz would have re-asked (N6 says no — but the message does not).
