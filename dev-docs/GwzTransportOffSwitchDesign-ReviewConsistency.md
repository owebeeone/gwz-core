## 1. Findings

### [P2-1] §2's configuration-file rule contradicts the libgit2 source it cites, and the server design's reading of that source, for a set-but-empty `XDG_CONFIG_HOME` (and is silent where libgit2 ignores the environment)

- **Location.** §2, "The configuration files", first bullet: "`$XDG_CONFIG_HOME/git/config`, or `$HOME/.config/git/config` when that variable is unset **or empty**; then `$HOME/.gitconfig`, whose value wins. These are the files `git config --global` reads and writes, in libgit2's order (`libgit2/src/libgit2/sysdir.c:324-420`)". Also §2's fourth bullet, "gwz's global configuration is libgit2's (server design §5, the exclusion table)", and the second bullet, "A relative `HOME` or `XDG_CONFIG_HOME` names no file."
- **Root cause.** The draft applied the "empty is the same as unset" convention it takes from `GWZ_URL_SCHEME` and `GWZ_SERVER` to `XDG_CONFIG_HOME`. That is git's convention (`git config` treats an empty `XDG_CONFIG_HOME` as unset), not libgit2's.
- **Evidence.** `sysdir.c` at `b172e3d1`, lines 401–406:
  ```c
  if (uid == euid) {
      if ((error = git__getenv(&env, "XDG_CONFIG_HOME")) == 0)
          error = git_str_joinpath(out, env.ptr, "git");
      if (error == GIT_ENOTFOUND && (error = git__getenv(&env, "HOME")) == 0)
          error = git_str_joinpath(out, env.ptr, ".config/git");
  }
  ```
  `git__getenv` returns 0 for a set-but-empty value, so libgit2's XDG directory becomes the relative path `git`; only an unset variable (`GIT_ENOTFOUND`) falls through to `HOME`. The server design states exactly this at its line 1434 ("`XDG_CONFIG_HOME is set but empty, which libgit2 reads as the relative path git`"), and the session plan's CS8.1 test row refuses an empty `XDG_CONFIG_HOME` at open on that ground. Further, lines 356–359 and 407–410: with `uid != euid`, or on macOS with `APP_SANDBOX_CONTAINER_ID` set, libgit2 ignores `HOME` and `XDG_CONFIG_HOME` and reads the passwd home; the draft's "found from the snapshot's variables, never the process's" does not say what the resolver does in those cases, and neither does §9.
- **Violated invariant.** The draft's own parity claim for the key's location (§2: "These are the files … in libgit2's order"; "gwz's global configuration is libgit2's"), and the review rule that a citation must say what the draft claims. Under the draft's own "a relative value names no file", libgit2's reading of an empty `XDG_CONFIG_HOME` would name no XDG file; the draft instead reads `$HOME/.config/git/config`.
- **Reproduction.** `XDG_CONFIG_HOME= HOME=/home/u gwz fetch`, with `gwz.transport = off` in `/home/u/.config/git/config` and no `~/.gitconfig`. The draft's resolver turns the switch on. In the same process, libgit2's own reader of "the user's global configuration" — the native credential callback's `git2::Config::open_default()` at `transport_support.rs:267`, which the draft itself cites in §1 as the one user-level configuration gwz reads — looks for `./git/config` relative to the working directory and never sees that file. Two readers of one notion disagree, and §9's file rows ("a relative `HOME` reads no file") do not exercise the case, so either implementation passes.
- **Impact.** A parity defect in the one form whose location this design defines by parity with libgit2; a documented message to users ("your global git configuration") that is not what libgit2 reads for them; and a 1.1.0 behaviour that the 1.2.0 server refuses at open (CS8.1), so the two releases disagree on the same input. Blast radius is small (an empty `XDG_CONFIG_HOME` is rare), which is why this is a text-bounded P2 and not higher.
- **Required correction.** Choose and state one of: (a) follow libgit2 exactly — a set-but-empty `XDG_CONFIG_HOME` is the relative path `git` and, by the draft's relative rule, names no file, with no fallback to `HOME`; and state the `uid != euid` / `APP_SANDBOX_CONTAINER_ID` rule (refuse, or read the snapshot regardless as a stated departure); or (b) keep git's rule and say in §2 that it departs from libgit2 for an empty `XDG_CONFIG_HOME`, naming the credential callback's divergent read. Either way, say what an empty `HOME` does (the server design treats "set but empty" as relative), and correct the parity sentence so it claims only what the cited code does.
- **Closure / regression test.** §9's gwz-core file rows gain: an empty `XDG_CONFIG_HOME` with `off` in `$HOME/.config/git/config` yields the chosen outcome; an empty `HOME` yields the chosen outcome; and, under (a), a `uid != euid` or sandbox-ID row. The citation `sysdir.c:324-420` is re-read against the revised text.

### [P3-2] §3 "The scan never fails a request" contradicts §4 for the ignored-value warning under Python's `error` filter

- **Location.** §3, last sub-bullet: "A file the scan cannot read gets no note. The scan never fails a request." §4, gwz-py: "A filter that turns it into an error makes that `call` or `submit` raise it, before any effect" and "§3's notes are warnings of the same kind."
- **Evidence and sequence.** `warnings.simplefilter("error")`; a `Client` whose workspace root holds `gwz.transport = off` in its own `config`; a `fetch`. By §4 the ignored-value note is issued through `warnings` at the native entry; under `error` it is raised, and `call`/`submit` propagate it — the request fails before any effect. §3 says the scan never fails a request. §9's gwz-py rows test the `error` filter for the switch-on warning only ("under `error`, `call` and `submit` raise it before any effect"); the ignored-value row ("a repository value gives one warning naming its scope") runs under the default filter.
- **Violated invariant.** Internal coherence between §3 and §4; a test section that covers each stated behaviour.
- **Consequence.** An implementer reading §3 may swallow the `PyErr` from the ignored-value warning (so the user's `error` filter is silently ineffective for one of the two warnings), or honour it (so §3's sentence is false). Either way one document sentence is wrong and no test says which.
- **Required correction.** Qualify §3: the scan's own failures (unreadable file, missing workspace) never fail a request; a warning filter the caller sets applies to its notes as to §4's. Add a §9 row: under `error`, a repository value makes `call` and `submit` raise before any effect.
- **Closure.** The added row.
