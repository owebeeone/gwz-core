## 1. The owner, in one paragraph

One helper child runs under one `Runner` (`runner.rs`), started by `process_tree::spawn` into a process tree the owner holds as a `ProcessTree`. A `HelperJob` (`owner.rs`) holds the child, the tree and the two admission permits (the host's helper slot and the endpoint's slot) from spawn to retirement. Success, failure, timeout, cancellation and a dropped future end in one of three states: **retired** (on success: the leader has exited, the tree is let go of, the permits are released, and what the helper left running is left running); **cleaned up** (on failure, timeout or cancel: the tree has been ended and is empty, the leader waited for, the permits released); **retained** (the `AuthOwner` keeps child, tree and permits until `reap_pending` or `reap_ready` finds the leader gone and the tree empty, ending any member that is still alive); or owner dropped (the retained children go with it). The interface is the same on both platforms; only `process_tree.rs` has two arms.

## 3. Timeouts and cancellation

Unchanged from Unix, and the Windows arm adds no clock. The lookup has an allocation allowance (waiting for a host slot), a single interaction deadline from the helper's start, and the caller's `CancellationToken` plus the owner's own. `Runner::check` is the one place that turns an expired deadline into `Timeout` and a cancelled token into `Cancelled`; success is admitted only if it still holds at the end, while the job still owns its tree (`finish_job`). Draining polls every `DRAIN_POLL` (2 ms) and a wait for the leader's exit every 2 ms, inside the existing `CLEANUP_GRACE`; neither is a new deadline for the caller. A cancel or deadline before spawn starts no process. A tree that does not drain within the grace on a failure path is reported `CleanupPending` and stays charged to capacity; on the success path nothing is waited for (C8).

## 4. Pipes and framing

Unchanged from Unix. Stdin: the request is written then the pipe is closed; a broken pipe is not a failure (Git ignores `SIGPIPE`; a helper may answer without reading), any other write error is `Pipe(kind)`. Stdout: at most `OUTPUT_LIMIT` (16 KiB) plus one probe byte; one more byte is `OutputTooLarge` and ends the tree. Stderr: drained and discarded without bound (a 40,000-byte flood does not reject the answer). The three run concurrently with the wait. Output is CRLF-tolerant by the existing parser (one trailing CR).

**OQ-C (decision: accept, recorded).** On Windows the bytes pass through the completion-port pipes' internal buffers (mio), which are not ours and are freed without wiping; the Unix path has no such copy. Sizes, for TR1.8 §4's dependency-copies list: reads fill pooled 4 KiB buffers (at most two are kept for reuse, the rest freed), so a copy of the answer, **password included**, sits in up to 16 KiB of them for the lookup's life (`OUTPUT_LIMIT`); a write copies the whole slice it is given into a buffer of that size (gwz sends `url=...` only, no secret); stderr is a 4 KiB scratch of diagnostics. Every pending call owns its buffer until it completes or is cancelled.

**OQ-C, the environment (added 2026-10-16 for review finding State P3-3).** The configuration view, which can carry a credential (`http.extraHeader`), reaches the child through `GIT_CONFIG_PARAMETERS`. The owner builds that value, and every other value of the child's environment, once, at its final size, in a wiping owner (`wiped.rs`, `process_tree/environment.rs`'s `EnvValue`): bytes on Unix, UTF-16 on Windows, with no `String`, `OsString` or growing `Vec` between the view and the child. The owners move from the runner's `Environment` into the `HelperCommand` and are overwritten when the command drops, which the runner does as soon as the spawn returns. On Windows the block `CreateProcessW` takes is one such owner of exactly its size, built straight from the values' owners (`environment_block`), so no per-entry copy exists. Tests: `the_configuration_view_is_held_in_a_wiping_owner_until_the_environment_drops` (both platforms) and `the_environment_block_is_one_wiping_owner_of_exactly_its_size` (Windows), whose audit probes record each owner's length and that it was all zero when it dropped. Accepted copies, which are not ours to wipe, for TR1.8 §4's list:
- **Unix, std's `Command`.** The spawn gives `Command::envs` each value, and std keeps one copy in its environment map (an `OsString`) and builds a second at spawn (the NUL-terminated `envp` string), both freed without wiping when the spawn returns. That is two copies of the view, each as long as the view (at most the view's `PREPARATION_LIMIT`, 4 MiB), and they last from the call of `envs` to the return of `spawn`. The alternatives cost more than they save: a `pre_exec` hook cannot allocate between `fork` and `exec` in a multi-threaded process, and moving the view to argv or a file puts it where other users can read it.
- **The kernel.** Each platform copies the environment into the child's own address space; that is the child's.

## 5. Environment

The child's environment is exactly the captured snapshot (`Config.environment`) minus `GIT_ASKPASS`, `SSH_ASKPASS`, `GIT_DIR`, `GIT_COMMON_DIR` and `GIT_WORK_TREE`, plus `GIT_TERMINAL_PROMPT=0`; with a configuration view, also minus every `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_*` and `GIT_CONFIG_VALUE_*`, `GIT_CONFIG_SYSTEM` removed, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL` set to the platform's null source (`/dev/null`; `NUL` on Windows) and `GIT_CONFIG_PARAMETERS` set to the view. It is built as an explicit list (`Environment` in `runner/environment.rs`), whose values are in wiping owners (OQ-C, the environment), which both platforms hand to the spawn. Nothing is read from the process environment.

- **Names compare as the platform compares them.** On Windows without regard to ASCII case: `Git_AskPass` is `GIT_ASKPASS`, and a filter that missed it would hand an ask-pass program to the helper. Prefix tests compare the encoded bytes, so a name that is not Unicode (a lone surrogate) still starts with an ASCII prefix. Tests: `askpass_is_never_in_the_helpers_environment`; the unit tests of `names`, `starts_with` (with the lone-surrogate row), `set`, `remove_prefix`.
- **Working directory.** Unix: `/`. Windows: the Windows directory as the operating system names it (`GetWindowsDirectoryW`), not the caller's snapshot (**OQ-E, decided**: the review found `SystemRoot` caller-controlled). Its parent is a drive root where any user may create a folder, so the owner sets `GIT_CEILING_DIRECTORIES` to that parent and Git does not search upward into it. Spike S4: with a planted `.git/config` above the working directory, `git config` read the planted `credential.helper` without the ceiling and found no repository with it. Spike S5 repeats it at a drive root, with a `subst` drive standing in for `C:\` and the ceiling `confine()` computes (`Z:\`): Git for Windows 2.55.0.windows.3 read the planted helper without it and nothing with it. **Step 4.3 records the Git version tested** (no minimum is enforced, operator 2026-10-11); 2.55.0.windows.3 is the one verified, and the Git for Windows that gwz ships or requires must be tested the same way before the ceiling is relied on.
- **The view is UTF-8 on Windows** and becomes a UTF-16 value without replacement; bytes that are not UTF-8 are `ConfigurationRefused` (`a_view_that_the_environment_cannot_carry_is_refused_rather_than_converted`). The environment block is sorted by name without regard to case, as `CreateProcessW` expects, and refuses a NUL, an empty name, and an `=` after the name's first unit: a name may start with `=` (the hidden per-drive variables such as `=C:`), as `EnvironmentSnapshot::checked` accepts (`an_environment_block_keeps_a_drive_variable_and_refuses_an_equals_after_the_first_unit`; `a_helper_started_with_a_drive_variable_in_its_snapshot_sees_it`).
- **No size refusal on Windows.** On Unix an over-long environment value fails the spawn (`E2BIG`) and is reported as `ConfigurationRefused`. On dabeest `CreateProcess` accepted a 4 MiB `GIT_CONFIG_PARAMETERS`, so the Windows bound is the view's own `PREPARATION_LIMIT` (4 MiB) and nothing at spawn (**OQ-G**).
- **Command line.** The executable is an absolute path passed as the exact application name, quoted; each argument is quoted the way `CommandLineToArgvW` reads it back (`arguments_are_quoted_the_way_the_command_line_parser_reads_them_back`). A relative program is refused. The test fakes are `.cmd` files run as `cmd.exe /d /c script`; the extension rule for production executables is 4.3's.
- **Creation flags**: `CREATE_NO_WINDOW | CREATE_UNICODE_ENVIRONMENT | EXTENDED_STARTUPINFO_PRESENT` (**OQ-D**).

## 6. Decisions and open questions

Decided by the operator on 2026-10-10:

- **OQ-A, release on success.** On success the job's `KILL_ON_JOB_CLOSE` is cleared and the job closed; survivors live on, as on Unix, under Git and in 1.0.17. Timeout, cancel and gwz's exit kill the whole tree. The reviews' blind convergence (Code F2, Safety F1) was the Git Credential Manager browser flow: a browser that GCM starts must not die with the lookup. Spike S1 shows a descendant of a `!sh` helper stays in the job after git exits (so the kill paths reach it) and S2b that a classic process started through the shell does too; S2 shows a packaged app is outside the job and so survives under any policy.
- **OQ-B, a private `CreateProcessW`.** `JOB_LIST` plus `HANDLE_LIST` (C1, C9). The create-suspended, assign, resume sequence and its window are gone.

Recorded and not reopened (the reviews agreed):

- **OQ-C**: accept the copies (section 4).
- **OQ-D**: keep `CREATE_NO_WINDOW` and die-on-unhandled-exception. Spike S3: under `CREATE_NO_WINDOW` a `!sh` helper's `powershell` descendant reported no console window and six processes on one console (git, sh, powershell and their hosts): no console is allocated per descendant. A real flash can only be seen from an interactive desktop, which dabeest's SSH logon does not have.
- **OQ-E**: the Windows directory from the OS, plus the ceiling (section 5).
- **OQ-F**: a job that cannot be created in, or a creation the system refuses, refuses the helper (`SpawnFailed`), never runs it uncontained. A refusal cannot be produced on dabeest; `a_creation_that_fails_after_the_job_exists_runs_nothing` injects one (a handle that is not a job).
- **OQ-G**: no spawn-time size bound (section 5).

Decided by the operator on 2026-10-16:

- **OQ-H, the spawn gate (operator decision D25, 2026-10-16). Partly discharged.** D25 reads: "Build it before S7.1. The gate in the host context serializes a std spawn with an inheritance window (WH2 helper launch, gwz-sspi worker launch); gwz-core's std spawn sites on transport paths go through it, including the call into libgit2's `Cred::credential_helper` (`gitbackend/transport_support.rs`), which is added to C9. git2-rs is not changed." Built: the gate, the WH2 helper launch's window, and gwz-core's std spawn sites on transport paths, libgit2's `Cred::credential_helper` included (C9). **Not built: the gwz-sspi worker launch's window.** gwz-sspi launches its worker on its own driver thread and 0.1.1 gives the host no seam to hold the gate around it. It needs an operator ruling between two routes: coarse gating of the whole `Supervisor::start` future (unsound if the future is dropped while the launch goes on, and it blocks every gated spawn of the host for up to the start deadline), or an additive gwz-sspi 0.1.2 launch guard in `Options` that the host fills with `SpawnGate::hold`, with a second move of the pins (and a host-level gate that the CLI makes before it makes the `Supervisor`). **S7.1 waits on that ruling**, because D25 is a precondition of S7.1 and one of the two windows it names is open.

Open after the gate, each for the operator:

- **`gwz log`'s `git rev-list`** (`operation/commit_log/mod.rs:320`) is not gated (C9 gives the reason). Gating it takes a gate parameter on `open_default_head_histories`, which is public, and on `handle_log`.
- **gwz-sspi's worker launch** needs a launch guard in gwz-sspi's `Options` for the host to hold the gate around it; gwz-sspi is unchanged here.
- **A process-wide host.** The gate is per host, and a driver entry is a host (C9, scope). Two operations of one gwz-py process do not exclude each other until the entries take a shared host context.
- **The credential helper holds the gate as long as the user takes.** That is what holding git2-rs's call whole means (D25). The alternative is gwz-core's own `git credential fill` through `SpawnGate::output`, which holds the gate for the spawn alone; it is the debt the process-globals allowlist already records for that site.

## 7. Step 4.3's addendum: the path half (implemented)

Step 4.3 brings `executable`, `view`, `file_worker` and `lookup` to Windows (`lookup_until` waits for 4.4's admission and `lookup_setup`, SSH's password route, is 4.5's). What it decides, each with its tests in `https_auth/` (`executable::tests`, `view/path_tests.rs`, `view/paths.rs`, `view/tests.rs`, `runner/ceiling_tests.rs`):

- **Discovery.** A bare name is searched in the absolute directories of the captured `PATH`, whose key is found without regard to ASCII case on Windows (`Path`, `path`). A relative, drive-relative, root-relative or empty entry is skipped, so the current directory is never searched. The program is an `.exe` and nothing else: `git` is looked for as `git.exe`, `git.exe` and `GIT.EXE` as they stand, and a name with any other extension (`git.cmd`, `git.bat`, `git.com`, `git.ps1`, `git.exe.txt`) or a trailing dot is missing; there is no `PATHEXT`. An absolute `executable` must also be an `.exe` (a script is refused, not run through a shell). A name that is not found is `MissingExecutable`, which the product already reports as no `git` with the `GWZ_TRANSPORT=native` hint (`https_failure.rs`). A quoted entry with a separator in its name (`"C:\a;b"`) is read as the Windows loader reads it.
- **Paths are text on Windows.** What Git writes for a path, in `--show-origin` and in an `include.path` value, is UTF-8. The view turns it into a path through `str` (never `to_string_lossy`) and back the same way, so non-ASCII and spaced names survive, and **bytes that are not UTF-8, or a path with a lone surrogate (a legal Windows name), are `ConfigurationRefused`**. The environment values it builds are already UTF-16 (`parameters_value`, section 5).
- **Anchors.** Git writes its paths with forward slashes; the view joins a relative include to its file's directory with one `/` (an existing `/` or `\` is not doubled). A value with a root and no drive (`\x`, `/x`) or a drive and no root (`C:x`) depends on the current drive or directory, which Git decides and the view does not know, so it is refused. A UNC path is absolute. An origin with no directory, and a relative include from the command line (Unix anchors it at `/`, the helper's directory), have no anchor on Windows, whose neutral directory is the Windows directory: both are refused.
- **`~/`.** The captured `HOME`, found without regard to case, as on Unix: it must be an absolute path that is text. A Windows environment often has no `HOME` (Git for Windows falls back to `HOMEDRIVE` and `HOMEPATH`, then `USERPROFILE`); until the home resolver of step 3.1 is the one place that decides, an include of `~/` with no `HOME` is refused, exactly as on Unix.
- **Regular-file reads.** Config files are read through `git::regular_file::open` (step 1.3): a device, a pipe or a directory is refused by what it is and without waiting, a missing file is empty, a file over the source limit is refused, and a path longer than 260 characters is opened by a wide path.
- **OQ-E, the working directory.** Unchanged from section 5 (the Windows directory, `GIT_CEILING_DIRECTORIES` at its parent). `runner/ceiling_tests.rs` plants a repository one level above a working directory and shows that the Git under test finds it without the ceiling the owner computes and does not with it.
- **Minimum Git version.** Verified: Git for Windows 2.55.0.windows.3 (spike S5 and every Windows row of this step). The floor by feature is 2.26 (`git config --show-scope`; the view also needs `--null --show-origin --no-includes`, all older); no older Git was run, and gwz does not probe the version at run time, so a Git older than the verified one is untested rather than refused. **Operator decision (2026-10-11): no minimum Git version is required or enforced.** gwz neither probes nor refuses by version; an older Git is untested, not refused.
- **Not here.** The Windows form of the fake `git` that 28 files use (Table B.3) is not a script on Windows, where the program is created as an `.exe`: `helper_script::write_helper_script` writes a script that Git's shell runs as a configured credential helper, and `write_git_fixture` stays Unix's. Step 4.11 decides how the remaining fakes are ported.
