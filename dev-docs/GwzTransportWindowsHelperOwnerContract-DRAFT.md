# GWZ transport on Windows: the credential-helper process owner (the WH2 contract, process half)

Date: 2026-10-10 (revision 2, 2026-10-11). Status: **DRAFT, step 4.1 of `GwzTransportWindowsParityPlan.md` (revision 3). Not frozen.** Revision 1 was reviewed NO-GO by `GwzTransportWindowsHelperOwner-ReviewCodeConsistency.md` and `GwzTransportWindowsHelperOwner-ReviewSafetyState.md`; `GwzTransportWindowsHelperOwner-RemPlan.md` maps each finding to its fix. Revision 2 records the operator's decisions of 2026-10-10 on OQ-A and OQ-B and the spike rows the reviews asked for. It freezes only when the review of this revision has a GO (the contract handles credentials, `GwzWindowsHttpsIntegrationDesign-DRAFT.md:287`) and the operator has answered what section 6 still leaves open.

Scope. What a helper process owner must guarantee on Windows: process tree containment, timeouts, stdin and stdout framing, environment, cancellation and exit reaping, each mapped to what the Unix owner (`src/git/endpoint/https_auth/`) guarantees today. It is the process half of WH2 (`GwzWindowsHttpsIntegrationDesign-DRAFT.md` §3 "WH2", §5). The path half (executable discovery and its extension rule, the wide-path framing of the configuration view's file paths, regular-file reads) is step 4.3's addendum, listed in section 7. One piece of the view is decided here because the runner needs it to start a process: **the view's value is UTF-8 and becomes a UTF-16 environment value with no replacement character** (section 5). Baseline row P08 (`GwzTransportWindowsBaseline.md:329`) executed the Job Object primitive; this contract is its composition with the owner. The Job Object stays private to the HTTPS helpers in core: not a second SSPI owner, not a public process library (`GwzWindowsHttpsIntegrationDesign-DRAFT.md`, §5). The launch copies gwz-sspi's pattern (`supervisor/windows/attributes.rs`, `launch.rs`), not the crate.

## 1. The owner, in one paragraph

One helper child runs under one `Runner` (`runner.rs`), started by `process_tree::spawn` into a process tree the owner holds as a `ProcessTree`. A `HelperJob` (`owner.rs`) holds the child, the tree and the two admission permits (the host's helper slot and the endpoint's slot) from spawn to retirement. Success, failure, timeout, cancellation and a dropped future end in one of three states: **retired** (on success: the leader has exited, the tree is let go of, the permits are released, and what the helper left running is left running); **cleaned up** (on failure, timeout or cancel: the tree has been ended and is empty, the leader waited for, the permits released); **retained** (the `AuthOwner` keeps child, tree and permits until `reap_pending` or `reap_ready` finds the leader gone and the tree empty, ending any member that is still alive); or owner dropped (the retained children go with it). The interface is the same on both platforms; only `process_tree.rs` has two arms.

**Brokers.** A process that WMI `Win32_Process.Create`, Task Scheduler, COM `LocalServer` activation, a service, a packaged-app launch or a shell hand-off to an already running instance creates on a member's behalf is outside every job. Spike S2: `Start-Process notepad.exe` (a packaged-app alias on Windows 11) left the job empty; `Start-Process` of a classic executable stayed in it (S2b). This is the Windows analogue of `setsid` on Unix and is outside the contract.

## 3. Timeouts and cancellation

Unchanged from Unix, and the Windows arm adds no clock. The lookup has an allocation allowance (waiting for a host slot), a single interaction deadline from the helper's start, and the caller's `CancellationToken` plus the owner's own. `Runner::check` is the one place that turns an expired deadline into `Timeout` and a cancelled token into `Cancelled`; success is admitted only if it still holds at the end, while the job still owns its tree (`finish_job`). Draining polls every `DRAIN_POLL` (2 ms) and a wait for the leader's exit every 2 ms, inside the existing `CLEANUP_GRACE`; neither is a new deadline for the caller. A cancel or deadline before spawn starts no process. A tree that does not drain within the grace on a failure path is reported `CleanupPending` and stays charged to capacity; on the success path nothing is waited for (C8).

## 4. Pipes and framing

Unchanged from Unix. Stdin: the request is written then the pipe is closed; a broken pipe is not a failure (Git ignores `SIGPIPE`; a helper may answer without reading), any other write error is `Pipe(kind)`. Stdout: at most `OUTPUT_LIMIT` (16 KiB) plus one probe byte; one more byte is `OutputTooLarge` and ends the tree. Stderr: drained and discarded without bound (a 40,000-byte flood does not reject the answer). The three run concurrently with the wait. Output is CRLF-tolerant by the existing parser (one trailing CR).

**OQ-C (decision: accept, recorded).** On Windows the bytes pass through blocking-pool copy buffers that are not ours and are freed without wiping; the Unix path has no such copy. Sizes, for TR1.8 §4's dependency-copies list: stdout reads are requested in at most `OUTPUT_LIMIT` (16 KiB) slices, so a copy holds up to 16 KiB of the answer, **password included**; the stdin copy holds up to 2 MiB of the request (gwz sends `url=...` only, no secret); stderr is a 4 KiB scratch of diagnostics. Every pending call owns its buffer until it returns.

## 5. Environment

The child's environment is exactly the captured snapshot (`Config.environment`) minus `GIT_ASKPASS`, `SSH_ASKPASS`, `GIT_DIR`, `GIT_COMMON_DIR` and `GIT_WORK_TREE`, plus `GIT_TERMINAL_PROMPT=0`; with a configuration view, also minus every `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_*` and `GIT_CONFIG_VALUE_*`, `GIT_CONFIG_SYSTEM` removed, `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL` set to the platform's null source (`/dev/null`; `NUL` on Windows) and `GIT_CONFIG_PARAMETERS` set to the view. It is built as an explicit list (`Environment` in `runner/environment.rs`), which both platforms hand to the spawn. Nothing is read from the process environment.

- **Names compare as the platform compares them.** On Windows without regard to ASCII case: `Git_AskPass` is `GIT_ASKPASS`, and a filter that missed it would hand an ask-pass program to the helper. Prefix tests compare the encoded bytes, so a name that is not Unicode (a lone surrogate) still starts with an ASCII prefix. Tests: `askpass_is_never_in_the_helpers_environment`; the unit tests of `names`, `starts_with` (with the lone-surrogate row), `set`, `remove_prefix`.
- **Working directory.** Unix: `/`. Windows: the Windows directory as the operating system names it (`GetWindowsDirectoryW`), not the caller's snapshot (**OQ-E, decided**: the review found `SystemRoot` caller-controlled). Its parent is a drive root where any user may create a folder, so the owner sets `GIT_CEILING_DIRECTORIES` to that parent and Git does not search upward into it. Spike S4: with a planted `C:\...\.git\config` above the working directory, `git config` read the planted `credential.helper` without the ceiling and found no repository with it.
- **The view is UTF-8 on Windows** and becomes a UTF-16 value without replacement; bytes that are not UTF-8 are `ConfigurationRefused` (`a_view_that_the_environment_cannot_carry_is_refused_rather_than_converted`). The environment block is sorted by name without regard to case, as `CreateProcessW` expects, and refuses a NUL or a name holding `=`.
- **No size refusal on Windows.** On Unix an over-long environment value fails the spawn (`E2BIG`) and is reported as `ConfigurationRefused`. On dabeest `CreateProcess` accepted a 4 MiB `GIT_CONFIG_PARAMETERS`, so the Windows bound is the view's own `PREPARATION_LIMIT` (4 MiB) and nothing at spawn (**OQ-G**).
- **Command line.** The executable is an absolute path passed as the exact application name, quoted; each argument is quoted the way `CommandLineToArgvW` reads it back (`arguments_are_quoted_the_way_the_command_line_parser_reads_them_back`). A relative program is refused. The test fakes are `.cmd` files run as `cmd.exe /d /c script`; the extension rule for production executables is 4.3's.
- **Creation flags**: `CREATE_NO_WINDOW | CREATE_UNICODE_ENVIRONMENT | EXTENDED_STARTUPINFO_PRESENT` (**OQ-D**).

## 6. Decisions and open questions

Decided by the operator on 2026-10-10:

- **OQ-A, release on success.** On success the job's `KILL_ON_JOB_CLOSE` is cleared and the job closed; survivors live on, as on Unix, under Git and in 1.0.17. Timeout, cancel and gwz's exit kill the whole tree. The reviews' blind convergence (Code F2, Safety F1) was the Git Credential Manager browser flow: a browser that GCM starts must not die with the lookup. Spike S1 shows a descendant of a `!sh` helper stays in the job after git exits (so the kill paths reach it) and S2b that a classic process started through the shell does too; S2 shows a packaged app is outside the job and so survives under any policy.
- **OQ-B, a private `CreateProcessW`.** `JOB_LIST` plus `HANDLE_LIST` (C1, C9). The create-suspended, assign, resume sequence and its window are gone.

Recorded and not reopened (the reviews agreed):

- **OQ-C**: accept the copies (section 4).
- **OQ-D**: keep `CREATE_NO_WINDOW` and die-on-unhandled-exception. Spike S3: under `CREATE_NO_WINDOW` a `!sh` helper's `powershell` descendant reported no console window and six processes on one console (git, sh, powershell and their hosts): no console is allocated per descendant. A real flash can only be seen from an interactive desktop, which dabeest's SSH logon does not have.
- **OQ-E**: the Windows directory from the OS, plus the ceiling (section 5).
- **OQ-F**: a job that cannot be created in, or a creation the system refuses, refuses the helper (`SpawnFailed`), never runs it uncontained. A refusal cannot be produced on dabeest; `a_creation_that_fails_after_the_job_exists_runs_nothing` injects one (a handle that is not a job).
- **OQ-G**: no spawn-time size bound (section 5).

Open for this revision's review: whether C9's microsecond window (the child ends are inheritable until `CreateProcessW` returns) needs a gwz-wide spawn gate. It affects only a concurrent `bInheritHandles=TRUE` spawn that names no handle list (std's `Command`); gwz-sspi's worker launch names one. **Recommend** no gate now, and a source check that production code spawns no std `Command` while a helper starts.
