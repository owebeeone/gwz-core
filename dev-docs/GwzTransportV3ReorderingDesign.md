# GWZ transport profile 3 — out-of-order stream opening

Date: 2026-09-23. Status: **DRAFT; operator-authorized remediation round 2, review required**.

The operator chose receiver-side out-of-order acceptance after the [independent-delivery/start-ticket NO-GO](../../dev-docs/GwzTransportDeliveryStartTicket-Verdict-3.md). This is a new transport-identity design object, not another remediation of that stopped tuple. It replaces the *opening-order assumption* in the proposed [independent-delivery amendment](GwzIndependentTransportDeliveryAmendment.md). The accepted [placement design](GwzRemoteTransportPlacementDesign.md) and released profile-1/2 behavior remain controlling until this design and its implementation pass separate gates. This document freezes transport profile semantics only; the Python caller guide's three open surface findings remain outside this review and still block operation-session activation.

## 1. Problem and selected boundary

The initiator currently assigns a monotonically increasing positive `stream_id` to every Open and CheckIdentity. The profile-2 receiver uses one `highest_id`: it silently returns success for any later opening with `stream_id <= highest_id`. A per-key host dispatcher can deliver Open 2 before Open 1. The receiver accepts 2 and silently drops 1 even though 1 is fresh, allowing the host to acknowledge a stream that does not exist. Preserving one global delivery order would couple every new stream to a stalled earlier Open. Instead, profile 3 makes the **receiver** distinguish a genuinely unseen ID from a seen/retired ID, independent of arrival order.

The binding/session generation remains the namespace. IDs are allocated once by the initiator, monotonically from 1, and are never reused within that binding. Open and CheckIdentity share one namespace. The receiver may admit fresh ID 2 before fresh ID 1 after each passes its own request/operation/context checks. Order **within** one stream, and the prerequisite Bind/Bound and opening transitions for dependent controls, remains required. The host may dispatch different stream keys independently as the prior amendment proposes. Delivery order itself is not proof of freshness or authority.

## 2. Explicit profile negotiation and limits

Profile 3 is an explicit Bind/Bound selection. A host using per-key opening dispatch sends a bootstrap Envelope with `version=1`, `Bind.versions=[3]`, and `stream_id=0`; it must verify a bootstrap Bound Envelope with `version=1`, `Bound.version=3`, and `stream_id=0` before releasing any Open/CheckIdentity. An older endpoint rejects with UnsupportedVersion, with no Git, credential or pool effects and no fallback after this attempt. A host may separately choose its existing profile-2 FIFO placement before binding, but it must not silently downgrade a requested profile-3 operation or run the per-key dispatcher on a profile-2 binding. Existing version-1 defaults, profile-2 messages, field numbers, and profile-2 receiver rules remain unchanged. For profile 3, the existing Envelope shapes and message kinds are retained and post-Bound envelopes carry `version=3`; CheckIdentity remains legal with exactly the profile-2 body, explicit-key policy and terminal rules. This explicitly supersedes the accepted placement design §6 sentence calling CheckIdentity “v2-only”: it is legal in profiles 2 and 3, and illegal in profile 1. This and the opening-order rule are the only placement §6 semantic amendments in this object. This is a semantic profile revision, not a new physical wire carrier.

Profile 3 fixes `MAX_STREAM_IDS_PER_BINDING=4096`, distinct from the existing **64 concurrent streams** and **256 lifetime request IDs** defaults. A receiver validates positive IDs no greater than 4096 before any route/action allocation. The initiator refuses a 4097th allocation with local Capacity and requires a new binding; it never wraps or reuses an ID. The application host may rotate before either its request-ID or stream-ID lifetime cap, but generation rollover is not part of this transport profile. The operation-session draft's four live/draining-generation limit remains a separate activation decision. These fixed profile-3 caps require no new Envelope field. Changing a cap requires a later profile/negotiation revision, not a local tuning flag.

Both mux roles retain bounded ID history until the entire binding is retired. The initiator records each ID it successfully allocates/enqueues; the endpoint records each opening it admits from the peer. The endpoint may therefore have gaps where the initiator abandoned an opening before delivery. At most 4096 records exist per role. Each record stores ID, registered request ID, operation ID, opening kind, active/draining/terminal state and, if a terminal acknowledgement was actually observed, its identity. This is a separate lifetime budget from the 64 active-route slots. A fixed admission charge of at most 512 bytes per record reserves at most 2 MiB per binding for this table, including storage for bounded identifiers and lookup structure; implementation must prove the bound with a bounded slot representation or lower the lifetime cap before activation. The richer active or draining route is separately charged against the 64-route cap and negotiated stream/queue budgets. Never discard a record merely because its stream closes or a higher ID arrives. The session and its table retire together only after the host has fenced old-generation delivery and all active/cleanup owners have drained.

## 3. Receiver admission transaction

For a profile-3 Open/CheckIdentity, validate the outer message and session/generation, version, positive bounded ID, live registered request, matching operation/endpoint context, and message body **before** endpoint authority or work. The table lookup has four cases:

1. **Unseen ID:** reserve the fixed lifetime-record charge and one active-route slot, then admit the action to the bounded queue. Only after queue admission succeeds atomically install the route and mark the ID seen. A lower unseen ID is legal even if a higher ID was already admitted. If the queue returns WouldBlock, leave no seen record, route, operation binding or side effect; the host may retry that exact delivery under its deadline. A fallible allocation after queue admission is forbidden: reserve first or roll the transaction back before reporting success.
2. **Seen active ID:** another Open/CheckIdentity using it is a protocol error, even if its body is byte-identical; it cannot dispatch twice. Non-opening frames must match the active route's request, operation/session/endpoint context and valid stream transition. The existing per-stream state machine still applies.
3. **Seen draining ID:** a user-visible timeout, cancellation or result seals new application work but does **not** remove the mux route while the binding stays healthy. The request, route, stream/check validation state, host dispatchers and cleanup owner remain charged until peer terminal and same-key delivery cleanup finish, or until their finite cleanup deadline fails the binding. The draining route is non-authoritative: it validates and consumes correctly correlated, bounded peer frames under the same transition, offset, credit, flush and close-predecessor rules as a live route, but discards payload and cannot update the fixed user result, facts, endpoint choice or lease ownership. A late `IdentityChecked`/`IdentityCheckFailed` terminates a draining Check; a late `OpenFailed` terminates a draining Opening. A late `Opened` advances that *draining route* from Opening to Stream without granting application authority. Thereafter ordered Window, Data, Flush/Flushed, EndWrite and other legal stream controls may arrive and be validated before a legal `Failed` or `Closed` terminal. `Closed` requires a real prior initiator Close and EndWrite; an Opening that was cancelled before Opened cannot fabricate that predecessor. A valid endpoint failure is an alternative terminal after late Opened. A local Cancel uses the existing causal barrier and aborts earlier unsent same-key data as the delivery amendment specifies. After peer terminal but before the cleanup fence, the charged route may consume only an exact duplicate terminal or a correctly correlated Cancel already in flight in the opposite direction, with no second effect. Wrong request/operation/endpoint, malformed body, impossible transition or conflicting terminal remains Protocol; a foreign session gets `WrongSession` as below.
4. **Seen terminal ID:** retain a tombstone on both roles only after the route's peer terminal and host delivery/cleanup fence have completed. An exact duplicate of the observed terminal acknowledgement for the same request/context is idempotent and changes no state; compare a cryptographic digest of the canonical bounded `(request_id, Envelope)` together with its kind and registered context. A conflicting terminal, new Open/check or other effectful frame is a protocol error. No terminal ID can reopen work, mutate observations, release another lease or change recorded facts.

The host's cleanup fence closes both producers for this stream key, resolves every already dequeued admission/abort race, and drains or explicitly aborts all queued frames in both directions before releasing its charged route. A peer terminal alone is not that fence. If the fence or peer terminal cannot complete within the bounded cleanup deadline, fail the binding and wake waiters rather than discarding the route while another request remains healthy. This may interrupt a peer operation only on an explicit bounded cleanup failure, not merely because a legal late frame arrived after a user-visible outcome. The draining validator may reuse the stream state machine or a common transition core, but cannot substitute an approximate kind-only shadow state. Its payload-discard mode must still enforce negotiated frame, offset, flow-control and queue bounds. Active plus draining routes never exceed the negotiated active-route limit.

For a positive ID **never seen** in a non-opening frame, return Protocol and fail the binding; it cannot create a route. A malformed frame for the live session or an ID above the profile cap likewise fails closed. An envelope from a different session/generation leaves this binding untouched but returns a distinct, non-disconnecting `WrongSession` error on profile 3; it must never return `Ok` or count as peer admission. The v1/v2 mismatch result remains unchanged. A registered request that was sealed before a delayed opening arrives is not live, so the opening is rejected and cannot reattach; the host's delivery-or-abort contract must surface the failure rather than acknowledging it as a successful Open. The receiver never uses `id <= highest_id` as a stale test in profile 3. The initiator may keep a high-water counter **only to allocate** new IDs. Only `Ok` after validated peer action-queue and route-table admission acknowledges an Open/CheckIdentity; neither host enqueue nor `WrongSession` does.

An Open/check which the host atomically aborts before peer admission creates no receiver record. Its ID remains spent at the initiator and is never reissued. The host must guarantee that an aborted frame cannot later be delivered on the still-live binding; if it cannot decide the admission/abort race, it fails the binding and keeps cleanup charged. This preserves the prior amendment's cancellation and fail-closed rule without inventing a receiver tombstone for an opening the receiver never saw. Future physical carriers must prove the same fence or add an explicit skip/retire control; this in-process design does not claim that wire proof.

## 4. Integration with independent delivery

Profile-3 identity tolerance does **not** remove causal barriers within one key. Bind/Bound and charged core/endpoint registration precede any opening. Open or CheckIdentity must reach the peer before its dependent Cancel or response; Opened must reach the initiator before established-stream Window/Failed. A failure during Opening uses OpenFailed. The proposed ready-selective urgent and per-key ordered dispatchers may let Open/check 2 pass a blocked Open/check 1, but each item still has the proposed 30-second enqueue-to-peer-admission deadline. A blocked or malformed earlier opening must be admitted, explicitly aborted, or fail the binding by that deadline; the receiver never reports success for a frame it ignored as stale. Later streams do not wait for a global opening barrier.

The **host**, independent of the receiving profile, owns the admission receipt. At enqueue it pins an immutable, owner-bound pair of sender and intended peer Port identities plus their session/route generations to the private delivery item; these identities come from the established host binding, never from a caller-supplied field in the Taut message. It must validate that exact pair before invoking `deliver()` and keep both Port objects pinned through the delivery/abort decision. A mutable “current endpoint” lookup may not retarget a queued or in-flight item. If the selected Port is profile 2, profile 1, unbound or profile 3, the same host check applies: a mismatched pair is **not delivered**, cannot turn any legacy `Ok(())` into an admission receipt, and fails or atomically aborts the origin binding's item, wakes its waiter and retains cleanup charge. The unrelated replacement binding remains healthy. After the pinned intended peer returns `Ok`, the host may acknowledge only that item's admission; a profile-3 `WrongSession` remains a defense in depth, not the host's generation-affinity proof. A port replacement racing an in-flight delivery cannot revoke or redirect its pinned target: that old generation drains or fails under the normal delivery deadline. No extra wire field or physical carrier is required for this same-process host identity.

Python's loop-bound host remains a forwarder of Taut delivery events; it neither allocates stream IDs nor manages the seen table. The Rust receiver mux owns the table and the endpoint's existing authentication/pool policy remains unchanged. Version-1 start tickets still require owner-bound admission and request registration; this document does not approve their caller API. The transport profile is equally applicable to local Rust pumps and a supplied same-process endpoint. No separate-process or iroh transport is claimed.

## 5. Required proof before activation

- A deterministic counterexample must deliver Open 2 before Open 1, CheckIdentity 2 before CheckIdentity 1, and mixed Open/check pairs, then prove both distinct actions and routes exist exactly once. Repeat with one opening delayed behind saturated Data on another key; neither can be silently acknowledged and the earlier one admits or the binding fails by its deadline.
- Seeded Monte Carlo runs must permute independently keyed openings, responses, Data/control chunks, terminal messages and randomly sized reads, with seed printed and replayable. The reassembled byte streams and action receipts must equal the source; 100% of admitted IDs are either active/terminal or explicitly failed, never silently missing.
- Inject WouldBlock immediately before action admission, allocation/charge failure before commit, duplicate Open/check while active, duplicate after retirement, exact and conflicting terminal acknowledgements, stale Data/Window after retirement, an unknown non-opening ID, a sealed request and an ID above 4096. Verify no second action, authority transfer or false success. With A and B on one binding, fix A's user-visible outcome during Opening, then deliver late Opened, correctly ordered Window/Data and a legal Failed terminal to A's charged draining route; A's outcome/facts remain fixed, B continues, and wrong-context or impossible frames fail closed. An unsolicited Closed without prior Close is Protocol. Separately establish A, send EndWrite/Close, fix its local outcome, then deliver a legal Closed. Check a locally timed-out CheckIdentity and a peer Cancel racing its terminal in both orders. On an expired cleanup fence, assert an explicit binding failure rather than a silently removed route.
- Saturate 64 active routes, then retire and create up to 4096 lifetime IDs while checking the 2 MiB accounting on each role. The next allocation refuses locally and preserves old tombstones until its binding retires. Operation-session generation rotation, including its four-generation cap, is proved at the separate application activation gate.
- Verify profile-3 Bind/Bound followed by CheckIdentity on both mux roles; v3-only offer to a v2 endpoint must refuse before effects; profile-2 FIFO/CheckIdentity tests and released profile-1 defaults remain unchanged, and profile 1 still refuses CheckIdentity. A mixed-version host must never run out-of-order opening dispatch on v2. With S1 profile 3 draining and S2 profile 2 or unbound, deliberately select S2 for an S1 Open and CheckIdentity before and during dispatch in both directions. The host rejects the port-pair mismatch before delivery, so S2 receives no action even though its legacy session-mismatch path could return `Ok`; S1 fails/aborts, its waiter wakes and cleanup stays charged, while independent S2 work continues. Repeat S2 profile 3 to verify `WrongSession` defense and repeat correct-generation delivery to verify true admission.
- Re-run the independent-delivery amendment's urgent-versus-ordered barriers, full control reserve, loop-stall watchdog, partial registration/close, two-peer isolation, and delivery-or-abort race tests. An endpoint `receive()` returning success for an ignored opening is a test failure.
