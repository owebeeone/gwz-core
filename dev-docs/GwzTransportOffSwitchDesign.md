**Names.** The plan calls this step the off switch. Its user-facing name is the transport setting, `gwz` or `native`, and no user-facing string says "off switch" (remediation plan D2). "Native selected" is what the plan calls the switch on. The internal fields `ProcessAttributes.transport_off` and `SessionOptions::transport_off` keep their names, and are true when native is selected.

## 1. Decision

- gwz gets one documented opt-out, the **transport setting**. With `native` selected, every network operation takes libgit2's native transport, as 1.0.17 does, builds no transport runtime, and runs at 1.0.17's defaults (§6). `gwz`, the default, keeps gwz's own transport. A network operation is a request in transport scope, as the one predicate both drivers already call decides it (`gwz-core/src/transport_scope.rs:1-15`).
- It is the user's one escape hatch to libgit2's own transports. Since OD15 and the reversal of OD10 and OD11, the only other native paths are a caller without a host context (TR2.11) and `git://`, `http://` and `file://` remotes (amendment 2 §3.19).
- Three forms, each taking `gwz` or `native`:

  | Form | Name | Read by |
  |---|---|---|
  | Flag | `--transport <gwz\|native>`, a global option | gwz-cli |
  | Environment | `GWZ_TRANSPORT=gwz\|native` | gwz-cli, gwz-py |
  | Global configuration | `gwz.transport = gwz\|native` in the user's global git configuration | gwz-cli, gwz-py |

- **Why these names.**
  - The flag and the variable pair as `--url-scheme` and `GWZ_URL_SCHEME` do (`gwz-cli/src/url_scheme_arg.rs:26-27`), and as the server design's `--server` and `GWZ_SERVER`: the variable is the flag's name in upper case after `GWZ_`, with the same values. No product reads `GWZ_TRANSPORT` today; the nearest name is gwz-core's developer-only `GWZ_TRANSPORT_CHECKOUT`.
  - The values name the transport, as `--url-scheme`'s values name the URL form (`url_scheme_arg.rs:8-14`), so every report reads in the flag's own words: `transport: native (from GWZ_TRANSPORT)`. An `on|off` pair would report the escape hatch as a double negative, and could be read as "no network". Each form can say `gwz` as well as `native`, so it can override the form below it. "Native" is already gwz's user-facing word for libgit2's layer (`gwz-cli/docs/commands/auth.md:39, 50-53`).
  - "Transport" is already the user's word: `--verbose` shows "transport authentication diagnostics" (`gwz-cli/src/globalargs/parser.rs:219-225`). JSON's `meta.transport` holds those authentication rows, so the setting's object is `meta.transport_setting` (§5).
  - **Git configuration, not a gwz file.** gwz has no configuration file of its own. The only user-level configuration it reads for its own behaviour is git's, which the native credential callback opens (`gwz-core/src/git/gitbackend/transport_support.rs:265-271`). gwz already keeps one key of its own there, `remote.<name>.gwzSshIdentity`, read from one level only, the repository's (`gwz-core/src/git/gitbackend/transport_support/identity.rs:288-299`). `gwz.transport` is its counterpart, read from one level only, the user's global one. Users set it with `git config --global gwz.transport native`. A value written without `--global` lands in a repository's own configuration, which §3 ignores. No new file format, location or parser is needed.

## 2. The forms and their precedence

- **Precedence:** the flag, then the variable, then the global configuration. The first form that carries a value decides, and the forms below it are neither read nor checked, as a given `--url-scheme` leaves `GWZ_URL_SCHEME` unread (`url_scheme_arg.rs:47-49`). With no value anywhere, `gwz` applies.
- **Values.** Each form takes `gwz` or `native`. The flag takes them exactly. The variable ignores ASCII case and surrounding white space, and an empty one is the same as unset, as for `GWZ_URL_SCHEME` (`url_scheme_arg.rs:50-55`) and `GWZ_SERVER` (server design §3). The key ignores case. Any other value is refused, an empty value and a key with no value included. Within a file the last value wins, as git reads it.
- **The files are git's `--global` set,** read where `git config --global` writes them (D5): `$XDG_CONFIG_HOME/git/config`, or `$HOME/.config/git/config` when that variable is unset or empty; then `$HOME/.gitconfig`, whose value wins.
  - `HOME` and `XDG_CONFIG_HOME` come from the snapshot, never from the passwd entry. An empty or relative `HOME` names no file, and a relative `XDG_CONFIG_HOME` names no XDG file, since the caller's directory, perhaps a workspace, would otherwise supply the value.
  - **Departures.** From libgit2's own global lookup (`libgit2/src/libgit2/sysdir.c:324-420`), in each of which the key follows git: libgit2 reads an empty `XDG_CONFIG_HOME` as the relative path `git` (`sysdir.c:401-406`), and takes the passwd home when the real and effective user IDs differ, or for the home under `APP_SANDBOX_CONTAINER_ID` (`sysdir.c:347-359, 407-410`). From git: an empty `HOME`, which git reads as `/` (it reads `/.gitconfig`), and a relative `XDG_CONFIG_HOME`, which git reads against the current directory, name no file here. The native transport's own reads follow libgit2's rule: its credential callback's `Config::open_default()` (`transport_support.rs:267`) and native SSH's `known_hosts`.
  - **Includes.** `include.path` is followed, as git and libgit2 follow it, with one more departure. A path beginning `~/` resolves against libgit2's process-wide home (`libgit2/src/libgit2/config_file.c:523-528`), fixed when libgit2 first initialises in the process (`sysdir.c:453-465`). In gwz-cli that is at startup, from the environment its snapshot is taken from. In gwz-py it is the process's first libgit2 call, not import, since the extension's module init makes none (`gwz-py/native/src/lib.rs:153-170`). `includeIf` never applies: the files are opened without a repository, so libgit2 skips every conditional include (`config_file.c:727`). gwz therefore evaluates includes against no repository. The command it prints to locate an included value runs git in `/` (`git -C /`), where git finds no repository either, so it too follows `include.path` and applies no `includeIf` (§10).
  - `GIT_CONFIG_GLOBAL`, which git honours and libgit2 does not (server design §5, the exclusion table), is not read, and neither are `GIT_CONFIG_PARAMETERS` and `GIT_CONFIG_COUNT`, which libgit2 does not implement.
  - **A file that cannot be read** carries no value, as git and libgit2 treat it (`config_file.c:114-124`; D4), and is reported as skipped (§5). A missing file carries no value.
  - **An unparsable file** is refused. libgit2's message names the file and line that failed, which may be a file the global file includes (`libgit2/src/libgit2/config_parse.c:15-25`), and the refusal shows it (§10).
  - **`file`** names the global file whose value decided (§5, §10). A value reached through `include.path`, an entry whose `include_depth` is above 0, is reported as "in a file included by `<file>`", with `"included": true` in the JSON, and its messages give a command that locates it (§10). libgit2 records the included file's own path as the entry's `origin_path` (`config_file.c:812`), but git2-rs's `ConfigEntry` exposes only `include_depth` (`git2-rs/src/config.rs:525-565`), and this design directs no change to git2-rs.
  - **Windows.** The flag and the variable are unchanged, and the variable's name matches in any case. The files follow libgit2's Windows templates (`sysdir.c:326-332, 377-386`), read from the snapshot. TR1.8 states these rows among the forms' Windows behaviour, each recorded with 1.0.17 on dabeest, with at least one row with `HOME` unset (amendment 2 §3.5).
- **A malformed form** is refused before any effect, naming the form (§10). gwz-cli refuses it as a usage error, exit 2 (`gwz-cli/src/lib.rs:296-298`), as it refuses a bad `GWZ_URL_SCHEME` (`url_scheme_arg.rs:58-66`). gwz-py raises it from that operation's `call` or `submit` (§10).
- **When it is resolved, in 1.1.0:**
  - **gwz-cli:** once per command, while `invocation_from_cli` builds a request in transport scope (`gwz-cli/src/globalargs/invocation.rs:14-42`; the predicate `transport_meta` asks, `gwz-cli/src/globalargs/dispatch.rs:362-377`), from the command's environment at its start. A command with no network request never reads it, so `status`, `diff`, `log` and the `hook` family are untouched, malformed forms included.
  - **gwz-py:** at each network operation's native entry, from that operation's snapshot, which is taken while the caller holds the GIL (`gwz-py/native/src/client_host.rs:153-169`; Python design §2.2–§2.3). The files are then read, and §3's scan runs, with the GIL released. This replaces the seam that answers "gwz" today (`gwz-py/native/src/route/transport.rs:46-53`), as amendment 2 §3.17 directs. A change to `os.environ` or to a file takes effect at the next operation. This per-operation reading is 1.1.0's; from 1.2.0 a `Client` reads the setting once, when it opens (§8).
  - gwz-py has no flag form in 1.1.0, in its library or its CLI, just as its CLI has no `--max-retries`, and `Client` takes no transport parameter.

## 3. A workspace or repository value

- **Ignored, by construction.** The resolver reads only the user's global files. `gwz.conf/` and `.gwz/` carry no setting, unlike the URL scheme, which a workspace remembers on purpose (`url_scheme_arg.rs:37-39`). Each git scope has one outcome:
  - global, `.gitconfig` and the XDG file: read (§2);
  - a repository's own configuration, its `.git/config` and `config.worktree`: ignored, with a note, for the workspace root (scope `root`) and for each member (scope `member`) the request targets;
  - system: not read, and no note. libgit2's system file is `/etc/gitconfig` on Linux and macOS (`sysdir.c:277-284`), while git's is fixed when git is built, such as Homebrew's `/opt/homebrew/etc/gitconfig`, so a note could name the wrong file;
  - the command scope (`git -c`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`) and `GIT_CONFIG_GLOBAL`: not read.
- **Why.** Others write a workspace, and share it. The two transports differ in proxy handling, in the environment credential helpers run with, and in host-key checking, so which transport runs is the user's choice alone. A `HOME` inside a workspace already hands that workspace git's global configuration, credential helpers included; the setting adds nothing to that exposure.
- **The note's scan** (D6). When a driver resolves the setting for a network request, it also looks for the key in the repositories the request targets, as the operation itself resolves them (`gwz-core/src/workspace_ops/target_selection.rs:74`, which `handle_fetch.rs:82` and `push_member.rs:73` call). It reads each one's own configuration, `<common dir>/config` and, when present, `<git dir>/config.worktree`, as gwz's repository inspector names them (`gwz-core/crates/repo-inspect/src/config_scan.rs:8-13, 47-58`).
  - The scan finds `<git dir>` and `<common dir>` from the text of the repository's `.git` file and its `commondir` file, under the same guard below. In the common case `.git` is a directory, which is `<git dir>`, and holds no `commondir` file, so it is `<common dir>` too. It never uses `Repository::open_ext`, as the inspector does (`gwz-core/crates/repo-inspect/src/layout.rs:49-76`), since that open reads `.git/config` before any guard could run.
  - A file is opened only if `symlink_metadata` reports a regular file of at most 1 MiB, the bound the server design's configuration scan uses (its §5, "The files it reads"). Anything else is skipped without a note.
  - The scan never refuses or blocks a request. A workspace or file it cannot read gets no note, and the operation reports its own errors. It opens each file without a repository, as §2 opens the global files, so it follows `include.path` and applies no `includeIf`. An `include.path` inside a scanned file remains the repository's own hazard, as for any command that opens that repository.
  - An ignored value is never checked: a malformed one gets its note, reported as written, and no refusal.
  - Each file that holds the key gets one note (§4, §10), naming its scope and, for a member, its ID, whichever transport is selected. A value the file reaches through `include.path` is noted as in a file included by it. gwz-py reports each file once per `Client`, and keeps that record in the `Client`'s `ClientHost`.

## 4. The notice

- **gwz-cli.** With native selected, one note on standard error in human mode, before the request runs (§10). It takes the existing `gwz: note:` form, which is also printed in human mode only (`gwz-cli/src/clirequest/invocation.rs:278-285`), and it needs no `--verbose`.
  - It prints for every command whose request is in transport scope, a `--dry-run` and a workspace whose remotes are all `file://` included. A CLI command runs at most one such request, so a session's first network operation is the command's only one.
  - `--json` and `--jsonl` print no note. `meta.transport_setting` carries it (§5), as DR-1 keeps the machine truth beside a stderr warning (`gwz-cli/src/merge_render.rs:245-251`).
  - Only selecting `gwz` silences it (OQ1).
- **gwz-py's notice is a `warnings` warning** of category `UserWarning`, issued at the native entry when a network operation resolves `native` (Python design §2.2). It is gwz-py's only warning, so only it can be made an error (D1). There is no new warning class: 1.1.0 leaves gwz-py's public API unchanged (amendment 2 §3.1).
  - It is issued from one location, attributed to the `gwz` package, so Python's default filter shows each text once per process. A filter on its message, or on the module `gwz`, controls it.
  - A filter that turns it into an error makes that `call` or `submit` raise it, before any effect. The caller sees it as the `__cause__` of the `GwzBridgeError` the bridge raises (`gwz-py/src/gwz/bridge.py:331-334, 350-353`).
- **gwz-py's ignored-value notes are `logging` records** on logger `gwz`, at `WARNING` (D1), so no warnings filter can turn a repository's file into a refusal. gwz-py logs nothing today. An application that configures no logging sees each record's message on standard error, through Python's last-resort handler. A failure to log is ignored.
- **gwz-py's CLI** prints each warning and record as a line on standard error: its text with the leading `gwz: ` replaced by `gwz-py: note: ` (§10). It does so in every output mode, since its JSON has no setting field in 1.1.0.
- **No global.** The CLI's "once" is its command's own control flow, and gwz-py's per-file record belongs to its `ClientHost`. Python's "once" is the `warnings` module's registry: state a named dependency keeps, the exception gwz-core's `AGENTS.md` names.

## 5. Reporting

- **`--verbose`** (gwz-cli, human mode). For a command whose request is in transport scope, one line heads the transport rows, wherever `--verbose` prints them (`gwz-cli/src/globalargs/render_exit.rs:13-29`): `transport: <gwz|native> (<origin>)`. It names the form that decided, or `default`, the global files gwz read, and each skipped file (§10).
- **JSON.** `meta.transport_setting` (§10) is absent on a default payload, and absence means the gwz transport by default, with nothing ignored or skipped. That keeps default payloads byte-identical, as DR-1's key does (D7). It is gwz-cli's rendering, not a protocol field; 1.1.0 adds none (Python design §2.7). `--jsonl` emits no event for it (§10).
- **The rows.** With native selected, each `meta.transport` row comes from libgit2's native transport and carries no endpoint receipt: `endpoint_id`, `connection_id`, `stream_id` and `reused` are null, as for any backend without a host context (`gwz-core/src/git/gitbackend/transport_candidate_tests/host_context.rs:73-93`). That is the route's evidence in both drivers' observations. Authentication rows are reported on either transport.
- **The route ledger.** S7.2 (1.1.0)'s row for the setting (amendment 2 §3.11) is filed per driver and platform. It states:
  - the route: libgit2's native transport for every network operation, the CLI in process and gwz-py per operation, with no runtime;
  - the forms and their precedence, user scope only, resolution before any connection opens, never a fallback, and the note;
  - its defaults, which are 1.0.17's: `--jobs` 50, `--max-per-host` 8 and `--ssh-timeout` 3 seconds when omitted, in both drivers, with two exceptions (§6): a gwz-core caller without a host context runs at 100 and 32, and gwz-py's timeout is the process's one clock for both transports;
  - what it lacks: pooling, setup retry and the 30-second setup budget. What it keeps is 1.0.17's behaviour, OD16's offer included;
  - its evidence: TR2.5's route rows (§9), in place of an S5.6 cell, as the Python rows take S6.3's (1.1.0 amendment §3.5); and TR8.1 (1.1.0)'s and TR8.4's native-route rows, which run at those defaults. OQ4 adds a consumer-build row.
- **S7.2 (1.1.0)'s migration notes** state the same defaults and exceptions, and what the native transport lacks.

## 6. What the setting changes, and what it does not

**With native selected:**
- **No transport entry.** gwz-cli runs the request on `Git2Backend::new()` instead of inside `with_local_transport` (`gwz-cli/src/globalargs/dispatch.rs:6-23`), and gwz-py takes its native route (`gwz-py/native/src/route/transport.rs:69-71`). A backend without a host context installs nothing, so libgit2 serves every remote with its own transports (`gwz-core/src/git/gitbackend/transport_binding.rs:132-137`).
- **1.0.17's defaults** (D3). When their flags are omitted, `--jobs` is 50, `--max-per-host` 8 and `--ssh-timeout` 3 seconds, as at gwz-core `v1.0.17` (`src/operation/resolve_jobs.rs:2`, `resolve_per_host.rs:2`) and gwz-cli `v1.0.17` (`src/lib.rs:177`). Today they are 100, 32 and 9. Explicit values are honoured in both drivers, whatever they are.
  - **Why.** A stock OpenSSH server drops new unauthenticated connections beyond its `MaxStartups` start value, 10 by default. The transport retries such a drop (amendment 2 §3.20) and the native transport does not, so at 32 per host the native transport would fail members that 1.0.17 serves at 8.
  - **How.** The driver that selects native writes 50 and 8 into the request's policy when the caller left them unset: gwz-cli where its `policy()` fills them from `--jobs` and `--max-per-host` (`gwz-cli/src/clirequest/invocation.rs:120-121`), and gwz-py at the native entry, which rewrites the request as it rewrites `~/` identities (`gwz-py/native/src/route/transport.rs:124-177`). `resolve_jobs` and `resolve_per_host` (`gwz-core/src/operation/resolve_jobs.rs:5-10`, `resolve_per_host.rs:6-11`) read that policy (for example `gwz-core/src/workspace_ops/handle_fetch.rs:133-134`), so they see explicit values. gwz-cli sets libgit2's timeout once the invocation is built, before any backend exists. Today it sets it at `gwz-cli/src/lib.rs:176-178`, ahead of `invocation_from_cli`, which creates no backend (`gwz-cli/src/globalargs/invocation.rs:14-42`).
  - **Why the drivers and not core** (E3). Core's network handlers reach their backend only through the `GitBackend` contract (`gwz-core/src/git/gitbackend/contract.rs:25, 1067`), which exposes no route (for example `gwz-core/src/workspace_ops/pull_head_member_preflight/member_validation.rs:13-26` and `gwz-core/src/workspace_ops/handle_materialize/apply.rs:20-46`). The host context is a `pub(crate)` accessor of `Git2Backend`'s candidate-only `Runtime` (`transport_binding.rs:8-9, 26-34`). `resolve_jobs` also sizes `gwz log`'s merge, which never has a host context (`gwz-core/src/operation/commit_log/merge.rs:30-42`), and an ordinary build before S7.1 has none at all. Keying the defaults in core would need a new method on that public contract and a rule for which operations it covers, which this design does not take. From 1.2.0 the session host fills them instead, keyed on the session's `transport_off`, which `open` gives it, so no such method is needed (§8).
  - **TR2.11's callers.** A gwz-core caller without a host context takes the native route, but no driver fills its policy, so it runs at 100 and 32 unless it passes values. 1.0.17 ran it at 50 and 8.
  - **gwz-py's constructor.** TR2.5 changes `Client`'s `max_connections_per_host` default from 32 to `None`, meaning unset, as `meta()`'s per-call parameter already is (`gwz-py/src/gwz/client.py:284`). Today an explicit 32 cannot be told from the default and is not sent (`client.py:188-194, 294-295`). With `None`, any value the caller passes, 32 included, is sent and honoured. With `gwz` selected nothing changes, since an unset value and 32 both resolve to 32. The keyword is newer than 1.0.17, whose constructor had none (gwz-py `v1.0.17` `client.py:159`; added at gwz-py `33a1f3f`).
  - **gwz-py's timeout.** Its libgit2 timeout is process-wide and fixed by the first backend (`transport_support.rs:20-31, 38-58`), so it cannot follow a per-operation setting. A native operation uses the process's value: what `Client.configure_transport_timeout` set through the protocol's `configure_transport_runtime`, or what gwz-py's CLI's `--ssh-timeout` set, or 9 seconds. 1.0.17's 3 seconds is not its default. An application that wants 3 seconds sets it before its first operation, as `gwz-cli/docs/commands/auth.md:50-53` already tells Python applications to.
  - **One clock** (E4). In gwz-py that value is the process's one clock for both transports: libgit2's connect and I/O timeout for native operations, and the stall clock each transport runtime reads at its start (Python design §1, §2.2). A process that uses both transports therefore chooses one value for both: 3 seconds for native operations also means 3-second stalls on transport ones.
- **Clocks and retry.** `--ssh-timeout` is libgit2's connect and I/O timeout (`transport_support.rs:61-67`), and 0 means none. gwz-py's `configure_transport_runtime` sets the same process-wide value (`gwz-core/src/protocol/transport_capabilities.rs:32-38`). There is no 30-second setup budget and no setup retry, so `--max-retries` has no effect: the retry plan's §4 and §5 are the transport's.
- **gwz-py's cancellation.** A waiting operation is refused with `cancelled`. A running one cannot be cancelled: its cancel fails with `unsupported_operation` (`gwz-py/native/src/client_host/operations.rs:197-210`). It still counts against its `Client`'s limit of 8, and `close()` and interpreter exit wait for it up to the bound, reporting its cleanup unconfirmed if it has not ended (Python design §2.4–§2.6).

**Unchanged:**
- **It is not a fallback.** The setting is resolved before any connection opens, and gwz never sets it. A transport failure, whether a refusal, an authentication failure or a timeout after its retries, is reported as that failure, and the operation never re-runs on the native transport. A refusal may name `native` as the user's remedy, as TR1.6's and TR1.8's do, with §10's hint. Naming it never selects it.
- **OD16's hazard.** On Windows the native transport answers the same default-credential challenge, through gwz's callback (`transport_support.rs:272-274`) and WinHTTP. As OD16 records, selecting native does not lessen the hazard.
- **Always native:** `git://`, `http://` and `file://` remotes and local paths (`transport_binding.rs:163-165`; `gwz-core/src/git/endpoint/ssh_destination.rs:19-28`), and a caller without a host context (TR2.11), whatever the setting.
- Commands with no network request, the protocol, and `transport_capabilities`, which describes the build and in 1.1.0 carries no per-operation field (Python design §2.8).
- With `gwz` selected, behaviour is as without this design, apart from the `--verbose` line, §3's notes, and their JSON.

## 10. The surface this freezes

In gwz-cli's strings, `gwz` stands for the invoking CLI's name. Every string reports the setting as `gwz` or `native` (D2).
- **Values, paths and identifiers** (E1). Values and paths follow two different rules:
  - A value, `<value>`, is shown as `GWZ_URL_SCHEME`'s message shows it: quoted, with control characters escaped (`gwz-cli/src/url_scheme_arg.rs:58-60`).
  - A path, `<file>`, or a member ID shown in a note, the `--verbose` line or a message has its control characters escaped the same way, so one entry is one line.
  - In a command gwz prints, `<file>` is quoted for the shell instead: single-quoted for POSIX shells, with an embedded `'` written `'\''`; on Windows, double-quoted, which TR1.8 may refine. A path that holds a control character gets no command, and neither, on Windows, does one that holds `%`, `$`, `` ` `` or `!`, which a shell expands inside double quotes there: `cmd` expands `%`, and `!` under delayed expansion; PowerShell `$` and `` ` ``; and Git Bash `$`, `` ` `` and, interactively, `!`. Such a message names the file, escaped, and says to remove the key from it.
  - The gwz-py strings follow the same rules. The JSON carries paths and IDs as JSON strings.
- **Scopes,** as §3 lists them: the global files are read; a root's or a member's `.git/config` and `config.worktree` are ignored, with a note; system configuration is not read, and gets no note; the command scope and `GIT_CONFIG_GLOBAL` are not read. `file` names the global file whose value decided, and a value reached through `include.path` is reported as in a file included by it (§2).
- **Where a value is, and how to remove it** (E2). Three placeholders recur below:
  - `<where>` is `<file>` for a value that file holds, and `a file included by <file>` for one it reaches through `include.path`;
  - `<remove>` is `remove it with git config --file '<file>' --unset-all gwz.transport` for a value `<file>` holds. For an included value, it is `git -C / config --file '<file>' --includes --show-origin --get-all gwz.transport shows which file holds it; remove it there`. For a `<file>` that gets no command, it is `remove it from that file`, or for an included value `remove it from the file that holds it`;
  - `--unset-all` removes every line of the key, and also a single one. `--file` reaches a value the named file itself holds, whichever global or repository file it is. `git config --global --unset-all` writes only to `~/.gitconfig` when that file exists, and `git -C <dir> config` only to `.git/config`, so neither reaches a value in the XDG file or in `config.worktree` (both exit 5). git never writes into an included file, and `git config --global --get-all` does not find a value there, since `--global` turns `--includes` off; hence the locating command. It runs git in `/`, since git applies an `includeIf` against the repository it finds from its working directory: in `/` it finds none, so, like gwz (§2, §3), it follows `include.path` and applies no `includeIf`. Without `-C /`, run inside a workspace, the command could also list a value that only an `includeIf` reaches, which gwz never reads. `<file>` is absolute, so `-C /` changes nothing else.
  - The help gives `git config --global --unset-all gwz.transport`.
- **`--transport <gwz|native>`**, a global option listed beside `--ssh-timeout`. It is not added to `gwz --help`'s short list (`gwz-cli/src/help.rs:7-37`), which names no transport option.
  - Help: `Transport for network operations: gwz (the default) or native, libgit2's own, as gwz 1.0 used`
  - Long help: `Which transport carries network operations: gwz's own SSH and HTTPS transport (gwz, the default), or libgit2's native transport, as gwz 1.0 used (native). native is an escape hatch you choose before a command runs, not a fallback: gwz never moves an operation from one transport to the other. With native, --jobs defaults to 50, --max-per-host to 8 and --ssh-timeout to 3, as in gwz 1.0, unless you give them; --ssh-timeout is libgit2's connect and read timeout; and there is no connection pooling, no setup retry and no 30 second setup budget, so --max-retries has no effect. git://, http:// and file:// remotes always use the native transport. This flag overrides the environment variable GWZ_TRANSPORT (gwz or native; unsetting it removes it), which overrides gwz.transport in your global git configuration (git config --global gwz.transport native sets it; git config --global --unset-all gwz.transport removes it). gwz reads ~/.gitconfig and $XDG_CONFIG_HOME/git/config (by default ~/.config/git/config), not a file named by GIT_CONFIG_GLOBAL, and not system git configuration, and it applies no conditional include (includeIf). gwz.transport in the workspace root's or a member's own git configuration (.git/config or config.worktree) is ignored, with a note. While native is selected, each command that uses the network says so once.`
  - Until TR2.1 adds `--max-retries`, the clause `, so --max-retries has no effect` is left out (§12).
- **`--jobs` and `--max-per-host`** (E8; the retry plan's §8 text, §12): their help's `(default 100)` and `(default 32)` read `(default 100; 50 with --transport native)` and `(default 32; 8 with --transport native)`, and their long help's `Defaults to 100.` and `Defaults to 32.` read `Defaults to 100; 50 with --transport native.` and `Defaults to 32; 8 with --transport native.`
- **`--ssh-timeout`** (D3; the retry plan's §8 text, §12):
  - Help: `Per-attempt stall limit for setup and for a body read; stalled setup is retried (0 = no timeout, default 9; 3 with --transport native)`
  - Long help gains at its end: ` With --transport native it is instead libgit2's connect and read timeout, with no setup retry and no 30 second setup budget, and it defaults to 3, as in gwz 1.0.`
  - S7.2 (1.1.0) rewrites `gwz-cli/docs/commands/auth.md:50-53`, whose `(default: 3 seconds; 0 disables it)` states one default for both drivers, to state each driver's: in gwz, 9 seconds, or 3 with `--transport native`; in gwz-py, 9 on either transport (§6).
- **`--verbose`'s long help** gains: ` It also names the transport selected for network operations, gwz or native, and what selected it. Authentication rows (meta.transport in JSON) are reported on either transport.`
- **The note,** with native selected, in human mode, on standard error, before the request, for a command whose request is in transport scope:
  - `gwz: note: using libgit2's native transport (from --transport native), as gwz 1.0 did; omit --transport native to use gwz's transport`
  - `gwz: note: using libgit2's native transport (from GWZ_TRANSPORT=native), as gwz 1.0 did; unset GWZ_TRANSPORT, or pass --transport gwz for one command, to use gwz's transport`

- **Refusals,** after `gwz: ` with exit 2 in the CLI:

  - `gwz.transport in <where> must be gwz or native, not "<value>"` and, for a key with no value, `gwz.transport in <where> must be gwz or native, and has no value`, each followed by `; <remove>, or fix it; --transport or GWZ_TRANSPORT decides without it`;
  - `could not parse <file>, or a file it includes, for gwz.transport: <cause>; fix the file and line it names; --transport or GWZ_TRANSPORT decides without it`, where `<cause>` is libgit2's message, which names the file and line, shown with its control characters escaped, as a path is.

  - `<origin>` is `from --transport`, `from GWZ_TRANSPORT`, `from gwz.transport in <where>` or `default`.

  - Each skipped file adds `; skipped unreadable <file>`.

- **JSON:** `meta.transport_setting` is `{"transport": "gwz" | "native", "source": "flag" | "environment" | "global_configuration" | "default", "file": string or null, "included": bool, "ignored": [{"scope": "root" | "member", "member_id": string or null, "file": string, "included": bool, "value": string or null}], "skipped": [{"file": string}]}`.

Otherwise it is present on the response of a command whose request is in transport scope. Other commands' output never carries it, and neither does an error record whose `meta` is null.
