# GWZ transport — sequenced virtual-stream design

Date: 2026-09-24. Status: **DRAFT interface design for dual review; no implementation or activation**.

This design implements [Q1–Q9](GwzTransportSequencedStreamRequirements.md) and the operator's [sequencing direction](GwzTransportSequencedDeliveryDirection.md). It is a new object after the [stopped profile-3 design](../../dev-docs/GwzTransportV3ReorderingDesign-Verdict.md), not a correction to its host-scheduler terminal barrier. The accepted [placement design](GwzRemoteTransportPlacementDesign.md) continues to control endpoint authority, Bind/Bound, request registration, bounded cleanup and pool policy. For profile 3 only, this document supersedes [GwzRemoteTransportDesign.md](GwzRemoteTransportDesign.md) §2's carrier-adapter “Ordered delivery” responsibility and in-process “same ordering” sentence, and the placement design's corresponding same-stream carrier-ordering assumption. The profile-3 carrier delivers bounded frames and reports disconnect; the virtual-stream service owns reconstruction. Profiles 1/2 retain their ordered-carrier contract. The file-stream API, Git protocol and physical carrier remain unchanged.

## 1. Negotiated shape and identity

The candidate uses **transport profile 3**, which has never been released. Bind and Bound keep bootstrap `Envelope.version=1` and `stream_id=0`. A host selecting sequenced delivery offers `Bind.versions=[3]` only and verifies `Bound.version=3` before any stream frame. An older endpoint rejects UnsupportedVersion before Git, credential or pool effects; there is no silent downgrade. Profile-1/2 validation and behavior remain unchanged. CheckIdentity is legal in profiles 2 and 3 with the same explicit-key body and terminal rules, superseding the accepted placement §6 phrase “v2-only” for profile 3 only.

The Taut `Envelope` gains one optional, missing-ok integer field **`message_seq` at tag 5**. It has no value on bootstrap and profiles 1/2, and is mandatory positive on every profile-3 message with positive `stream_id`. No new Data framing or core service method is introduced. The receiver derives the sending direction from its pinned bound Port role; an Envelope cannot assert or change it. Each `(session_id, stream_id, sending direction)` has its own sequence starting at 1. The sequence counts **all** kinds, including Open/CheckIdentity, Data, Window, Flush/Flushed, EndWrite, Close, Closed, Cancel and failure. The first initiator frame for a stream is Open or CheckIdentity at sequence 1. The endpoint's first response frame starts its independent sequence at 1. A sender never emits a frame after its own terminal and never reuses a sequence. Checked integer overflow fails that binding before emission.

The sequence is assigned atomically when a logical frame enters the transport's bounded outbound ownership, **before** any host queue or dispatcher can see it. One sequencer per stream/direction covers both mux-generated lifecycle controls and StreamMachine-generated data/flow controls. On outbound WouldBlock, no frame or sequence is committed. Once emitted, a frame keeps its sequence through queueing, retry and delivery; it cannot be renumbered to make a graceful close pass an earlier frame. The terminal's own sequence is its sending-direction final watermark: a graceful terminal with sequence N needs all preceding `1..N-1` applied; an abortive terminal with N may explicitly supersede still-missing predecessors below N. No separate final-message-number field is needed. Existing Data and final byte offsets independently prove byte continuity.

The initiator still allocates positive stream IDs once within a binding; Open and CheckIdentity share the namespace. This profile fixes a 4096 lifetime-ID ceiling and a 64 active-or-provisional-or-draining-stream ceiling per binding. A receiver tracks *seen IDs*, not only the highest ID, so Open 2 may be admitted before fresh Open 1. A 4097th allocation refuses locally; IDs never wrap. A provisional record for a pre-Open frame consumes an active slot and a bounded lifetime record but has no route authority. A higher opening ID does not retire a lower unseen one. The host must pin the exact sender and intended peer Port generation for every item regardless of the peer's profile, so an older port's foreign-session `Ok` cannot acknowledge delivery to the intended peer. A profile-3 receiving Port returns a distinct non-disconnecting WrongSession outcome for a foreign session.

## 2. Receive, apply and report

The receiver first validates bounded encoding/typed shape, negotiated version, session, positive stream ID, registered request and sequence range before allocating reassembly storage. It checks request/operation/endpoint authority **before executing** an Open/check or any buffered successor. An unknown stream's message with sequence greater than 1 may be held as a *provisional* frame under that registered request, with no Git, credential, pool, route or observation effect. When its Open/check sequence 1 arrives, the receiver validates the full context, converts the charged provisional record into a route, admits the opening action to the bounded action queue, then applies contiguous buffered successors. A correctly correlated initiator Cancel may instead abort that provisional ID before Open/check arrives: it seals the ID without endpoint work, resolves the pending opening as `Superseded`, and contains a later matching sequence-1 opening without applying it. It may not bind an operation/endpoint chosen by the Cancel body; those remain checked against the registered request and any later opening. If sequence 1 never arrives and no such validated abort completes by the fixed gap deadline, the binding fails; an ordinary provisional frame cannot create a route by itself.

For a known stream, a frame at the next expected sequence is applied through the **existing** mux/StreamMachine transition and byte-offset grammar, then the contiguous buffered prefix is applied. A higher sequence is stored but has no state-machine or file-stream effect yet. A sequence already buffered with different canonical bytes is Protocol; an identical buffered duplicate reuses its pending receipt. A sequence already applied is `AlreadyResolved`, never re-applied or treated as a new action receipt. The bounded opening identity and terminal identity remain in the stream's lifetime record; older applied Data/control hashes need not be retained because their sequence cannot cause effects again. Unknown or conflicting context is Protocol, not a reason to create a replacement route.

Profile 3 adds a host-facing **delivery ticket** rather than changing the application's read/write stream API. Submitting a frame may return `Buffered` once the peer owns it in a bounded reorder slot, but this is **not** peer application. The ticket resolves exactly once as `Applied`, `Superseded`, or typed failure when the receiver applies, aborts or rejects that sequence. Open/check resolves `Applied` only after its validated action queue and route admission; a gap-buffered control cannot masquerade as that opening receipt. The host retains tickets and their cleanup charge even if an application waiter is cancelled. The host may have several bounded tickets for one stream outstanding and must not await a later ticket in a way that prevents dispatch of an earlier missing sequence. Profile-1/2 `Port::deliver` and their receipts keep their existing behavior; a profile-3 facade may provide an adapter that awaits the ticket result, but the independent host pumps use the nonblocking submit/ticket form.

## 3. Terminals and the two byte directions

Every direction has its own message sequence; the protocol does **not** impose a total order across the two directions. Ordinary Window, Data, Flush, Flushed and EndWrite apply only when their sending-direction prefix is contiguous. Data.offset must equal the next received byte offset when applied; EndWrite.final_offset and Close.final_offset must match the resulting byte count. The existing close handshake still supplies cross-direction prerequisites: Closed cannot report graceful completion before the initiator's real Close and required EndWrite have been processed. A graceful EndWrite, Close, Closed or successful identity terminal waits for all earlier messages in its own direction; if a predecessor is missing, the terminal remains buffered and no EOF, flush completion, healthy lease return or success is reported.

`OpenFailed`, `IdentityCheckFailed`, `Failed` and legal `Cancel` are **abortive**. After the opening/context is known, a validated abortive terminal at sequence N may fix the failure without waiting for lower missing sequences. The provisional Cancel exception above may abort an opening before it has authority, without acquiring a route. An abortive terminal resolves buffered predecessors below N as `Superseded`; any later arrival with a lower sequence is validated for binding/context, consumed without effect and reported `Superseded`, not `Applied`. A frame above N from that sending direction is Protocol because the sender must not emit after terminal. The opposite direction may have already generated or delivered frames: both sides seal new work and keep charged cleanup until its in-flight frames are delivered or atomically aborted. A correctly correlated late frame in either direction cannot change the fixed failure, facts or lease outcome. Bytes already consumed by a Git host are not rolled back; the Failure effect and facts retain their existing meaning. A successful Closed has no such skip authority. An endpoint may release a healthy pooled connection only after the full graceful handshake and cleanup fence; an abortive outcome disposes or otherwise handles the connection under the existing pool-health rules.

After terminal, a bounded lifetime record holds request/operation/endpoint/session identity, the terminal's direction, sequence and canonical digest. Exact terminal replay is idempotent but is not a second `Applied` receipt. Superseded older frames are non-authoritative. A conflicting terminal, impossible successor or a frame for a different registered context fails closed. A request remains registered while tickets, queues, endpoint work or lease cleanup remain; user-visible completion alone does not release those owners. A finite cleanup deadline fails the binding and wakes waiters if ownership cannot drain. No active Git exchange is transparently replayed.

## 4. Reorder capacity and progress

Reassembly counts **encoded frame bytes plus decoded allocation** against the negotiated per-direction queued-byte/frame limits, in addition to the stream's existing receive-window accounting. Profile 3 caps buffered out-of-order frames at 8 per stream/direction and 32 per binding/direction; active, provisional and draining streams together cap at 64. It reserves one worst-case admitted frame charge and one frame slot, outside those reorder counts but within the negotiated queue, for a missing next-expected predecessor. Bind 3 refuses if the negotiated limits cannot support one buffered frame, that predecessor reserve and the existing control reserve simultaneously. A lower missing sequence uses the reserve ahead of higher ones; a higher frame that cannot be admitted returns WouldBlock without consuming a sequence at the receiver. The host reports the lowest missing sequence, schedules it fairly across streams and keeps processing unrelated ready streams. This is a liveness rule, **not** a same-stream FIFO correctness rule. A gap's fixed 30-second deadline starts when its first higher-sequence frame is buffered; it is independent of that frame's enqueue-to-peer-admission deadline, which has already ended at `Buffered`. The gap deadline cannot be reset by more higher frames, duplicates or cancelled application waiters. Expiry or an unresolved saturated reserve fails the binding rather than waiting forever or acknowledging a graceful terminal.

The reassembly store, pending delivery tickets, request records and 4096 lifetime-ID records have separate explicit charges; implementation must prove their aggregate ceiling before activation. The 512-byte-per-ID candidate record from the stopped design is not presumed sufficient for this new state; a representation/budget proof may lower the lifetime cap before this profile is frozen. No buffered pre-Open frame receives a special unlimited reserve. Malformed, unauthorised, oversized or beyond-window frames fail before effects. Carrier loss fails owned streams and resolves every ticket; dropping an application future cannot strand a buffer slot. A separate-process or iroh carrier is not claimed, but an eventual carrier can map the same `Buffered`/`Applied`/`Superseded` outcomes to acknowledgements without changing the file-stream semantics.

## 5. Compatibility and proof gate

The old profile-1/2 path retains its present FIFO-dependent behavior and does not receive profile-3 frames. The taut generator must preserve decoding of retained messages and the profile-1/2 semantic contract when adding optional tag 5; generated Rust/Python projections must be qualified together, with no hand-edited generated code. The field must be semantically absent on bootstrap and profiles 1/2; encoding it as CBOR null is acceptable only if retained-reader compatibility tests prove the old projection accepts it and preserves the old message semantics. Otherwise the generator must omit the field or a compatible new taut wrapper must be chosen before activation. Neither this design nor a successful Bind alone enables the per-key concurrent host schedule; the host must implement ticket ownership, generation pinning, deadlines and bounded gap progress first.

Required deterministic cases: send Open 2 before Open 1; deliver a same-stream Window/Flushed after a higher-sequence Failed and prove the failure absorbs it; deliver Closed before earlier Data/EndWrite and prove no early success; receive a post-opening frame before Open sequence 1; fill the reorder budget while its missing predecessor is ready; duplicate and conflicting sequences, an expired gap, ID 4097, a foreign generation, profile-2 refusal of a profile-3-only Bind, and two streams sharing one binding with one failing. Seed-replayable Monte Carlo tests permute message deliveries independently in both directions and across streams, randomize write chunks and read sizes, and compare every reconstructed byte and terminal outcome against a reference ordered stream. The failure report prints the seed and case index. The test oracle must distinguish `Buffered`, `Applied`, `Superseded` and failure; merely counting received envelopes is insufficient.

GO on this document would accept the **design contract only**. Before implementation, carry the accepted Q-rules and protocol scope into authoritative `GWZDesign.md` and baseline `GWZRequirements.md`, then implement the taut projection and stream/mux state TDD-first. Core/host integration, Python caller surface, platform checks, physical wire and release each retain their separate gates.
