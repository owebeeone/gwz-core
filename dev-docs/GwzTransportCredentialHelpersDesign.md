## 1. Decisions

§8 classifies each difference from 1.0.17 by the decision it follows from. This design's own choices that can break a setup working on 1.0.17 are §12's questions.

1. **One way to ask.** The transport asks the configured helpers only by spawning `git credential fill` under CS3.4's rules (§3). The direct `gh auth git-credential get` spawn goes. `gh` answers when git's configuration names it, as `gh auth setup-git` writes it, which is how it reached 1.0.17 (REQ:94-96).
2. **Only to answer a challenge.** A lookup answers a discovery 401 whose challenge offers `Basic`, or on Windows `NTLM`, `Basic` or `Digest` (TR1.8). A 404, and a push before its challenge, no longer start one (§2.1).
3. **For the URL that challenged.** The helper is asked for the URL whose 401 the credential answers, after discovery's validated redirects. The credential goes to that URL only, and a redirect after the challenge ends the operation, as §3.19 says; OQ4 recommends following it under discovery's rules (§2.2, §5).
4. **Once per route.** One lookup per route in an operation, held with the route and zeroized when it retires. It is never sent after a rejection, nor to another URL, route or operation (§5).
5. **Pooling.** A connection that carried a credential serves only that credential's route (§6).
6. **No retry, no store, no erase.** A rejected credential fails at once (§7). `git credential approve` and `reject` are never run, as 1.0.17's lookup runs `get` only (`CRED:387-428`) and CS §5.8 requires (CS:375).
7. **No prompts,** as §3.19 sets. OQ3 recommends letting a helper show its sign-in window (§3).
8. **Waits and codes.** Waiting for a helper slot counts against the Open's allocation deadline, not the helper's bound (§3.3; OQ6). Each outcome has its own message under OQ7 (1), while under OQ7 (2) M8 shares M2's, and 1.0.17's codes and clone treatment wherever 1.0.17 had the case (§11); OQ5 proposes one new code, for the bounds.

## 2. When the transport asks

### 2.1 The challenge
- Discovery starts anonymously for both services, as 1.0.17's first request does: libgit2 sends a credential only after a challenge (`LG/http.c:370`; `LG/httpclient.c:561-567`). GitHub answers a private repository's anonymous discovery with a 401: 1.0.17 offered a helper's credential there (a 1.0.17 `--verbose` row, `offered=true`, recorded in the working draft `GwzRemoteTransportBugReport.md`, which is not committed).
- A lookup runs only when the final discovery response is a 401 and one of its `WWW-Authenticate` fields names a scheme the platform answers with a helper's credential:
  - `Basic` on macOS and Linux, the only scheme 1.0.17 completes there: `libgit2-sys` 0.18.8 defines neither `GIT_NTLM` nor `GIT_GSSAPI` (its `build.rs:256-268`, as in the fork's `git2-rs/libgit2-sys/build.rs`), so NTLM and Negotiate are stubs (`LG/auth_ntlm.h:16-30`; `LG/auth_negotiate.h:15-25`; `LG/auth.c:66-73`);
  - `NTLM`, `Basic` or `Digest` on Windows. TR1.8 states how the credential answers each, over WinHTTP's scheme order (`LG/winhttp.c:139-151`).

  Each field is one challenge, and its scheme is the field's first token, compared without case, as libgit2 reads it (`LG/httpclient.c:203-208, 281-292`).
- **No lookup for:**
  - a 401 that names no such scheme, or none (M6). On Windows a `Negotiate`-only challenge takes the logon session's credentials, with no helper asked (TR1.8, OD16);
  - a 404, which keeps HTTPS §7's refusal path. Today a 404 also starts the gh retry (HTTPS:121-122; `TH/request.rs:193-197`; `TH/https_endpoint.rs:351-367`), where 1.0.17 asks only on a 401 (`LG/http.c:265-269`);
  - a POST's 401, never replayed (HTTPS:138-139), as in 1.0.17 on macOS and Linux (`LG/http.c:275-278`): M11. On Windows WinHTTP asks the callback and replays the POST (`LG/winhttp.c:1243-1256`) without the body it has already sent (`:1144-1146`); TR1.8 records that case;
  - a push before its challenge. Today receive-pack asks gh before its first request (HTTPS:140-143; `TH/request.rs:158-162`); it now starts anonymously, as fetch does. A server that serves receive-pack discovery anonymously and challenges only the POST fails the push with M11, as on 1.0.17 on macOS and Linux;
  - any response while the policy is `Disabled` (§2.3).

### 2.2 The URL
- Call U the URL of the request the 401 answered: the repository base that discovery reached after its validated redirects, at most five hops, HTTPS only, with no userinfo, query or fragment (HTTPS §5; `EP/https_worker.rs:469-510`; `EP/https_destination.rs:95-128, 179-200`). Amendment 2 calls this "the transport's one validated discovery redirect" (C2).
- The helper is asked for U. The authenticated discovery request goes to U itself, not to the original URL, and follows no redirect, as §3.19 says (OQ4). Today the gh attempt restarts at the original URL (`EP/https_worker.rs:307-316`) and looks gh up again at each hop (`:319-346`).
- The endpoint keeps U, and the schemes the 401 offered, with the operation's retained first attempt (`TH/https_endpoint.rs:216-226, 351-367`), whether or not it keeps the challenged connection.
- **What reaches git.** URL text reaches git only inside the `url=` line, percent-encoded exactly as the parsed URL serializes it, and git refuses a component that decodes to a newline: in the probe, `%0A` in a path or a username made git exit 128 before any helper ran. A decoded carriage return, `%0D`, git refuses only after it has started the helper with part of its input written. So the destination also refuses a path, and under OQ1 (b) a username, that decodes to any control character, before any Open. Today `Destination::parse` checks the raw text and the encoded path only (`EP/https_destination.rs:16-18, 188-198`), so `%0A` passes it. The new check lives in the shared shape check, `validate_url_shape` (`:179-202`), which `parse` and `redirect` both reach (`:95-133, 163-177`), so a redirect's `Location` meets it too.
- As on 1.0.17 on macOS and Linux, and as in git, a remote may redirect discovery to another host and have the helper answer for that host. The credential then goes to that host alone.

### 2.3 The policy
- `CredentialHelperPolicy` applies as 1.0.17 has it. `AllowConfigured`, the default (`GB/backend.rs:4-8, 41-50`), permits lookups. `Disabled` (`without_credential_helpers`, `:52-61`) maps to the anonymous policy (`GB/transport_binding.rs:106-113`): no `git` is spawned, and a 401 fails with M7. Only gwz-core's own tests build a `Disabled` backend; the gwz CLI and gwz-py never do, and `gwz-core/docs/GitBackend.md:25-27` documents it for embedders.
- In 1.0.17 the policy gates the helper only (`GB/transport_support.rs:265-271`), and the default-credential branch runs under either policy (`:272-274`). TR1.8 keeps or changes that split for its own offer.
- `--transport native` (TR1.5) and a caller without a host context (TR2.11) take the native route, where 1.0.17's callback runs unchanged until CS3.4's native half, in 1.2.0 (amendment 2 §3.15).

## 3. The lookup

### 3.1 Command and input
- `git -c credential.interactive=false -c core.askPass= credential fill`, spawned directly, without a shell. Its input is one `url=` line, U as §2.2 states, then a blank line. Under OQ1 (b) the URL's username goes only inside that line, never as a `username=` line and never re-serialized from a decoded field. OQ3's options (a) and (b) drop `-c credential.interactive=false`.
- `core.askPass=` is CS §5.8's (CS:367-373), which CS3.4 implements: with it and `GIT_TERMINAL_PROMPT=0`, git itself never prompts, on any version. CS3.4's step and amendment 2 list only the other two settings (C1).
- git derives `protocol` and `host`, with a non-default port, keeps `path` only under `useHttpPath`, and applies `credential.*.username`. In the probe a helper received `protocol=https` and `host=127.0.0.1:8443`, and `path=owner/my repo.git` only with `useHttpPath`. Its `GIT_CONFIG_PARAMETERS` carried both `-c` settings, so a helper that reads `credential.interactive`, such as the Git Credential Manager, does not prompt either.
- On POSIX, `git` is the first `git` on the snapshot's `PATH`, absolute entries only. TR1.8 states how `git` is found and started on Windows. git starts the helpers, so TR2.2's two helper forms and helper paths with spaces are git's to resolve.
- Running `git credential fill` is not the Git CLI transport the owner ruled out (REQ:116-118): it moves no repository data and opens no connection.

### 3.2 Environment, configuration, directory and process group
- The environment is `env_clear()` plus the runtime's snapshot (`TH/endpoint_environment.rs:38-69`; under 1.1.0 S6.1's variant, the caller's), less `GIT_ASKPASS`, `SSH_ASKPASS`, `GIT_DIR`, `GIT_COMMON_DIR` and `GIT_WORK_TREE`, plus `GIT_TERMINAL_PROMPT=0`. Nothing else is added: `GH_PROMPT_DISABLED` (`EP/https_auth.rs:297`) was the gh spawn's.
- The working directory is `/`, or the system drive's root on Windows (C10). With `GIT_DIR` dropped (C11), git reads no repository's local configuration on POSIX, as 1.0.17's `Config::open_default()` (`GB/transport_support.rs:267`) reads none; TR1.8 states the Windows bound, where the root is writable.
- **Configuration scope.** The lookup reads git's system, global and XDG files and `GIT_CONFIG_*` (D1). As on 1.0.17, it reads no repository-local file, even for a member gwz works in, and no `includeIf "gitdir:…"` applies: 1.0.17's libgit2 skips every conditional include without a repository (`libgit2/src/libgit2/config_file.c:727-728`). The remedy, which M2 and the notes give: keep credential settings in the global file, outside `includeIf`.
- `git` starts as the leader of a new process group, this design's own choice (OQ3), and every kill signals the group. In the probe, killing `git` alone left its helper running, reparented to PID 1, in `git`'s group. A process in the spawned group that reads the terminal is outside the foreground group, so the terminal stops it, and the bound kills it. A process another session starts, such as gpg-agent's pinentry, is in no spawned group: it is neither stopped nor killed, and may stay on the terminal after M4, as on 1.0.17. TR1.8 states the Windows equivalent, a job object.
- **Its cost.** A terminal's Ctrl-C now reaches gwz's group only. gwz-cli installs no signal handler (a search of gwz-cli's and gwz-core's sources finds no `ctrlc`, `signal_hook` or `tokio::signal`), so when it exits on Ctrl-C, a helper still waiting outlives it until the helper ends; one stopped on the terminal is sent SIGHUP when its group is orphaned. Today's gh spawn shares gwz's group (`EP/https_auth.rs:286-302`). OQ2.

### 3.3 Bounds and cleanup
- **The bound.** The interaction allowance, 120 s and fixed: every Open from the CLI and gwz-py sets it (`TH/session/driver.rs:626-634`; `POOL/mod.rs:50`), and an Open with a shorter interaction deadline shortens it (`EP/https_worker.rs:241-245`). It starts when the lookup starts. The network clocks do not run during it.
- **Admission.** The endpoint's 8 helper permits, then the host context's 8 helper slots, which every endpoint its driver opens shares (`EP/https_auth.rs:27-35`), both awaited and both charged to the Open's allocation deadline (OQ6): up to 30 s, less what the anonymous attempt used, since the authenticated retry gets no fresh allowance (HTTPS:126-135), or less again when the caller's own allocation deadline is nearer (`TH/session/driver.rs:117-127, 621-623`). A wait that runs out fails with M10, starts no helper and sets no latch. Today the permit wait consumes the helper's bound (`EP/https_worker.rs:329-333`), and the slot is tried once and fails at once with `Capacity` (`EP/https_auth.rs:278-284`), retained unreaped children included (`:27-28`). Awaiting it, as the reuse design awaits it in 1.2.0 (REUSE:147, C9), folds that `Capacity` outcome into M10. CS3.4's "takes no `gh` slot" (SP:411) stays its native half's rule.
- **Kill** at the bound, on the operation's or the endpoint's cancellation, and on drop. A `git` not reaped within the 500 ms grace (`EP/https_auth.rs:26`) is retained with its slot, and reported as pending cleanup (`:352-387, 470-503`).
- **Completion.** The lookup completes when `git` exits and its stdout is at EOF. It then closes stderr's read end, so a helper's background child that writes there afterwards gets a broken pipe, as from any closed pipe; nothing kills that child on success. Today the lookup also waits for stderr's EOF (`EP/https_auth.rs:336-339`), which such a child can hold open after `git` has exited, and 1.0.17 waited for it with no bound (`CRED:451`).
- **Pipes.** The input is written, then closed; a broken pipe is not a failure (`EP/https_auth.rs:390-407`). stdout is bounded at 16 KiB, and overflow fails the lookup with M8. stderr is drained and discarded; today it is kept, up to 16 KiB (`:334-341`).

### 3.4 Output and secrets
- Only `username` and `password` are read. Other lines are tolerated and never logged.
- Both must be present. Either may be empty, as git and 1.0.17 accept (`CRED:336-357`; probe: `password=`); today's parser requires both non-empty (`EP/https_auth.rs:538-543`). A control character once one trailing CR is dropped, a `:` in the username, output that is not UTF-8, or output without a final newline is refused with M8 (`:506-548`).
- **Buffers.** stdout's buffer, pre-sized to its 16 KiB limit so that no growth leaves a copy, and the scratch buffer stderr is drained through are zeroize-on-drop types. Every exit path therefore zeroizes them: completion, the bound, cancellation, overflow, an abandoned branch of the lookup's select and an unwind. Today only a completed stdout is zeroized (`EP/https_auth.rs:348`). `Secret` zeroizes on drop and has no Debug form (`:231-259`).
- The Authorization value is built for each request from the `Secret`, in a zeroizing buffer, and handed to hyper marked sensitive (`EP/https_worker.rs:717-725`). Today `Secret::header` leaves its base64 and header strings unzeroized (`EP/https_auth.rs:237-245`). Hyper's copy is a library copy (HTTPS:169-171).
- The environment copy the spawn takes is not zeroized, as for the gh spawn today; the snapshot's zeroization is CS1.9's, in 1.2.0.

### 3.5 The gh route, and CS3.4's native half
- The gh spawn (`lookup_owned`, `EP/https_auth.rs:261-388`) becomes this spawn. Its owner, slots, bounded pipes, kill-and-retain cleanup and `Secret` stay. The program, arguments, input, environment filter, process group, slot waits, completion rule, buffers, stderr handling and parser change, and `https_auth::Config` names `git`, not `gh` (`TH/endpoint_environment.rs:58-61`).
- The command line, the environment filter and the parser form one module, which CS3.4 calls from the native callback in 1.2.0. Both halves then run one spawn.
- The process-globals allowlist's `permanent` entry for the gh spawn (`gwz-core/scripts/checks/process_globals_allowlist.json:16`) names this spawn instead. The native route's `Cred::credential_helper` entry (`:28`) stays `debt` until CS3.4.
- The wire values `AuthPolicy::Gh` and `AuthMethod::Gh` (`gwz-transport/src/protocol.rs:140-146, 392-398`) stay, and mean the configured helpers. Users already see the method as `helper` (`GB/transport_observations.rs:111`). Renaming the identifiers is S7.1 (1.1.0)'s protocol decision.

## 4. Outcomes

| Outcome | Wire failure | Message | Then |
|---|---|---|---|
| A credential | — | — | Sent to U (§5) |
| No credential: `git` exits non-zero with no fields, whatever the reason: no helper answered and prompting is off or unavailable, a helper said `quit`, or git failed, for example on its configuration | `Authentication` | M2 | Nothing sent |
| Unusable: the pipe to `git` failed; stdout over 16 KiB; malformed output (§3.4), or a field missing after a zero exit | `Authentication`, the pipe's included | M8, naming the cause (OQ7 (1)), else M2's text | Nothing sent |
| The bound passed | `Timeout`, setup cause `Interaction` | M4 | Group killed; latched under OQ3 (c) only |
| No slot before the allocation deadline | `Timeout`, setup cause `Allocation` | M10 | No helper started; never latched |
| No `git`, or a `git` that is found but cannot start | `Unavailable`, with setup cause `NotFound` when none is found | M1 | Latched |
| Cancelled mid-spawn | `Cancelled`, or `Io` while cleanup is pending | cancelled | Group killed; retained if unreaped |
| A 401 after the credential | `Authentication`, `authenticated = false` | M3 | §7 |
| A 403 after the credential | `RepositoryRefused` | M9 | No second lookup |
| A redirect after the challenge, under OQ4 (c), or (b) to another origin | `UnsupportedOperation` (HTTPS:313) | M5 | §5 |
| A 401 naming no scheme gwz answers | `Authentication` | M6 | No lookup |
| Helpers disabled | `Authentication` | M7 | No lookup |
| A POST challenged after an anonymous discovery | `Authentication` | M11 | No lookup, as 1.0.17 on macOS and Linux |

- **Latched.** The endpoint records a missing or unstartable `git` in its per-operation record, and every later lookup in that operation fails at once with M1. A timeout latches the same way, for the same host and port, only under OQ3 (c), where it means a hung helper; under (a) or (b) it may mean a slow user, so every lookup gets its own bound (§8). N members behind one hung helper then cost one bound, not one per eight members. Every other outcome is its route's alone.
- **Kills.** Under OQ3 (a), or OQ2 (b), "group killed" reads "`git` killed": its helpers are in gwz's own group.
- **Wire codes.** Every lookup failure but M1, M4, M10 and a cancel crosses as `Authentication`, a pipe failure included: the pipe to `git` is local, not the network loss `Io` names (HTTPS:303), which must stay unsuppressed (HTTPS:332-334). M6's `Authentication` is the 401's own (HTTPS:315). With the facts, the core's own policy (M7) and the failing request, a discovery or a POST (M11), these select §11's codes (OQ7).
- **Windows.** For TR1.8's precedence, no credential, unusable output and a missing or unstartable `git` count as no helper credential, as 1.0.17's callback falls through after any helper failure (`GB/transport_support.rs:265-274`). A timeout or a cancel ends the request.

## 5. Holding and sending the credential
- **Held** with the route: the endpoint's write-once record per operation, original URL and service family (`EP/https_policy.rs:60-115`), beside U. An operation is the endpoint's registration of one request, which owns its routes (`TH/https_endpoint.rs:176-195`): one CLI command, or one gwz-py operation. It is zeroized when the operation's routes retire (`:112-114`), and never cached across operations.
- **Sent** only on that operation's requests whose repository base is U:
  - the discovery request, sent once to U, on the challenged connection when it is clean (GHA), else on a new one;
  - the route's later requests: its POSTs, which go to the pinned base (`EP/https_worker.rs:313-315`), and later discovery requests that reach U.
- **Never sent** to another base (another scheme, host, port or path), another route or operation, as `Proxy-Authorization` (HTTPS:236), or after U rejects it.
- **A redirect after the challenge.** A 3xx answer to a request that carried the credential ends the member's operation with M5. No request goes to its `Location`, and its connection is discarded. This is §3.19's rule; 1.0.17 follows the redirect (D13), and OQ4 recommends following it under discovery's rules. Only OQ4 (d) would send the held credential to another path, on the same origin.
- **Once per route,** as 1.0.17's libgit2 keeps one credential for all of a remote connection's requests (`LG/http.c:155-161, 370`). The alternative, a lookup per request (HTTPS:163-164 today), would spawn `git` and its helpers for every negotiation POST, and a helper that asks its user each time, such as a password manager's, would ask that often.
- **Facts** are unchanged: method `Gh`, shown as `helper`; `credential_offered` once the Authorization reaches the send path (`EP/https_worker.rs:418-420`); `authenticated = false` on a 401 after offering, otherwise unknown (`:454-456`).
- **Never logged.** No helper output, credential or Authorization value reaches an event, error, observation or evidence file (HTTPS:166-167).

## 6. Pooling within one command
- **A credential scopes its connection.** When a lookup succeeds, the endpoint mints an opaque scope for the credential from its ID source, never derived from the secret. A connection that has carried that credential is pooled idle only under its scope, and leased only to a request carrying the same credential: the same route, in the same operation. Anonymous requests and other routes never get it.
- A connection that has carried no credential is unscoped, and any request may lease it. The first credential it carries scopes it; the challenge carry (`EP/https_worker.rs:540-547`) is one case.
- Scoped connections count against the per-host and total caps, stay evictable while idle (`POOL/allocation.rs:104-129`), and are discarded when their route retires.
- **Mechanism.** The pool's HTTPS identity carries the scope (`POOL/mod.rs:133-146`; idle matching compares identity, `POOL/allocation.rs:19-24`). A release may move an unscoped connection to a scope, never back. That is a gwz-transport change, for 1.1.0's gwz-transport release.
- HTTPS §6 keys a connection by host and port alone and lets every request use it (HTTPS:249-251, 262-263). It gains this scope (C3), and GHA:56-57 gives way for a connection that carried a credential (C4). TR1.8 applies the same scope to a connection that completes a `Negotiate` or `NTLM` exchange.

## 7. Retry
- An authentication failure is not retried (RETRY:171-172, 196-198). A 401 after the credential fails the route's request with M3. The helper is not asked again for that route in that operation, and the credential is not sent again.
- 1.0.17 reruns the helper and resends its answer on every 401, until libgit2's limit of 15 requests per stream, then fails "too many redirects or authentication replays" (`LG/http.c:418-441`; `LG/http.h:14`).
- Each route asks once: a fetch of N private members on one host runs N lookups, as 1.0.17 runs one per remote.
- A setup retry of the connect that will carry the credential (RETRY S3.5) reuses it, with no new lookup. Helper outcomes are not setup failures, so the per-key machine (RETRY §5) never sees them.
- The next operation looks up afresh.
- OD18 (amendment 2 §3.20) starts a key's first wave of connects in parallel. It governs connects, and a 401 is no setup failure, so neither rule here changes.

**Migration notes.** Release text for 1.1.0; the table after the notes maps each one to the rows and the open question behind it.
- **N1. HTTPS sign-in runs git.** For a repository that asks for a password or token over HTTPS, gwz runs `git credential fill`, which asks the credential helpers configured for git, so `git` must be on PATH for private HTTPS repositories. Public repositories need no `git`.
- **N2. git chooses the helpers,** as `git fetch` does: every helper your git configuration names for the URL, in order, from git's own system configuration (for example Homebrew's `osxkeychain`), your global configuration and `GIT_CONFIG_*`. gwz 1.0 read fewer, so a helper it never ran may now answer first, with a stale credential, or with a valid one for another account: a fetch then fails, or a push is made as that account. macOS may ask once for keychain access.
- **N3. Where settings are read.** As in gwz 1.0, a credential setting in a repository's own `.git/config`, or under any `includeIf`, whether `gitdir:` or `hasconfig:remote.*.url:`, does not apply, even for a repository gwz is working in: gwz reads only git's system and global configuration and `GIT_CONFIG_*` variables. Keep credential settings in your global git configuration, outside `includeIf`.
- **N4. What a helper is asked.** A configured `credential.username` now reaches the helper, a URL with an IP address names its host, and with `useHttpPath` the path arrives decoded. A helper may hold no credential under these names: run `git ls-remote` with the repository's URL to store one. A helper named by a relative path is resolved from the root directory, so `!./bin/x` runs `/bin/x`: name helpers by absolute path or through `PATH`.
- **N5. Prompts.** gwz never prompts for an HTTPS credential, and git does not prompt for it. A helper that asks through another program, such as gpg-agent's pinentry, may stay on screen after gwz gives up. Whether a helper may prompt, the text is one of these:
  - "A credential helper may show its sign-in window, or ask on the terminal, during a gwz command, as gwz 1.0 allowed, once for each repository that needs one."
  - "A credential helper may show its sign-in window during a gwz command, as gwz 1.0 allowed. A helper that asks on the terminal is stopped there, and fails after 120 seconds."
  - "Credential helpers may not prompt. When one needs you to sign in, sign in once with git (`git ls-remote` with the repository's URL), then rerun gwz."

  Where a helper may show a window, a server's redirect can open one for a host you did not name: sign in only where you expect.
- **N6. Waiting.** Its first sentence is one of these:
  - "gwz waits 120 seconds for a credential helper, then fails the repository; the helper may stay open."
  - "A helper that does not answer within 120 seconds is stopped, and its repository fails."

  Its second is one of these:
  - "gwz runs at most eight helpers at once; a repository that cannot start one within 30 seconds fails, and a rerun picks it up."
  - "gwz runs at most eight helpers at once; a repository that waits for one spends part of its 120 seconds, and fails when they run out."
- **N7. Rejected credentials.** A rejected credential fails its repository at once, and gwz does not ask the helper again in that run. As in gwz 1.0, gwz neither stores nor erases credentials. Renew a credential where it is kept: with a sign-in tool, sign in again; for a stored password or token, run `git ls-remote` with the repository's URL, which fails once and erases the old one, then again to enter the new one.
- **N8. gh.** `gh` is used only where git's configuration names it, as `gh auth setup-git` writes. To renew its token, sign in with it: `gh auth login` or `gh auth refresh`.
- **N9. Redirects.** During discovery, a helper is asked for the URL gwz sends the credential to, on every platform; on Windows gwz 1.0 asked for the configured URL. If your helper holds a credential only for the old host, store one for the new host, or point the remote at it. Where a helper may show a sign-in window, a redirect can make it ask about a host you did not name. After the credential is sent, a redirect, in one of these texts:
  - "is followed, and the new location gets its own credential, only if it asks for one";
  - "is followed on the same host, as above; to another host it fails the repository: point the remote at the new URL";
  - "fails the repository: point the remote at the URL the server redirects to";
  - "is followed, and on the same host your credential is sent again, as gwz 1.0 did; another host gets its own, only if it asks".
- **N10. NTLM.** On macOS and Linux, a server that offers both NTLM and Basic is now answered with Basic, where gwz 1.0 failed. Windows' schemes are listed with the Windows changes.
- **N11. The native transport.** `--transport native`, or `GWZ_TRANSPORT=native`, uses libgit2's native transport, with gwz 1.0's credential handling and without `git`.
- **N12. User names and passwords in remote URLs.** One of these texts:
  - "An HTTPS remote URL with a user name or password is refused: put the user name in `credential.<URL>.username` and the secret in a credential helper."
  - "A user name in an HTTPS remote URL is passed to your credential helper, as gwz 1.0 did; a password is refused: move it to a credential helper."
  - "Both are used as gwz 1.0 used them."
- **N13. Refused values.** A credential holding a control character, a user name holding a colon, and a repository URL whose path decodes to a control character are refused.
- **N14. Error codes.** As in gwz 1.0, an HTTPS credential failure reports `RemoteRejected` on fetch and push. On clone, as in gwz 1.0, a `private: true` repository is skipped quietly when no credential was available, a helper's answer was unusable, credential helpers were off, the server asked for authentication gwz cannot answer, or the server refused the account (HTTP 403); on macOS and Linux, gwz 1.0 failed some of these instead, when the server offered Negotiate or NTLM; `gwz --verbose clone` lists each one skipped, and why. A rejected credential (HTTP 401) fails the repository on clone with `GitCommandFailed`, as in gwz 1.0, and so does a redirect gwz refuses after sending a credential. A missing `git`, or one that cannot start, reports `ExternalToolMissing`. The sentence on time is one of these:
  - "A helper that did not answer in time, or could not start in time, reports `CredentialHelperTimeout`, and fails the repository on clone too."
  - "A helper that did not answer in time, or could not start in time, reports `RemoteRejected` on fetch and push, and on clone fails the repository with `GitCommandFailed`."

## 12. Open for the operator
- **OQ1. HTTPS remote URLs with userinfo (D16).** 1.0.17 passes a URL's username to the helpers and uses a URL's password before any helper (`LG/http.c:143-153`; `GB/transport_support.rs:268`). Azure DevOps' clone URLs carry the organisation as the username, and the Git Credential Manager picks the account by it. The transport refuses userinfo before any open (REQ G4, :182-188; DES §3.3, :190-202; `EP/https_destination.rs:179-186`), so those remotes break on upgrade, against OD13's parity.
  - (a) Keep the refusal, and list it in the notes.
  - (b) **Recommended.** Carry the URL's username in the Open's destination, in the field that today holds an SSH username only, `Destination.ssh_username` (gwz-transport `src/protocol.rs:674-680`; DES:200-202), which S7.1 (1.1.0) widens or renames. It holds the username percent-encoded, exactly as the parsed URL serializes it, and the endpoint's re-validation (DES §3.3) applies §2.2's decoded check to it. Pass it to `git credential fill` only inside the `url=` line: never as a `username=` line, never re-serialized from a decoded field, and never onto the request. The destination refuses a username that decodes to any control character, before any Open (§2.2). A password stays refused.
  - (c) Also use a URL's password, as decision 5 of 2026-10-02 does for SSH URLs (`dev-docs/CurrentProgramCheckpoint.md:259`). It would put a secret in the Open, which HTTPS §1 forbids (HTTPS:23).
- **OQ2. Ctrl-C and the helper's process group (§3.2).** (a) **Recommended.** Accept the cost in 1.1.0, list it in the notes, and add a later step in which gwz-cli treats Ctrl-C as the operation's cancellation, which kills every group. (b) Keep `git` in gwz's group: then a timeout, a cancel or a drop kills `git` alone, and its helper lingers, which in a long-lived gwz-py process accumulates. OQ3's option (a) is this question's (b); under OQ3 (b) or (c), this question stands as written.
- **OQ3. Helpers that prompt (D9, with D10's bound, §3.2's process group and §4's latch).**
  - **1.0.17.** A helper may prompt: the Git Credential Manager's sign-in or OAuth window, or a helper that reads the terminal. It runs with the live environment, in gwz's own process group, with no bound (`CRED:387-428, 451`). gwz-py ran the same callback, so it does not differ from the CLI.
  - **What decides it.** §3.19 sets `GIT_TERMINAL_PROMPT=0` and `-c credential.interactive=false` (P2-1, from CS3.4), and CS §5.8 adds `-c core.askPass=`. That rule was written for a session host that may serve with no user present, and its parity cost was not put to the operator. The process group, which keeps the terminal from the helper, is this design's own. Together they fail with M2 a user whose credential needs interactive refresh, such as Azure DevOps or GitHub through the Git Credential Manager, where 1.0.17 prompted.
  - **Every option keeps git itself silent,** with `GIT_TERMINAL_PROMPT=0` and `-c core.askPass=`: 1.0.17 never ran git's own prompt, and gwz asks for several members at once. Under every option, a helper that prompts through another session, such as gpg-agent's pinentry, is neither stopped nor killed, and may stay after M4, as on 1.0.17.
  - **(a) Parity.** Drop `-c credential.interactive=false`, and start `git` in gwz's own process group. Cost: a kill at the bound, on a cancel or on drop reaches `git` alone, so a prompting helper outlives it. Its window stays open, a terminal helper keeps reading the terminal after gwz exits, and stray helpers build up in a long-lived gwz-py process. The bound then stops gwz waiting, not the helper. OQ2 goes away, since Ctrl-C reaches the helper. No timeout latches. With more members than eight waiting on prompts, the rest wait for a slot within the 30 s allocation deadline, and fail with M10 if the first prompts take longer. Hazard for the notes: N5's first text, and the first text of N6's first sentence.
  - **(b) Recommended: a window, not the terminal.** Drop only `-c credential.interactive=false`; the process group, git's silence and the bound stay, and no timeout latches. The Git Credential Manager turns its terminal prompts off under `GIT_TERMINAL_PROMPT=0` and keeps its window: that is its documentation as recalled here, not checked, and §10's dabeest row confirms it before release. Cost: a helper that prompts on the terminal is stopped there, and fails with M4 at the bound, up to 120 s later; a sign-in slower than the bound fails with M4; and members beyond eight fail with M10, as under (a). OQ2 is unchanged. Hazard for the notes: N5's second text, and the second text of N6's first sentence. gwz-py takes the same option: an unattended Python process has no window to show, and its helper fails as on 1.0.17.
  - **(c) As drafted:** no helper prompts, and a timeout latches its host, since it means a hung helper. Cost: interactive refresh fails with M2, and the user signs in with git first. OQ2 and the bound are unchanged. Hazard for the notes: N5's third text, and the second text of N6's first sentence.
  - **Recommendation: (b).** It brings back the common case, a sign-in window on Windows and macOS, while git stays silent, the terminal stays gwz's, and every kill reaches the spawned group. It amends §3.19's spawn bullet, for 1.1.0's transport. CS §5.8 can keep `credential.interactive=false` for a server's sessions, where no user is present; its next revision states the in-process case.
- **OQ4. A redirect after the challenge (D13).**
  - **1.0.17** follows it, as D13's row says. On macOS and Linux it resends the held credential to the same host unasked, and asks the helper again on another host's 401. On Windows it sends the held credential to the new location, whatever its host. git itself follows a redirect of its first request by its documented default, `http.followRedirects=initial`.
  - **A renamed or transferred private repository on GitHub.** GitHub serves git operations at a repository's old name through a redirect: its documentation as recalled here, not checked. It answers a private repository's anonymous discovery with a 401, which is how 1.0.17's helper was asked for the private member (a 1.0.17 `--verbose` row, `offered=true`, recorded in the working draft `GwzRemoteTransportBugReport.md`, which is not committed), and it shows a private repository, or its new name, only to a request it has authenticated. So the 301 plausibly reaches only the authenticated request, and §3.19's rule would fail every such member that 1.0.17 fetches. How sure: moderately. This is reasoning from GitHub's private-repository behaviour, without network access here, and T13 settles it.
  - **(a) Recommended: parity within discovery's rules.** A 3xx answer to the authenticated discovery request is followed under discovery's validated redirect rules (HTTPS §5): HTTPS only, discovery only, the five-hop limit counted across both phases. The old credential never goes to the new location. The next request goes there without one, and only that location's own 401 starts a fresh lookup, for its URL, whose credential goes there alone (§2.2, §5). Hazard for the notes: the server that received the credential chooses where discovery goes next, and the helper may then answer for that location. That is the exposure an anonymous redirect already has (§2.2), with at most one lookup per URL and six in one discovery. It still differs from 1.0.17 on the same host: it asks afresh where libgit2 resends, so a helper keyed by path (`useHttpPath`) must hold a credential for the new path.
  - **(b) Same origin only.** As (a), for a redirect to the same scheme, host and port, which covers GitHub's renames and transfers; any other ends the operation with M5. A move to another host, which 1.0.17 follows, fails.
  - **(c) As drafted:** §3.19's rule, M5.
  - **Codes under each option.** Under (a) and (d) a redirect is followed, as on 1.0.17, and its location's own outcome has its own code. Under (b), for another origin, and under (c), M5 has the code 1.0.17 gave a redirect it refused (`LG/http.c:246-260`; `libgit2/src/util/net.c:963, 973`): `remote_rejected` on fetch and push, and on clone a failed member with `git_command_failed`, never a quiet skip.
  - **(d) Parity on the same origin.** Follow a same-origin redirect of the authenticated discovery, and resend the held credential to the new path, as libgit2 does; another origin asks afresh, as under (a). Hazard: the credential goes, unasked, to a path the server chose on the same origin. It keeps a `useHttpPath` helper's old-path credential working after a rename.
  - **Recommendation: (a).** It amends §3.19's sentence "A redirect after the challenge ends the operation, with no credential sent" to: "A redirect after the challenge is followed under discovery's rules; no credential goes to its location until that location challenges, and then only one looked up for its URL." TR1.8's rule for an SSPI exchange stays TR1.8's.
- **OQ5. A code for a helper that did not answer in time (§11).** M4 and M10 have no 1.0.17 case, so the catalog's rule decides their code, not parity. They share their facts with M2 and M8, and their recovery, answer or finish the waiting helper and retry, is neither M2's nor M8's. No existing code means a timeout.
  - (a) **Recommended.** Allocate `credential_helper_timeout`, JSON `CredentialHelperTimeout`, at the next free value, 75 at gwz-core `ab48966f`, after `transport_record_limit` (74; `protocol/gwz.taut.py:669-836`). It changes gwz-core's `protocol/gwz.taut.py` (`GwzErrorCode`), its generated `src/protocol/generated.rs` and `candidate_generated.rs`, `model::ErrorCode` (`src/model/mod.rs:13`) with `src/protocol/convert.rs`, gwz-py's generated protocol (`scripts/regen_protocol.py`, checked by `scripts/check_protocol_drift.py`), and `docs/ErrorCatalog.md` and `docs/MessageCatalog.md`. Its catalog row: "A credential helper did not answer within its fixed bound, or no helper slot freed up within the allocation deadline, typically while a helper waited for a sign-in, an unlock or a confirmation. Nothing was sent. | Answer or finish the helper, or sign in once with `git ls-remote <URL>`; then retry."
  - (b) No allocation: M4 and M10 take the boundaries' defaults, `remote_rejected` on fetch and push, as M2 and M8 do, and `git_command_failed` on clone, where they fail the member. A driver tells them from M2 and M8 by message text only, and a later allocation would change their code. Surface's round-2 GO assumes (a).
- **OQ6. Where a wait for a helper slot is charged (§3.3, D10).** 1.0.17 ran every member's helper at once, with no bound. The transport runs at most eight (the endpoint's permits and the host context's slots, `EP/https_auth.rs:27-35`), so a ninth waits.
  - (a) **Recommended.** Charge the wait to the Open's allocation deadline, as E6 decided: up to 30 s, less what the anonymous attempt used. Every helper that starts gets the full interaction allowance, so M4 always names the bound the helper had, and a wait that runs out starts no helper (M10). Hazard for the notes, the first text of N6's second sentence: with more than eight helpers each slower than the budget left, such as sign-in windows under OQ3 (a) or (b), the rest fail with M10 until the user signs in once, where 1.0.17 waited for each.
  - (b) Charge it to the interaction allowance, 120 s, as REUSE:147 does for 1.2.0. More queued members succeed under slow sign-ins. Hazard, the one Safety's round-1 P3-1 named: a queued member's helper gets only what the wait left of 120 s, so M4 names that remainder as what was left of the fixed 120-second allowance, and one member can time out with less time than another had; under OQ3 (c), such an M4 latches the host, though the starved helper may not be hung. The second text of N6's second sentence applies, §9.1's OQ6 contingency amends the 173-177 replacement, and M10 names the allowance.
  - **Recommendation: (a).** Each started helper keeps its stated bound, a wait for capacity is charged like the pipeline's other admission waits (`TH/session/driver.rs:621-623`), and M10's recovery, finishing one sign-in and retrying, clears the queue.
- **OQ7. What crosses from the endpoint (§9.4's C10).** The endpoint reports a failure as its wire code, effect, facts and setup cause only (gwz-transport `src/protocol.rs:603-608, 926-933`), and the core writes the member's error from those (`EP/https_remote.rs:168-196`). §4's wire codes, with the facts, the core's own policy and the failing request, select every code and clone treatment in §11 and every message except three details: whether an `Authentication` lookup failure was M2 or M8, M8's cause, and M6's scheme names. Today every helper failure crosses as `Authentication` (`EP/https_auth.rs:214-228`), and the core prints only the code (`EP/https_remote.rs:191-195`). It is a wire-format decision, so it is the operator's.
  - (1) **Recommended.** An optional detail field on gwz-transport's wire `Failure`. It carries only a cause from M8's fixed set and M6's scheme tokens, at most four, each an HTTP token cut at 32 characters: never helper output, stderr, a URL or the rest of a header, as §5's rule requires of everything gwz reports. It is a wire change, for 1.1.0's gwz-transport release as §6's scope is, which S7.1 (1.1.0) must name. M8 and M6 then read as §11 writes them, T10(b) and T17 assert them, and clone fails a member behind a `Negotiate` challenge without `Basic` loudly, as 1.0.17 did (§11).
  - (2) Shared text, with no wire change: M8's outcomes print M2's text, and M6 names no scheme. Costs, from Surface's round 3: M2 then tells a user whose helper did answer that none did, and its next step, `git ls-remote`, succeeds, since git has no 16 KiB bound and accepts non-UTF-8 bytes, a missing final newline and a value carrying a CR. A user of a CRLF-edited helper script or a CI token helper meets "git works, gwz says no credential", a dead end that reopens round 1's Surface P3-7 as a P3. M6 without the scheme name leaves the user unable to tell the server's administrator what the server offers, reopening the scheme-naming half of round 1's Surface P3-3 as a P3. Mitigations, on the Troubleshooting page: a subsection "git succeeds, gwz reports no credential" that lists M8's causes, with a check of the helper's answer for a CR, its size and its encoding that never prints the secret, and that M2's page pointer leads to; and a check that shows the server's `WWW-Authenticate` header, for example `curl -sI` on `<url>/info/refs?service=git-upload-pack`. §9.1's OQ7 (2) contingency applies, and §11's first two parity exceptions hold in full.
  - **Recommendation: (1).** Every message keeps the text the reviews passed, clone fails a `Negotiate` challenge as 1.0.17 did, and the field carries only fixed, bounded values.
