# GWZ sequenced virtual-stream requirements

Date: 2026-09-24. Status: **DRAFT amendment for review; no implementation authorization**.

This targets [remote transport requirements](GwzRemoteTransportRequirements.md) §5.4 S2, S4, S5, S7 and S9 and the matching remote-transport paragraphs in [GWZRequirements.md](GWZRequirements.md). The operator chose to put ordering in the virtual-stream protocol after the [prior profile-3 design failed review](../../dev-docs/GwzTransportV3ReorderingDesign-Verdict.md). The existing local profile-1/2 implementation and accepted placement, authentication and pool policies remain unchanged until a sequenced profile is negotiated and implemented. The separate [design draft](GwzTransportSequencedStreamDesign.md) supplies a proposed mechanism, not an additional requirement.

**Q1 — Independent streams.** A binding MUST permit arbitrary interleaving of messages for distinct virtual streams. A delayed or blocked message on stream A MUST NOT impose a binding-wide ordering barrier on stream B when B's own admission capacity and prerequisites are available.

**Q2 — Same-stream reordering.** The supplied carrier MAY deliver messages generated by either side of one virtual stream out of order. The virtual-stream service MUST reconstruct each sending direction's causal message order before applying ordinary effects or exposing bytes, EOF, flush completion or graceful close to the file-stream API. It MUST NOT rely on a host per-stream FIFO for correctness. The two directions need no shared total order; explicit request/response and close prerequisites still apply.

**Q3 — Sequence identity.** Every non-bootstrap message in a negotiated sequenced profile MUST have a bounded, non-reused position within its `(binding session, stream ID, sending direction)`. A delayed, duplicate, conflicting or out-of-range position MUST NOT create a second action, duplicate bytes, change a terminal result, transfer authority or release a lease twice. Open and CheckIdentity share the existing binding-scoped stream-ID namespace; accepting a fresh lower ID after a higher ID MUST NOT silently discard it.

**Q4 — Stream equivalence.** Data MUST be exposed exactly once, in byte order, with existing Data offsets and final byte offsets checked. Graceful EndWrite, Close and Closed MUST account for their required predecessor messages and byte ranges before reporting completion. EndWrite is a half-close, and Close requests cleanup; neither ends the initiator message sequence. Window and owed Flushed controls MAY follow Close while reverse output is drained under its finite deadline. Only an actual sender-final message fixes that direction's final message-sequence watermark. A received terminal or byte count alone MUST NOT assert a Git operation succeeded; git2 continues to interpret the Git protocol bytes and errors as with a socket.

**Q5 — Abortive termination.** A validated abortive failure/cancellation MAY supersede preceding messages from its sending direction under an explicit, finite cutoff. Covered frames that arrive later MUST be contained without becoming a successful byte delivery, resurrecting the stream, changing facts or failing unrelated streams solely because of their late arrival. Already-applied effects cannot be rolled back; the existing truthful `Effect` and facts rules still apply. Graceful completion MUST NOT silently skip a missing predecessor.

**Q6 — Bounded progress.** Reassembly, unknown/pre-opening IDs, host queues, decoded copies and blocked delivery receipts MUST have finite per-binding and per-stream budgets. Backpressure MUST leave room and a fair path for an expected missing predecessor to arrive, including while later messages are buffered. A gap, full reserve, lost carrier or unresolved admission/abort race MUST produce a finite explicit outcome; it MUST NOT hang or turn into a successful close. No active Git exchange is transparently replayed after failure.

**Q7 — Truthful admission.** The service MUST distinguish ownership of a bounded out-of-order frame from application of that frame in sequence. A host MUST NOT count buffering, duplicate suppression, stale-session discard or wrong-generation delivery as an applied Open/CheckIdentity or terminal. The host MUST pin the intended sender and receiving Port generation independent of negotiated profile; its delivery receipt MUST refer only to that intended peer. Cancellation of an application waiter MUST NOT silently discard a frame whose peer admission is undecided.

**Q8 — Compatibility and carrier scope.** The new semantics MUST be selected by explicit Bind/Bound negotiation; retained profile-1/2 encodings and behavior MUST remain unchanged. The payload remains taut-defined messages with variable-length Data bytes and may travel in process or through the existing supplied driver–core message channel. No separate raw-byte channel, new Git protocol, daemon, peer network or physical wire qualification is required for this design gate.

**Q9 — Proof.** Deterministic cases and seed-replayable Monte Carlo tests MUST permute messages within and across streams, vary write chunks and read sizes, and verify exact byte reconstruction, ordered controls, terminal facts, bounded memory and finite gap outcomes. They MUST include abortive terminal overtaking in-flight Window/Flushed, graceful Closed preceding Data, a pre-Open frame, post-Close Window and owed Flushed during a reverse drain exceeding initial credit, full reorder capacity with its missing predecessor ready, and two operations sharing one binding where one fails without changing the other.

If accepted, these Q-rules supersede only the same-stream carrier-ordering assumption of §5.4 and, for profile 3, [GwzRemoteTransportDesign.md](GwzRemoteTransportDesign.md) §2's carrier-adapter “Ordered delivery” responsibility and in-process “same ordering” sentence, §4.1's “The carrier supplies reliable ordered delivery for an established session” ordering obligation, and [GwzRemoteTransportPlacementDesign.md](GwzRemoteTransportPlacementDesign.md) §4's “asynchronous, ordered bidirectional delivery” host-adapter obligation. Under profile 3 the carrier supplies bounded delivery and disconnect reporting; the virtual-stream service reconstructs order. Profiles 1/2 retain their existing ordered-carrier contract. The prior S1–S9 protections, placement decisions and endpoint policy continue to apply. Before implementation, incorporate the accepted rules into the authoritative [GWZDesign.md](GWZDesign.md) and baseline [GWZRequirements.md](GWZRequirements.md) as required by this repository's AGENTS instructions.
